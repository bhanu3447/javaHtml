PATTERNS 08 · MOVE 2 · CREATE

Abstract Factory: create a whole matching set, never a mismatch

So far one object was created at a time. Now the dealership sells in India and in the EU, and each market needs a set of parts that match: engine, headlights and number plate. Abstract Factory puts the whole set behind one object, so a car can never get an EU engine with an Indian plate. You will feel the pain, refactor in small steps, watch it run, and choose it like a senior engineer.

PATTERNS 08

Abstract Factory: one object that creates a family of matching products

Seven sections, four levels: a beginner can stop after section 04; sections 05 to 07 add the interview depth. This is the last page of Move 2 (Create), so section 07 ends with a recap table.

01

See it: the problem Abstract Factory solves

Level 1 · See it
In 30 seconds When several objects must belong together (an India engine, India headlights, an India plate), do not create them one by one. Put all the create methods in one factory object per family. The code that builds the car receives one factory and can only ever get a matching set.

The dealership problem. The dealership sells in two markets, India and the EU. An Indian car needs a BS6 engine, headlights for left-hand traffic and an Indian plate; an EU car needs a Euro 6 engine, headlights for right-hand traffic and an EU plate. Today every place that creates a part has its own if (market.equals("IN")) … else …. Three places, three ladders, and nothing forces them to agree.

Words used here. A product is an object being created (an engine). A family is the set of products that belong to one market. A client is the class that uses the products (the assembly line). An interface is a list of methods with no code; concrete means a real class you can build.

💡 Remember itBuying a matched furniture set from one showroom. The "Scandinavian showroom" sells a sofa, a table and a lamp that all match; the "Classic showroom" sells another matching set. Walk into one showroom and you cannot leave with a Scandinavian sofa and a Classic table. Picture the glyph: a set of matching machines, all made by one maker.

02

Build it: from three ladders to one factory per market

Level 2 · Build it
In 30 seconds Three steps. 1) Give each kind of part an interface. 2) Write one interface, PartsFactory, with one create method per part. 3) Write one class per market that implements it, and hand a single factory to the assembly line. Run the program after each step.
Before: three ladders on the market text, and a plate that does not match

What breaks. A new market means editing three ladders. Worse, the ladders are written separately, so they can disagree: here the plate ladder tests "EUR" instead of "EU", so every EU car gets an Indian plate (the line Market EU: … | KA 01 AB 1234). The US row shows the other failure: a market nobody coded falls into the else of every ladder.

Refactor step by step. Use the lab to follow each move.

This visualisation needs JavaScript.

After: Abstract Factory, one factory per market

Each market's three new calls sit in one class, and AssemblyLine contains no class name of a part. Each method of the factory (createEngine(), createHeadlights(), createPlate()) is itself a Factory Method: it creates one product and returns the interface. Abstract Factory is a group of factory methods that must be used together; it is often implemented with them.

The honest weakness: new product vs new family

Adding a new family (the US) was one new class. Adding a new product (a Battery for EVs) goes the other way: the interface changes, so every factory must change. Run it and count the edits.

Go deeper: why not a default method?
You can give createBattery() a default body in the interface so old factories still compile. That hides the cost rather than removing it: a factory that silently inherits the default may build a battery that does not match its family, which is exactly the bug the pattern exists to prevent. Prefer the compile error.

04

Practise: add a family, test with a fake family

Level 2 · Practise

The dealership opens in Japan (left-hand traffic, like India). Add a JapanPartsFactory with its own engine (JC08 engine) and plate (JP 33 A 1234), reusing LeftBeam. Rule: do not edit PartsFactory, AssemblyLine or IndiaPartsFactory.

Hint
Two new product classes (implements Engine, implements NumberPlate) and one new class implements PartsFactory. Then new AssemblyLine(new JapanPartsFactory()).assemble() in main.
Solution

Only new classes and one line in main. Ran on JDK 25:

public class ExJapan {
    public static void main(String[] args) {
        new AssemblyLine(new IndiaPartsFactory()).assemble();
        // Engine: BS6 engine
        // Headlights: left-hand traffic beam
        // Plate: KA 01 AB 1234
        new AssemblyLine(new JapanPartsFactory()).assemble();   // the new family plugs in
        // Engine: JC08 engine
        // Headlights: left-hand traffic beam
        // Plate: JP 33 A 1234
    }
}

interface Engine { String name(); }
interface Headlights { String beam(); }
interface NumberPlate { String show(); }

class Bs6Engine implements Engine { public String name() { return "BS6 engine"; } }
class JapanEngine implements Engine { public String name() { return "JC08 engine"; } }         // NEW
class LeftBeam implements Headlights { public String beam() { return "left-hand traffic beam"; } }
class IndianPlate implements NumberPlate { public String show() { return "KA 01 AB 1234"; } }
class JapanPlate implements NumberPlate { public String show() { return "JP 33 A 1234"; } }    // NEW

interface PartsFactory {                                  // unchanged
    Engine createEngine();
    Headlights createHeadlights();
    NumberPlate createPlate();
}

class IndiaPartsFactory implements PartsFactory {         // unchanged
    public Engine createEngine() { return new Bs6Engine(); }
    public Headlights createHeadlights() { return new LeftBeam(); }
    public NumberPlate createPlate() { return new IndianPlate(); }
}

class JapanPartsFactory implements PartsFactory {         // NEW: one class
    public Engine createEngine() { return new JapanEngine(); }
    public Headlights createHeadlights() { return new LeftBeam(); }   // Japan drives on the left: reuse
    public NumberPlate createPlate() { return new JapanPlate(); }
}

class AssemblyLine {                                      // unchanged
    private final PartsFactory parts;
    AssemblyLine(PartsFactory parts) { this.parts = parts; }
    void assemble() {
        System.out.println("Engine: " + parts.createEngine().name());
        System.out.println("Headlights: " + parts.createHeadlights().beam());
        System.out.println("Plate: " + parts.createPlate().show());
    }
}

Test AssemblyLine without any real part class. Write a fake factory whose three create methods return stubs (Stub engine, Stub beam, Stub plate) and assemble a car with it.

Hint
An anonymous class implementing PartsFactory is enough. Engine, Headlights and NumberPlate each have one method, so a lambda such as () -> "Stub engine" can be the product.
Solution

Because the line only knows the interface, a test can hand it a fake family. Ran on JDK 25:

public class FakeFactory {
    public static void main(String[] args) {
        PartsFactory fake = new PartsFactory() {          // a fake family for a test: no real parts
            public Engine createEngine() { return () -> "Stub engine"; }
            public Headlights createHeadlights() { return () -> "Stub beam"; }
            public NumberPlate createPlate() { return () -> "Stub plate"; }
        };
        new AssemblyLine(fake).assemble();
        // Engine: Stub engine
        // Headlights: Stub beam
        // Plate: Stub plate
    }
}

interface Engine { String name(); }
interface Headlights { String beam(); }
interface NumberPlate { String show(); }

interface PartsFactory {
    Engine createEngine();
    Headlights createHeadlights();
    NumberPlate createPlate();
}

class AssemblyLine {

    AssemblyLine(PartsFactory parts) { this.parts = parts; }
    void assemble() {
        System.out.println("Engine: " + parts.createEngine().name());
        System.out.println("Headlights: " + parts.createHeadlights().beam());
        System.out.println("Plate: " + parts.createPlate().show());
    }
}

Explain Abstract Factory to a new teammate using the two markets: what is the family, what does the factory guarantee, what is easy to add and what is hard?

Model answer. A market needs a family of parts that match: engine, headlights, plate. PartsFactory has one create method per part, and each market has one implementation (IndiaPartsFactory, EuPartsFactory). AssemblyLine receives one factory and asks it for every part, so the parts always come from the same family and an EU car cannot get an Indian plate. A new market is one new factory class (easy, nothing existing changes). A new kind of part, such as Battery, changes the interface and every factory (hard).
05

Choose it: roles, look-alikes and trade-offs

Level 3 · Choose it
In 30 seconds Use Abstract Factory when you must create several related objects that have to match, and the family changes together (a market, a theme, a database vendor). Do not use it for one product, or when the list of product kinds keeps growing.

This visualisation needs JavaScript.

Use it when

  • Products come in families that must be used together (engine + headlights + plate for one market).
  • You want to switch the whole family in one place (configuration, a Spring profile) without touching the client.
  • The set of product kinds is stable, but new families keep arriving.

Do not use it when

  • There is one product that varies: a Factory Method or a plain factory is simpler.
  • The product kinds keep growing (a new Battery, then Seats…): every addition edits every factory.
  • The parts do not really need to match: separate factories or a Supplier each are enough.

Trade-offs

  • Consistency: the main benefit. One factory means one family, so mismatches cannot be built.
  • Extensibility: a new family is one class; a new product kind changes the interface and every factory (the Open / Closed principle holds in one direction only).
  • Complexity: many small classes (interfaces, concrete products, factories). Heavy for two products.
  • Coupling and testing: the client depends only on interfaces; a fake factory makes tests trivial (section 04).
  • The factory is still chosen somewhere: put that choice at the edge (startup, configuration, dependency injection).
  • Performance: a few virtual calls; not a concern.

In a Spring Boot backend

A conceptual sketch. A @Profile on a @Configuration class makes Spring register that class's beans only when the profile is active, so the active profile chooses the family once at startup. The services just ask for the beans (dependency injection) and never mention a market.

@Configuration
@Profile("eu")
class EuPartsConfig {
    @Bean PartsFactory partsFactory() { return new EuPartsFactory(); }
}

@Configuration
@Profile("in")
class IndiaPartsConfig {
    @Bean PartsFactory partsFactory() { return new IndiaPartsFactory(); }
}

@Service
class AssemblyService {
    private final PartsFactory parts;            // the active profile decides which one

    AssemblyService(PartsFactory parts) { this.parts = parts; }

    void assemble() { new AssemblyLine(parts).assemble(); }
}

Start with --spring.profiles.active=eu (or the SPRING_PROFILES_ACTIVE environment variable) and the EU family is injected everywhere. A variation gives each profile's configuration the individual beans (Engine, Headlights, NumberPlate) instead of a factory object.

Where Java and Spring already use it

  • javax.xml.parsers.DocumentBuilderFactory and javax.xml.transform.TransformerFactory: newInstance() finds an implementation, and the factory then creates its matching parser or transformer objects (conceptually similar: they create objects of one implementation family, not a literal GoF structure).
  • java.sql.Connection: its createStatement() and prepareStatement(...) create statement objects that belong to that connection's driver (conceptually similar: a family of related objects from one vendor).
  • Spring: @Profile("eu") on a @Configuration class chooses which family of beans the application gets.

In this code (it ran on JDK 25), which line behaves like asking a chosen factory to create one product?

import javax.xml.parsers.DocumentBuilder;
import javax.xml.parsers.DocumentBuilderFactory;
import org.w3c.dom.Document;

public class SpotXml {
    public static void main(String[] args) throws Exception {
        DocumentBuilderFactory f = DocumentBuilderFactory.newInstance();   // picks an implementation
        DocumentBuilder b = f.newDocumentBuilder();                        // line A: asks the chosen factory
        Document doc = b.newDocument();
        doc.appendChild(doc.createElement("car"));
        System.out.println(doc.getDocumentElement().getTagName());
    }
}
// car
  1. DocumentBuilderFactory.newInstance()
  2. f.newDocumentBuilder()
  3. b.newDocument()
  4. doc.createElement("car")
newInstance() picks the implementation of the factory itself (like choosing the market). Then f.newDocumentBuilder() asks that chosen factory to create a product, which is the "create method on a factory" role. It is conceptually similar to Abstract Factory, not a strict implementation: the JDK type is one factory class with a few create methods, and the implementation is found by lookup.
06

Master it: Abstract Factory in modern Java

Level 4 · Master it
In 30 seconds A factory is just "a way to create each product", so a record of Suppliers can be a whole family without writing a class per market. An enum that implements the factory interface gives you one constant per market and a safe valueOf lookup. Choose the factory once at startup and pass it down.
Create the family with…when
a class per marketeach factory has real logic (pricing, validation) or many products
a record of Suppliersa family is only "which class for each product"; no class per market
enum Market implements PartsFactorythe markets are a fixed, known list and you want valueOf and switch support
Spring profiles / DIthe family comes from configuration; no code ever reads a market name

Choosing the factory. The decision "which family" should be made once, at startup, from configuration or an environment variable, and the factory passed to everything that needs it. With dependency injection the container does that for you, which replaces the manual if (market…) that the pattern was meant to remove.

Advanced details: sharing and thread safety
Factories are usually stateless, so one instance can be shared by all threads (a Spring singleton bean, an enum constant). If a factory keeps a cache or counter, make that state thread-safe. A factory that returns a shared product (one Engine instance for all cars) is fine only if the product is immutable.
Common mistakes
  • Mixing factories: creating the engine from one factory and the plate from another. The pattern only protects you if the client holds one factory.
  • Returning concrete types from create methods (Bs6Engine createEngine()): clients depend on classes again.
  • Putting the market if inside the factory methods instead of having one factory per family.
  • Using it for one product: that is a Factory Method or a plain factory.
  • Letting product kinds grow without noticing that every factory changes each time.
  • Reading the market text everywhere instead of once at the edge.

A new requirement. The dealership launches an EV line: every market now needs a Battery, and next year a Charger too. Markets are stable (India, EU). Which design do you choose?

  1. Keep Abstract Factory unchanged and add if (market…) in the assembly line for batteries
  2. Add a createBattery() default method returning an Indian battery for every market
  3. Keep Abstract Factory: add createBattery() (and later createCharger()) to the interface and to every factory, accepting the edits so every market stays consistent
  4. Replace the factories with a single static CarFactory.create(market) switch
The product kinds grow, which is the pattern's weak direction, but with only two markets the edits are few and the compiler lists every factory you forgot. Option 1 reintroduces ladders. Option 2 silently gives EU cars an Indian battery: the mismatch bug again. Option 4 loses the guarantee. If kinds kept growing with many markets, consider splitting into smaller factories or a Builder per car.

Patterns it works with

  • Factory Method: every create method of an Abstract Factory is one.
  • Singleton: a concrete factory is often a single shared instance (an enum constant, a Spring bean).
  • Builder: when the problem is one product built in many steps rather than several matching products.
  • Prototype: a factory can hold prototypes and clone them instead of calling new.
  • Bridge (not built yet): another way to vary two dimensions independently.

Interview and review

Interview and review

Answer out loud first, then open the card.

01What is the Abstract Factory pattern? (the 30-second answer)
B · Abstract Factory is an interface for creating a family of related objects without naming their concrete classes. Each concrete factory creates one matching family; the client receives one factory and can only get products that go together. Example: PartsFactory with createEngine(), createHeadlights(), createPlate(), implemented by IndiaPartsFactory and EuPartsFactory.
02Walk me through it in more depth.
I · Roles: AbstractProducts (Engine…), ConcreteProducts, AbstractFactory (PartsFactory), ConcreteFactories, and the Client that holds only the abstract types. The factory is injected (constructor injection), so the choice of family is made once, outside the client. Benefits: consistency across products, one place per family, easy swapping and faking. Cost: many classes, and a new product kind changes the interface and every factory.
03Abstract Factory vs Factory Method?
I · Factory Method creates one product and uses inheritance: a subclass overrides one method. Abstract Factory creates a family and uses composition: the client holds a factory object with several create methods. Each method of an Abstract Factory is often a Factory Method. Rule of thumb: one product chosen by a subclass = Factory Method; several products that must match = Abstract Factory.
04What is easy and what is hard to add?
I · A new family (the US market) is one new factory class plus its products: nothing existing changes. A new product kind (Battery) adds a method to the interface, so every factory must change. That asymmetry is the pattern's main weakness, and a reason to avoid it when product kinds keep growing.
05How does it enforce consistency?
B · The client gets one factory and every product comes from it, so all products belong to one family. The family's new calls live in one class, so they cannot disagree the way separate if / else ladders can (the EU car with an Indian plate). It is not magic: if the client is given two different factories it can still mix.
06How does dependency injection replace manual factory selection?
I · Instead of code reading a market name and picking a factory, the container creates the right factory bean from configuration (for example a @Profile("eu") @Configuration) and injects it into the services. No application code contains the choice. In plain Java the same idea is "pick the factory once in main and pass it down".
07Difference from Builder?
I · Builder constructs one complex object in steps and returns it at the end. Abstract Factory returns several related products immediately, one per call. They combine well: a factory can hand out Builders.
08Is DocumentBuilderFactory an Abstract Factory?
I · Conceptually similar, not literal. DocumentBuilderFactory.newInstance() locates an implementation and the factory creates its parser objects; TransformerFactory works the same way. They show the idea of "one implementation family behind an interface", but there is no interface with matching product kinds as in the textbook structure. Say "conceptually similar" in an interview.
09How would you test code that uses an Abstract Factory?
I · Pass a fake factory that returns stubs (section 04). Because the client depends only on interfaces, no real engine, database or network is involved.
10Your product list grows every sprint. What do you do?
A · Each new product edits the interface and all factories, and every factory is a merge-conflict magnet. Options: split into smaller factories (a drivetrain factory and a body factory), use a record of Suppliers or a registry so a family is data rather than a class, build one car with a Builder that takes the market, or accept the edits if there are only a few markets and the compiler's list of broken factories is a feature. Avoid default methods that silently mix families.

8 takeaways

  • Abstract Factory: an interface with one create method per product, one implementation per family.
  • Roles: AbstractFactory = PartsFactory, ConcreteFactory = EuPartsFactory, AbstractProduct = Engine, Client = AssemblyLine.
  • The smell: if / else on a type code in several places that must agree, and an occasional mismatched set.
  • The client receives one factory (constructor injection), so it can only build a matching set.
  • Each create method is itself a Factory Method.
  • New family = one new class; new product kind = change the interface and every factory.
  • Modern Java: a record of Suppliers or an enum implementing the factory; choose the factory once at startup, or let Spring profiles and DI do it.
  • Do not use it for one product or when product kinds keep growing.
