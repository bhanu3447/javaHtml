Prototype: copy a finished example

Builder builds an object from parts, step by step. Prototype starts from a finished example and copies it, like a showroom's display car used as the model for an order. The catch is what "copy" means: a careless copy shares the original's list, and one change shows up in both. This page shows that bug, then fixes it. It also shows why a copy can break a Singleton.

PATTERNS 07

Prototype: start every demo car from a ready-made one

Seven sections, four levels: a beginner can stop after section 04; sections 05 to 07 add the interview depth.

01

See it: the problem Prototype solves

Level 1 · See it
In 30 seconds When an object is long to set up, do not build the next one from scratch: copy one that is already set up, then change what differs. Each object knows how to copy itself (a copy() method), so the caller does not need to know its class. The one thing to get right is how deep the copy goes.

The dealership problem. A demo car is a car kept for test drives. It has a trim (the version, like XZ+), a colour, a List of accessories, a Map of dealer-fitted extras with their prices in rupees, and a ServiceHistory object. Every new demo car repeats all that set-up. Worse, the booking code only holds a Car (an interface: a list of methods, with no fields). It needs a copy of "whatever this is", and it does not know whether that is a PetrolCar or an EvCar.

Words used here. A client is code that uses a class. A reference is the arrow from a variable to an object. A shallow copy copies the references, so both objects point at the same inner objects. A deep copy also copies the inner objects.

💡 Remember itA photocopier. You do not retype a form; you put the finished one on the glass and press a button, then write the new name on the copy. In the showroom, the display car is the master for an order: copy it, then change the colour. A shallow photocopy of a form that says "see attached sheet" copies the words but not the sheet, so both forms point at one sheet.

02

Build it: from repeated set-up to copy()

Level 2 · Build it
In 30 seconds 1) Give each class a copy constructor that copies its fields deeply. 2) Declare Car copy() on the interface. 3) Keep ready-made template cars in a Map (the prototype registry) and hand out copies, never the template.
Before: repeat the set-up, and copy by hand with instanceof

What breaks. nexonDemo() is called for every new car, so the full set-up runs each time. duplicate(Car) needs one instanceof branch per class, and it forgot the extras and the service history: the copy prints extras=0 and services=0, and the compiler said nothing.

The refactor. Use the lab to see each step and why it is made. Step 1 is deliberately wrong, so you meet the shallow-copy bug early.

This visualisation needs JavaScript.

After: copy() on the interface, a deep copy constructor and a registry

The client never writes new and never names a class: registry.create("tiago-ev-demo") gives back an EvCar (the last line prints EvCar). Changing the copy's colour or accessories leaves the template alone, because the copy constructor made its own list, its own extras map and its own history. Long and String values are immutable, so copying the map and list contents is enough here.

Go deeper: why copy() and not clone()?
The JDK has Object.clone() and the marker interface Cloneable. They are awkward (section 06 shows why), so most Java code writes its own copy() or a copy constructor. The pattern is the same; only the mechanism differs.

04

Practise: copy a quote, then build a registry

Level 2 · Practise

A Quote holds a list of items. Add a copy() method so that adding an item to the copy does not change the original. Expected lines: [Mats] and [Mats, Alarm].

Hint
A copy constructor that takes another Quote. Make a new list and add the other quote's items to it: items.addAll(other.items). Do not write this.items = other.items.
Solution

Ran on JDK 25:

import java.util.*;

public class ExCopy {
    public static void main(String[] args) {
        Quote original = new Quote();
        original.add("Mats");
        Quote copy = original.copy();
        copy.add("Alarm");
        System.out.println(original.items());   // [Mats]
        System.out.println(copy.items());       // [Mats, Alarm]
    }
}

class Quote {
    private final List<String> items = new ArrayList<>();

    Quote() { }
    private Quote(Quote other) { items.addAll(other.items); }        // a new list: the copy owns its items

    Quote copy() { return new Quote(this); }
    void add(String item) { items.add(item); }
    List<String> items() { return items; }
}

Build a QuoteRegistry: register(key, template) and create(key). create must return a copy (so the template stays clean) and throw IllegalArgumentException("No template: luxury") for an unknown key. Expected lines: [Mats, Alarm], [Mats], No template: luxury.

Hint
Keep a Map<String, Quote>. In create, look the key up, throw if it is null, otherwise return template.copy(), never the template itself.
Solution

Ran on JDK 25:

import java.util.*;

public class ExRegistry {
    public static void main(String[] args) {
        QuoteRegistry registry = new QuoteRegistry();
        Quote base = new Quote();
        base.add("Mats");
        registry.register("basic", base);

        Quote mine = registry.create("basic");
        mine.add("Alarm");
        System.out.println(mine.items());                       // [Mats, Alarm]
        System.out.println(registry.create("basic").items());   // [Mats]
        try { registry.create("luxury"); }
        catch (IllegalArgumentException e) { System.out.println(e.getMessage()); }   // No template: luxury
    }
}

class QuoteRegistry {
    private final Map<String, Quote> templates = new HashMap<>();
    void register(String key, Quote template) { templates.put(key, template); }
    Quote create(String key) {
        Quote t = templates.get(key);
        if (t == null) throw new IllegalArgumentException("No template: " + key);
        return t.copy();                                         // hand out a copy, keep the template safe
    }
}

class Quote {
    private final List<String> items = new ArrayList<>();
    Quote() { }
    private Quote(Quote other) { items.addAll(other.items); }
    Quote copy() { return new Quote(this); }
    void add(String item) { items.add(item); }
    List<String> items() { return items; }
}

Explain Prototype to a new teammate with the demo car: why copy instead of building again, what is the difference between a shallow and a deep copy, and what goes wrong with a shallow copy?

Model answer. Prototype creates a new object by copying an existing, already configured one, then changing what differs. It saves repeating a long set-up, and with a copy() method on the interface the caller does not need to know the concrete class. A shallow copy copies only the references, so the copy and the original share the same inner list and objects: adding an accessory to the copy also changes the original demo car. A deep copy also copies the inner objects (the list, the map, the ServiceHistory), so the copy is independent. Immutable values like String can be shared safely. A registry of templates ("nexon-demo") hands out copies, never the template itself.
05

Choose it: when copying beats building

Level 3 · Choose it
In 30 seconds Use Prototype when new objects are mostly the same as an existing one and the set-up is long, or when the code that needs a copy only knows an interface. Skip it for small or immutable objects: a constructor, a record or a withX() method is simpler.

This visualisation needs JavaScript.

Use it when

  • Objects are costly to set up (many settings, a database read, a heavy calculation) and each new one differs only a little from a standard one.
  • The code needs "a copy of this" but only holds an interface, so it cannot say new ConcreteClass().
  • You want a few named starting points (a registry of templates) instead of a family of subclasses.

Do not use it when

  • The object is small or immutable: just call the constructor, or use a record with a withColour(...) method (section 06).
  • The object holds things that must not be duplicated: a database connection, an open file, a Singleton. Copying a Singleton gives you a second "one".
  • The object graph is tangled (cycles, shared parts): a deep copy gets hard to write correctly. Rebuilding from a Builder is clearer.

Trade-offs

  • Complexity: a copy method per class, and every new field must be added to it. A forgotten field is a silent bug.
  • Extensibility: a new subclass writes its own copy(); callers do not change.
  • Coupling: low: the caller depends only on the interface.
  • Testing: easy to check: copy, change the copy, assert the original is unchanged.
  • Performance: a copy is cheaper than a long set-up, but a very deep copy of a big graph is not free. Copy only what must be independent.

In a Spring Boot backend

A conceptual sketch. A service keeps preconfigured template cars and copies one per order. Spring's @Scope("prototype") has a related name but a different mechanism: the container builds a new bean from the bean definition each time one is requested. It does not clone an existing instance.

@Configuration
class DemoCars {
    @Bean("nexon-demo")                          // a template: configured once, at startup
    Car nexonDemo() { return new PetrolCar("Nexon", "XZ+", "Blue"); }
}

@Service
class OrderService {
    private final Map<String, Car> templates;     // Spring injects every Car bean, keyed by bean name
    OrderService(Map<String, Car> templates) { this.templates = templates; }

    Car newOrder(String key) {
        return templates.get(key).copy();        // Prototype: copy the template, never hand it out
    }
}

@Component
@Scope("prototype")                              // a NEW bean from the definition per request:
class TestDriveSession { }                       // related name, but not a copy of an instance

Where Java and Spring already use it

  • Object.clone() and Cloneable: the JDK's built-in copy mechanism (section 06 explains the problems).
  • ArrayList.clone(): a shallow copy. The new list holds the same element objects.
  • new ArrayList<>(collection): the copy constructor. Also shallow: a new list, the same elements. List.copyOf(...) makes an unmodifiable copy.
  • Spring: @Scope("prototype") is conceptually similar only: it creates a new bean from the definition on each request.

import java.util.*;

        List<StringBuilder> a = new ArrayList<>();
        a.add(new StringBuilder("Nexon"));
        List<StringBuilder> b = new ArrayList<>(a);     // the copy constructor
        b.add(new StringBuilder("Tiago"));
        b.get(0).append("!");
        System.out.println(a.size());                   // 1

new ArrayList<>(a) copies the list but not the StringBuilder inside it: a and b hold the same StringBuilder. Adding "Tiago" to b does not touch a (so a.size() is 1), but append("!") changes the shared object, so a.get(0) prints Nexon!. A shallow copy.
06

Master it: Cloneable, records and graphs

Level 4 · Master it
In 30 seconds The JDK's Object.clone() is shallow by default, skips constructors, throws a checked exception and fights final fields. Effective Java (Item 13) advises a copy constructor or copy factory instead. For immutable data, use a record and withX() methods.

Object.clone() and Cloneable: why most teams avoid it

The program shows four problems: clone() copies fields as they are (the list is shared), no constructor runs (the counter stays at 1), a class that does not implement Cloneable throws CloneNotSupportedException, and ArrayList.clone() is shallow too.

The full list of problems (Effective Java, Item 13)
  • Shallow by default. You must override clone() and copy every mutable field yourself.
  • No constructor call. Checks and set-up in the constructor are skipped, so a clone can be an inconsistent object.
  • Checked exception. CloneNotSupportedException must be caught or declared, even when the class is Cloneable.
  • Final fields. super.clone() copies them as they are, and you cannot assign a final field again to give the copy its own list. That is why the field in CloneCar cannot be fixed inside clone().
  • Odd design. Cloneable has no clone() method: it only changes how the protected Object.clone() behaves. Object.clone() is protected.
  • Subclasses. A subclass must remember to override clone() too, or the copy has the wrong class.
The recommended alternatives are a copy constructor (new PetrolCar(other)) or a copy factory (PetrolCar.copyOf(other)), as in section 02. Arrays are the exception: array.clone() is fine.

Modern Java: records, withX() and defensive copies

A record is an immutable data class. Nothing can change after it is built, so nothing needs to be copied to stay safe. To "change" one field, you create a new record: nexon.withColour("Red"). The compact constructor uses List.copyOf(...) to make an unmodifiable copy of the list the caller passed in (a defensive copy), so the caller cannot change the record later through its own list.

Copying object graphs with cycles

A deep copy that simply calls copy() on every field loops forever if the objects point at each other (a car holds its Dealer, the Dealer holds its cars): you get a StackOverflowError. The fix is to remember what you already copied: keep an IdentityHashMap<Object, Object> from old object to new object, and reuse the new one when you meet the old one again. Another route is to serialize and read back, which handles cycles but is slow and needs Serializable. If the graph is this tangled, ask whether you should copy at all.

Common mistakes
  • A shallow copy of a mutable field: the copy and original share one list or map. Always copy mutable inner objects.
  • Handing out the template itself: a registry that returns the stored object lets any client change the master. Return template.copy().
  • A new field is not added to the copy constructor: the copy silently has a default value. A test that compares original and copy catches this.
  • Using Cloneable when a copy constructor is clearer.
  • Copying a Singleton (or any object with a unique identity, such as a connection): the copy breaks the "one" rule. Do not make a Singleton Cloneable (see Singleton).
  • Mixing up Spring's prototype scope with the pattern: Spring builds a new bean from its definition; it does not copy an instance.

A new requirement. The booking service must create orders from "nexon-demo" and "tiago-ev-demo" without knowing the class. Each demo car holds an accessories list and a ServiceHistory, and a new SuvCar class arrives next month. Which design do you choose?

  1. Make Car Cloneable and call super.clone() in each class
  2. A static duplicate(Car) with an instanceof branch per class
  3. Car copy() on the interface, each class copying its list and history in a copy constructor, and templates kept in a registry
  4. Give every desk the same template object and let each desk change what it needs
Option 3 is the pattern: the caller needs no class name, and the new SuvCar only writes its own copy(). Option 1 is shallow by default and would share the list and history. Option 2 needs a new branch for every class and is easy to get wrong. Option 4 shares one object, so the desks overwrite each other's changes.

Patterns it works with

  • Builder: build a template once, then copy it. Builder builds from parts; Prototype copies a finished example.
  • Singleton: cloning can break a Singleton, so such a class must not be copyable.
  • Factory Method: a factory can return a copy of a prototype instead of calling new.
  • Abstract Factory (lesson 08, coming): a factory can keep prototypes and copy them to make its products.
  • Composite (lesson 19, coming): copying a tree means copying the whole tree, the deep-copy problem again.
  • Memento (lesson 18, coming): a snapshot to restore (undo), not a new object to use.

Interview and review

Interview and review

Answer out loud first, then open the card.

01What is the Prototype pattern? (the 30-second answer)
B · Prototype creates new objects by copying an existing, configured object instead of building from scratch. Each class declares a copy() method, so the caller can copy an object without knowing its class. Often a registry keeps ready-made templates. Example: the dealership's "nexon-demo" car is copied for each order, and only the colour changes. The key risk is a shallow copy that shares inner objects.
02Walk me through a Prototype design in Java, and the traps.
I · A Car interface with copy(). Each class (PetrolCar, EvCar) implements it with a copy constructor that deep-copies mutable fields: a new ArrayList, a new Map, history.copy(). A CarRegistry holds a Map<String, Car> of templates and returns template.copy(), never the template. Traps: a forgotten field, a shallow copy of a mutable field, subclasses that forget to override copy() (the copy has the parent's class), and returning the template itself.
03Shallow copy vs deep copy?
B · A shallow copy copies the object's fields, so reference fields point at the same inner objects: change the list through the copy and the original changes too. A deep copy also copies the inner objects (recursively), so the two share nothing mutable. Immutable inner values (String, Long, records of immutables) can be shared safely, so a "deep enough" copy copies only what is mutable.
04Why does Effective Java advise against Cloneable?
I · Item 13: the contract is extra-linguistic. clone() is shallow by default, so you must override it and fix mutable fields; it does not call a constructor, so invariants can break; Object.clone() is protected and throws the checked CloneNotSupportedException; final fields cannot be replaced in the copy; and Cloneable itself declares no method. Prefer a copy constructor or a copy factory. Arrays are the exception: array.clone() is fine.
05What is a prototype registry and why return a copy?
I · A registry (a Map<String, Prototype>) stores preconfigured examples under a name and returns a copy of the chosen one. If it returned the stored object, a client could change the template and every later copy would inherit that change. It also hides the concrete classes: the client asks for "tiago-ev-demo" and gets an EvCar.
06When is copying cheaper than building?
I · When construction is expensive or long: many settings, data loaded from a database or file, a heavy calculation, or a long builder chain that is the same for most objects. Copying memory is usually cheaper than redoing that work. If construction is two lines, copying only adds code, and for immutable objects a record with withX() is simpler. Measure before claiming a speed gain.
07How do you copy an object graph with cycles?
A · A naive recursive deep copy never ends on a cycle (StackOverflowError). Keep an IdentityHashMap from original to copy; when you meet an original that already has a copy, reuse it. That also keeps shared parts shared in the copy. Alternatives: serialize and deserialize (handles cycles, slow, needs Serializable), or avoid copying such a graph.
08Prototype vs Builder vs Factory Method?
B · Factory Method: a method decides which class to create. Builder: assemble a complex object from parts, step by step. Prototype: start from a finished example and copy it. They combine: build a template once with a Builder, keep it in a registry, hand out copies.
09Prototype vs Memento?
I · Both copy state, but for different goals. Prototype makes a new, independent object to use. Memento captures a snapshot of an object so it can be restored later (undo). A memento is kept and put back; a prototype copy lives its own life.
10Is Spring's @Scope("prototype") the Prototype pattern?
I · Conceptually similar, not literally. With prototype scope the container creates a new bean from the bean definition each time it is requested; it does not clone an existing instance. The name is related: you get a fresh object every time, unlike the default singleton scope. Watch one trap: a prototype bean injected into a singleton is created once, at injection. Use ObjectProvider to get a new one each time.
11How would you copy a Java record?
B · You rarely copy one: it is immutable, so sharing is safe. To change one field, build a new record: withColour(...) calls the constructor with the new value. For a mutable collection component, the compact constructor does List.copyOf(...) so the record owns an unmodifiable copy.

8 takeaways

  • Prototype: create a new object by copying a configured one, then change what differs.
  • Declare copy() on the interface: the caller needs no class name.
  • A shallow copy shares inner objects, so a change in the copy shows in the original.
  • A deep copy copies the mutable inner objects too; immutable values like String may be shared.
  • A prototype registry keeps named templates and always returns a copy, never the template.
  • Object.clone() is shallow, skips constructors and throws a checked exception: prefer a copy constructor (Effective Java, Item 13).
  • For immutable data use a record and withX(); use List.copyOf for defensive copies.
  • Spring's @Scope("prototype") builds a new bean from its definition; it does not clone an instance.
