Singleton: one object for the whole program

In Factory Method and Builder you controlled how objects are made. Singleton goes further: it controls how many. A dealership has one stock register, and every desk must use that same book. You will see what goes wrong when each desk makes its own copy, fix it in small steps, and learn when one shared object is right and when it is a trap.

PATTERNS 06

Singleton: one stock register for the whole showroom

Seven sections, four levels: a beginner can stop after section 04; sections 05 to 07 add the interview depth.

01

See it: the problem Singleton solves

Level 1 · See it
In 30 seconds Some things must exist once: the stock register, the settings, a cache. Singleton makes the class itself guarantee that. The constructor is private, the class keeps its one instance in a static field, and everyone asks for it through getInstance(). Every caller then shares the same object.

The dealership problem. The showroom keeps a VehicleRegistry: the list of cars in stock, found by chassis number (the number stamped on each car, like CH-101). The sales desk, the service desk and the month-end reports all need it. Each of them writes new VehicleRegistry(), so each gets its own copy. When the sales desk sells a car, only its own copy changes.

Words used here. A class is the blueprint; an object (or instance) is one thing built from it with new. Static means "belongs to the class, not to one object". A constructor is the method that builds an object. Private means only the class itself may use it. A client is code that uses a class.

💡 Remember itThe showroom has one stock register book. Sales, service and reports all write in and read from that same book. If every desk photocopied its own book, the copies would drift apart. A glyph for it: one key on one hook: anyone may borrow it, nobody may cut a second.

02

Build it: from new everywhere to one instance

Level 2 · Build it
In 30 seconds Three steps. 1) Make the constructor private. 2) Keep the single object in a private static final field. 3) Add public static getInstance() that returns it. Then replace every new VehicleRegistry() with VehicleRegistry.getInstance().
Before: every desk builds its own registry

What breaks. The program prints "created" three times: three registries. After salesDesk.sell("CH-101") the sales desk says the car is gone but Reports still says it is in stock, and the counts are 2, 3 and 3. salesDesk == reports is false: they are different objects. Nothing in the class stops a fourth copy.

The refactor. Use the lab to see each step and why it is made.

This visualisation needs JavaScript.

After: a private constructor, a static field and getInstance()

The desks never write new. All three get the same object, so a sale at the sales desk is visible in Reports, and salesDesk == reports is true. This is eager initialisation: the registry is created when the class loads, which is simple and safe with several threads (the JVM loads a class only once). Printing "created" once, before main runs its first line, shows when it happened.

Go deeper: why final on the class?
A subclass could add a public constructor or a second instance. Marking the class final closes that door. It also tells the reader "this really is the only one".

04

Practise: make one, then make it testable

Level 2 · Practise

The dealership numbers its invoices with an InvoiceNumbers class that counts INV-1, INV-2... Two desks must never produce the same number, so there must be exactly one counter. Make InvoiceNumbers a Singleton. Expected lines: INV-1, INV-2, true.

Hint
The three pieces from section 02: a private constructor, a private static final field that holds the one object, and a public static getInstance() that returns it. Then both callers use getInstance().
Solution

Ran on JDK 25:

public class ExInvoice {
    public static void main(String[] args) {
        InvoiceNumbers a = InvoiceNumbers.getInstance();
        InvoiceNumbers b = InvoiceNumbers.getInstance();
        System.out.println(a.next());      // INV-1
        System.out.println(b.next());      // INV-2
        System.out.println(a == b);        // true
    }
}

final class InvoiceNumbers {
    private static final InvoiceNumbers INSTANCE = new InvoiceNumbers();   // 1. private static field
    private int last;

    private InvoiceNumbers() { }                                            // 2. private constructor

    public static InvoiceNumbers getInstance() { return INSTANCE; }        // 3. the one way in

    String next() { return "INV-" + (++last); }
}

StockReport calls VehicleRegistry.getInstance() inside its method, so you cannot test it without the real registry. Refactor so a test can pass a fake: add an interface StockLookup with isInStock(String), let VehicleRegistry implement it, and give StockReport a constructor that takes a StockLookup. Expected lines: CH-101: in stock, CH-999: sold out, CH-102: in stock.

Hint
The class that uses the registry should not know it is a Singleton. Pass it in (constructor injection) as the interface type. Only the place that wires the program together calls getInstance(), once.
Solution

The fake is a one-line lambda, because StockLookup has one method. Ran on JDK 25:

import java.util.*;

public class ExTestable {
    public static void main(String[] args) {
        StockLookup fake = chassis -> chassis.equals("CH-101");        // a test double: no real registry needed
        StockReport report = new StockReport(fake);
        System.out.println(report.line("CH-101"));    // CH-101: in stock
        System.out.println(report.line("CH-999"));    // CH-999: sold out

        StockReport real = new StockReport(VehicleRegistry.getInstance());   // production wiring, done once
        System.out.println(real.line("CH-102"));      // CH-102: in stock
    }
}

interface StockLookup { boolean isInStock(String chassis); }

final class VehicleRegistry implements StockLookup {
    private static final VehicleRegistry INSTANCE = new VehicleRegistry();
    private final Set<String> inStock = new TreeSet<>(List.of("CH-101", "CH-102", "CH-103"));
    private VehicleRegistry() { }
    public static VehicleRegistry getInstance() { return INSTANCE; }
    public boolean isInStock(String chassis) { return inStock.contains(chassis); }
}

final class StockReport {
    private final StockLookup stock;                                    // depends on the interface, not on getInstance()
    StockReport(StockLookup stock) { this.stock = stock; }
    String line(String chassis) { return chassis + ": " + (stock.isInStock(chassis) ? "in stock" : "sold out"); }
}

Explain Singleton to a new teammate with the stock register: what three things does the class need, why is the constructor private, and what goes wrong when each desk writes new VehicleRegistry()?

Model answer. Singleton guarantees one instance and one global way to reach it. The class needs a private constructor (nobody outside can build another), a private static field holding the single object, and a public static getInstance() that returns it. If every desk writes new VehicleRegistry(), each gets its own copy of the stock: a sale at the sales desk changes only that copy, so Reports still shows the car in stock, and nothing stops more copies. With Singleton all desks share one object, so they always agree.
05

Choose it: when one shared object is right

Level 3 · Choose it
In 30 seconds Use Singleton for something that is truly one per application: a registry, configuration, a cache. Do not use it as a convenient global variable: shared mutable state, hidden dependencies and hard tests are the price. In a Spring backend, let the container make the one instance and inject it.

This visualisation needs JavaScript.

Use it when

  • There must be exactly one of something for the whole application: a vehicle registry, a configuration object, a cache, a connection-pool manager.
  • Everyone must see the same state, and the object is created once and kept for the life of the program.

Do not use it when

  • You only want easy access from everywhere. That is a global variable in disguise: any code can change it, so bugs travel far.
  • The class hides a dependency: getInstance() inside a method means the method's signature does not show it needs a registry, and tests cannot replace it. Simpler alternative: create one object and pass it in (dependency injection), as in the intermediate exercise.
  • The values are stateless and shared: a stateless object is safe to share without any pattern. (The states in State are often exactly this: stateless state objects, kept as shared single instances.)

Trade-offs

  • Complexity: tiny to write; the cost comes later, in concurrency and tests.
  • Coupling: callers depend on the concrete class and on getInstance(), a global name. This is the biggest complaint.
  • Testing: one shared object keeps its state between tests. Fix: depend on an interface and inject it.
  • Concurrency: shared mutable state needs thread safety (section 06; also gathered in lesson 24, coming).
  • Performance: a single object saves memory and set-up time; locking, if you add it, costs a little per call.

In a Spring Boot backend

A conceptual sketch. You rarely write getInstance() in Spring: a bean is a singleton by default (one per ApplicationContext), the container builds it once and injects it. You get the benefit of one shared object without the global name, and tests can inject a fake.

@Component                                   // default scope = singleton: one per ApplicationContext
class VehicleRegistry implements StockLookup {
    private final Set<String> inStock = ConcurrentHashMap.newKeySet();   // shared state must be thread-safe
    public boolean isInStock(String chassis) { return inStock.contains(chassis); }
}

@Service
class StockReportService {
    private final StockLookup stock;
    StockReportService(StockLookup stock) {  // injected: no getInstance(), easy to replace in a test
        this.stock = stock;
    }
}

@Component
@Scope("prototype")                          // the opposite: a NEW object for every injection
class TestDriveSession { }

Where Java and Spring already use it

  • Runtime.getRuntime(): the one Runtime of the running program. A real Singleton: the constructor is private.
  • Desktop.getDesktop() (java.awt): returns the one Desktop of the application (it can throw on a headless machine).
  • Collections.emptyList(): returns a shared immutable empty list. A similar idea (one shared instance), though not a Singleton class.
  • Spring: the default bean scope is singleton; the container, not a static field, guarantees "one".

In this program (it ran on JDK 25), how many lines print true?

import java.util.*;

public class SpotSingleton {
    public static void main(String[] args) {
        Runtime a = Runtime.getRuntime();
        Runtime b = Runtime.getRuntime();
        List<String> x = Collections.emptyList();
        List<String> y = Collections.emptyList();
        System.out.println(a == b);                                         // true
        System.out.println(x == y);                                         // true
        System.out.println(new ArrayList<String>() == new ArrayList<String>());   // false
    }
}

  2. one
  3. two
  4. three
Runtime.getRuntime() returns the one Runtime, so a == b is true. Collections.emptyList() returns the same shared empty list each time (in OpenJDK), so x == y is true: a similar idea. Two new ArrayList are two different objects, so the last line is false. Two lines are true.
06

Master it: threads, reflection and enums

Level 4 · Master it
In 30 seconds The simple lazy version is not safe with several threads. Your options: eager (simplest), lazy with synchronized (safe, slower), double-checked locking with volatile, the holder idiom (lazy and lock-free), or an enum (also safe against reflection and serialization). This is the Level 4 depth; it is also gathered in lesson 24 (coming).

Four thread-safe versions

Why volatile is required in double-checked locking

The line instance = new Dcl() looks like one step but is three: 1 reserve memory, 2 run the constructor to fill the fields, 3 point instance at the object. The compiler or CPU may reorder steps 2 and 3. Another thread doing the first check without a lock could then see instance != null while the constructor has not finished, and use a half-built object.

volatile forbids that reordering and makes the new value visible to all threads straight away (Java 5 and later). Without it the code is wrong, even though it usually seems to work. This is explained, not demonstrated: the race is rare and depends on the CPU and the JIT compiler.

Why two checks? The first (no lock) keeps the common case fast. The second (inside the lock) stops two threads that both passed the first check from building two objects.

The holder idiom and the enum singleton

Holder. The nested class Lazy is not loaded until getInstance() first touches it. The JVM guarantees a class is initialised once, safely, so the instance is created lazily with no lock in your code.

Enum (Effective Java, Item 3). enum EnumRegistry { INSTANCE }: the JVM creates each constant once. Pros: one line, thread-safe, survives serialization and reflection (next card). Cons: it cannot extend another class (it can implement interfaces), it has no lazy-with-arguments option, and it is harder to replace in tests; some teams find it unfamiliar.

How reflection, serialization and cloning break a class-based Singleton

Reflection. setAccessible(true) switches off the private check, so code can call the constructor and make a second object. A guard in the constructor (throw if INSTANCE is set) helps for an eager singleton. An enum constructor cannot be called by reflection at all.

Serialization and cloning. Reading a Serializable object back builds a new object. Fix: add readResolve() returning the instance. Cloning only matters if someone makes the singleton Cloneable: clone() then copies it, so do not implement it (or throw from clone()). An enum handles both for you.

Common mistakes
  • Lazy without synchronisation: two threads can each see null and build two objects.
  • Double-checked locking without volatile: another thread may see a half-built object.
  • Mutable global state: any code can change it, bugs appear far from the cause. Make it thread-safe or immutable.
  • Hidden dependencies: getInstance() deep inside methods; tests cannot swap it. Inject an interface.
  • "One per JVM" is not exact: it is one per class loader. Two class loaders (some application servers) can each hold one.
  • A Singleton that holds per-request data: one shared object must not remember one user's order.
  • Using it when a plain object plus injection is enough.

A new requirement. The showroom's stock report must be unit-tested with a fake registry, and a second showroom application running in the same JVM (another Spring context) needs its own registry. Which design do you choose?

  1. An enum singleton, called as VehicleRegistry.INSTANCE from every service
  2. Double-checked locking with volatile, called as VehicleRegistry.getInstance() inside each service
  3. A static utility class with a static HashMap
  4. A plain class behind a StockLookup interface, created once per application at startup (a Spring singleton-scoped bean) and injected
Options 1 to 3 are all JVM-wide globals: one registry for both showrooms, and a fake cannot be injected. Option 4 still gives "one registry" inside each application (singleton scope is one per ApplicationContext), but each application has its own, and tests pass a fake through the constructor.

Patterns it works with

  • State: stateless state objects can be shared as singletons, since they hold no data.
  • Factory Method: a factory may return the same shared instance each time.
  • Builder: build the object once (configuration, say), then keep it as the one shared instance.
  • Abstract Factory (lesson 08, coming): a concrete factory is often a singleton.
  • Facade (lesson 12, coming): a facade is often the one entry point, kept as one shared object.
  • Flyweight (lesson 23, coming): many shared objects, one per value, instead of one overall.
07

Interview and review

Interview and review

Answer out loud first, then open the card.

01What is the Singleton pattern? (the 30-second answer)
B · Singleton ensures a class has exactly one instance and gives a global access point to it. In Java: a private constructor, a private static field holding the instance, and a public static getInstance(). Example: the dealership's VehicleRegistry, shared by the sales desk, service desk and reports; in the JDK, Runtime.getRuntime().
02Walk me through the thread-safe options.
I · 1) Eager static final field: simplest, thread-safe because class loading is. 2) Lazy with synchronized getInstance(): correct, but every call takes the lock. 3) Double-checked locking with a volatile field: lock only while the field is null. 4) Holder idiom: a private static nested class holds the instance, loaded on first use, lazy and lock-free. 5) Enum: one constant, also safe against reflection and serialization. In practice: eager or holder, or let Spring manage it.
03Why must the field be volatile in double-checked locking?
A · instance = new X() is allocate, run the constructor, assign the reference, and the compiler or CPU may reorder the last two. A thread passing the unlocked first check could then see a non-null reference to an object whose constructor has not finished. volatile forbids that reordering (a happens-before edge between the write and later reads) and makes the value visible to all threads. Without it the code is broken even if it usually works.
04What are the pros and cons of an enum singleton?
I · Pros: shortest code, thread-safe, serialization-safe (the JVM guarantees one constant), reflection cannot create another ("Cannot reflectively create enum objects"). Cons: cannot extend a class (interfaces are fine), eager-ish, no constructor arguments from outside, and awkward to mock; the style can surprise teammates. Joshua Bloch recommends it in Effective Java.
05How can a Singleton be broken, and how do you stop it?
A · Reflection: setAccessible(true) on the private constructor; guard in the constructor, or use an enum. Serialization: deserializing creates a new object; add readResolve() returning the instance, or use an enum. Cloning: only if the class is Cloneable; do not implement it, or throw from clone(). Several class loaders: each can load its own copy. Several threads: an unsafe lazy version.
06Singleton vs a static utility class?
B · A static class has no object: only static methods, no interface, no polymorphism, and its state is hard to replace. A Singleton is a real object, so it can implement an interface, be passed around and (with care) be mocked, and it can be created lazily. Use a static class for pure, stateless helpers (like Math); use a Singleton (or better an injected bean) when there is one shared object with state.
07Singleton vs a Spring singleton-scoped bean?
I · The GoF Singleton is enforced by the class: one per class loader (about one per JVM), reached by a static method. A Spring singleton bean is one instance per ApplicationContext, created and injected by the container; the class itself is an ordinary class that could be instantiated twice. Two contexts mean two beans. Spring's is easier to test and has no global name.
08Why is Singleton called an anti-pattern, and what are the testing problems?
I · It is global mutable state with a hidden dependency: a method calls getInstance() inside, so its signature does not show it, tests cannot replace the object, and state leaks from one test to the next. It also couples callers to a concrete class and complicates concurrency.
09How do you fix the testing problem?
I · Depend on an interface (StockLookup) and pass the object in through the constructor (dependency injection). Production code wires the one real instance once; tests pass a fake. Keep "one" as a decision of the application (one bean), not of the class.
10Eager or lazy: how do you choose?
B · Eager is simplest and thread-safe; choose it when creation is cheap or the object is always needed. Choose lazy (holder idiom) when creation is expensive or may never be needed, or when it depends on something not ready at class load. A failing eager constructor breaks class loading, which gives an ExceptionInInitializerError.

8 takeaways

  • Singleton: exactly one instance, one global way to reach it.
  • Three parts: private constructor, private static field, public static getInstance().
  • Without it, each new VehicleRegistry() is a separate copy, and the copies disagree.
  • Eager initialisation is the simplest and thread-safe; lazy needs care with threads.
  • Double-checked locking needs volatile because construction and publication can be reordered.
  • The holder idiom is lazy and lock-free; the enum is also safe against reflection and serialization.
  • Use it for true one-per-application resources; avoid it as a global variable.
  • In Spring the default scope is singleton (one per ApplicationContext): inject an interface instead of calling getInstance().
