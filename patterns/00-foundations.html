Before the patterns: the ideas they are made of

Every design pattern is built from a handful of ideas: interfaces, composition, programming to an interface, and the five SOLID principles. Learn to read a class diagram, see how Java picks the method that runs, why "has-a" usually beats "is-a", and watch each SOLID principle fix a real dealership problem, before and after. Then meet lambdas and do your first refactor to a pattern. Every program runs.

PATTERNS 00

Foundations: what patterns are built from

Sixteen short sections. Each idea has a lab you step through and a program you can run; the last two are the interview questions and the review.

01

What is a design pattern (and what is it not)?

In 30 seconds A design pattern is a named, proven solution to a design problem that keeps coming back, described as an arrangement of classes and objects. It is not code you copy, not a library and not an algorithm: it is an idea you write yourself, in your own classes, every time.

In 1994 four authors (the "Gang of Four", GoF) collected 23 such solutions in a book. Their names became a shared vocabulary: say "use a Strategy for the discounts" and every developer in the room pictures the same classes.

💡 Remember itA pattern is like a body style in the car world: "SUV" or "hatchback" names a proven shape that every engineer understands, but each manufacturer still builds its own car. A pattern names the shape; you build the classes.

Every pattern in this course is described with the same four parts:

ProblemWhen it applies: the recurring pain, here always a dealership problem.
SolutionThe classes, their roles and how they call each other (the diagram).

Go deeper: patterns, principles and idioms
Principles (SOLID, composition over inheritance) are general rules; patterns are concrete arrangements that follow them; idioms are language-level habits (try-with-resources in Java). Architectural patterns (MVC, microservices) work at a larger scale than the 23 GoF patterns, which work at the level of a few classes.
02

The three families, and the five moves of this course

In 30 seconds The 23 patterns fall into three GoF families: creational (how objects are created), structural (how objects are put together) and behavioral (how objects talk and share work). The families stay the official classification; this course teaches the patterns in five moves, one lesson per pattern.

The five moves, in learning order:

  • Swap (lessons 01–03): replace behaviour without rewriting the client. Strategy, Template Method, State.
  • Create (04–08): control how objects are made. Factory Method, Builder, Singleton, Prototype, Abstract Factory.
  • Wrap (09–13): compatibility, extra responsibilities, controlled access. Adapter, Decorator, Proxy, Facade, Bridge.
  • Talk (14–18): communication, requests, responsibilities. Observer, Command, Chain of Responsibility, Mediator, Memento.
  • Compose (19–23): structures of many objects. Composite, Iterator, Visitor, Interpreter, Flyweight.

Each lesson also shows an interview badge: ★ asked constantly (tier 1, 13 patterns), ◆ follow-ups and comparisons (tier 2, 4), ○ explain with one example (tier 3, 6). The map shows the families and lets you filter by tier:

03

Interface vs abstract class

In 30 seconds An interface is a promise of what a class can do: method signatures, no instance fields, no constructor. An abstract class is a half-built class: it can hold fields, a constructor and finished methods, but leaves some methods for subclasses. Neither can be created with new.

A class implements an interface (any number of them) and extends at most one class. Since Java 8 an interface may also carry default methods with a body, which narrows the gap, but it still has no state of its own.

Go deeper: the diamond problem and default methods
If a class implements two interfaces with the same default method, the compiler refuses it until the class overrides the method (it may call one of them with A.super.honk()). Classes win over interfaces: an inherited class method beats a default method. That is why multiple inheritance of behaviour through interfaces stays safe while multiple inheritance of state is not allowed at all.

Reading a class diagram

In 30 seconds Every pattern comes with a class diagram: boxes are classes, lines are relationships. You need four arrows: implements (dashed, hollow triangle), extends (solid, hollow triangle), has-a (a diamond at the owner) and calls / uses (a plain arrow).

05

Program to an interface, not an implementation

In 30 seconds Declare variables, fields and parameters with the interface type, and name the concrete class in one place only (where the object is created). The code that uses the object then works with any class that keeps the promise, including ones written later.

The checkout needs to take a payment. If its field were a CardGateway, adding UPI would mean editing the checkout. With a PaymentGateway field, the checkout calls pay and the object decides which code runs. That run-time choice is polymorphism. 06

How Java picks the method: overriding and dynamic dispatch

In 30 seconds A variable has a declared type (what you wrote on the left: Discount discount); the object it points to has a runtime type (the class after new). The compiler checks every call against the declared type; at run time the JVM runs the method of the object's class. That run-time choice is dynamic dispatch, the machinery behind polymorphism.

Two words that interviews love to mix up. An override is a method in a subclass (or implementing class) with the same name and parameter types as the parent's; @Override asks the compiler to check that. Which override runs is decided at run time, by the object. An overload is another method with the same name but different parameter types; which overload is called is decided at compile time, from the declared types of the arguments. Go deeper: what is not dispatched dynamically
static, private and final methods and constructors are bound at compile time (static binding): a static method with the same signature in a subclass hides the parent's instead of overriding it. Fields are not polymorphic either: car.name reads the field of the declared type. Inside the JVM, a call on a class type compiles to invokevirtual and on an interface to invokeinterface; HotSpot looks the method up in the class's method table and caches the result, so dispatch is cheap. Visitor (lesson 21) exists because Java dispatches on one object only (single dispatch), not on the argument's runtime type too.
07

Composition over inheritance

In 30 seconds Prefer building a class out of parts it has (composition) over inheriting from a parent it is. Inheritance is fixed at compile time and multiplies classes for every combination; composition lets you mix parts and swap them at run time.

Inheritance ("is-a") is right when the child really is a kind of the parent and keeps all its promises. But using it to combine features (body type and engine type) creates a class for every combination. Composition ("has-a") keeps each feature in its own small class and lets the car delegate the work to its part. Switch between the two views:

This visualisation needs JavaScript.

Strategy, Decorator, Bridge, State and Observer are all composition with a specific purpose. When you meet them, look for the field typed as an interface.

Go deeper: when inheritance is still right
Use inheritance when the subclass is truly substitutable for the parent (section 10), the hierarchy is shallow and stable, and you control both classes. Template Method (lesson 02) is a pattern built on inheritance. Inheriting from a class you do not control is fragile: a change in the parent can silently break the child (the "fragile base class" problem).
08

SOLID · S: Single Responsibility

In 30 seconds SOLID is five design principles named by Robert C. Martin; every pattern follows at least one of them. S: a class should have one reason to change, meaning it answers to one group of people. It does not mean "one method".

An invoice that computes its total, prints itself and saves itself answers to three teams. Each change by one team re-opens code the other two depend on. Split by reason to change, and each team edits only its own class. Compare the two views:

SOLID · O: Open / Closed

In 30 seconds Software should be open for extension, closed for modification: add a new behaviour by adding a class, not by editing code that already works and is tested.

A price calculator with an if / else chain over offer names must be edited for every new offer. Put each offer behind a Discount interface and a new offer becomes a new class; the calculator never changes again. You will recognise this shape in lesson 01: it is the Strategy pattern.

10

SOLID · L: Liskov Substitution

In 30 seconds Wherever code expects a parent type, any subtype must work without surprises: same promises, no new exceptions, no "does nothing" overrides. Named after Barbara Liskov (1987).

"An electric car is a car" is true in English, but if Car promises refuel(), an electric car cannot keep that promise and has to throw. Code written for Car then crashes on an electric one. The fix is a promise every subtype can keep: topUp() ("afterwards the range is full").

This visualisation needs JavaScript.

Before: a subtype that breaks the promise
After: a promise every subtype keeps
Go deeper: the square and the rectangle
The textbook example: Square extends Rectangle looks right, but a caller that sets width 5 and height 4 expects an area of 20, and a square that keeps its sides equal returns 16. Formally, a subtype may not strengthen preconditions, weaken postconditions, or break the parent's invariants. In the JDK, List.of(…) returns a List whose add throws: a deliberate, documented exception to the rule ("optional operations").
11

SOLID · I: Interface Segregation

In 30 seconds No class should be forced to depend on methods it does not use. Prefer several small, role-based interfaces over one fat one.

If one ShowroomStaff interface lists selling, repairing and test-driving, a mechanic must write a sell method that can only throw, and code holding a ShowroomStaff can call it. Split it into Seller, Repairer and Driver: each class takes only the roles it really has, and the wrong call no longer compiles.

12

SOLID · D: Dependency Inversion

In 30 seconds High-level business rules should not depend on low-level details; both should depend on an abstraction (an interface). The detail is then handed in from outside, usually through the constructor.

An order service that writes new SmsSender() is welded to SMS: switching to email means editing the business rule, and a unit test sends real messages. Give it a Notifier through its constructor instead. The arrows now point from both sides towards the interface, which is the "inversion". Passing the detail in is called dependency injection; Spring's container does it for every bean.

This visualisation needs JavaScript.

Before: the rule creates its detail
After: the detail is injected
Go deeper: DIP vs DI vs IoC
Dependency Inversion is the principle: depend on abstractions. Dependency Injection is a technique that follows it: the dependency is passed in (constructor, setter or field) instead of created inside. Inversion of Control is the broader idea that a framework, not your code, decides when things are created and called; Spring's IoC container creates the beans and injects them. Constructor injection is preferred: the dependency can be final, it is never missing, and tests just call the constructor.
13

Lambdas are tiny objects: functional interfaces, anonymous classes, method references

In 30 seconds A functional interface has exactly one abstract method; @FunctionalInterface asks the compiler to check that. You can implement one in four ways: a named class, an anonymous class, a lambda or a method reference. All four give you an object that implements the interface; only the amount of code changes.

Take one dealership rule, PriceRule with long apply(long price). A named class is the version you know. An anonymous class is a class with no name, written and instantiated in one place. A lambda (price -> price * 90 / 100) keeps only the parameter and the body: the compiler already knows the one method it must be. A method reference (Lambdas::festival) points at a method that already does the job. Step through the four versions: the diagram never changes.

💡 Remember itThe customer needs something that drives. You can buy a named model off the shelf (named class), have a one-off built on the spot (anonymous class), hand over just a key and a route (lambda), or point to a car already in the showroom (method reference). It still drives the same.

Why this matters for patterns: when the role is a single method, the pattern's classes shrink to lambdas. A Strategy is often just a PriceRule lambda, a Command is a Runnable, an Observer is a Consumer listener. The pattern is still there; the boilerplate is gone.

Go deeper: anonymous class vs lambda
Inside an anonymous class, this is the anonymous object; inside a lambda, this is the enclosing object (the program prints both). An anonymous class can have fields, several methods and implement an interface with many abstract methods or extend a class; a lambda can only implement a functional interface. Both can read local variables only if they are effectively final (never reassigned). The compiler writes a separate Outer$1.class file for each anonymous class; a lambda compiles to an invokedynamic call and its class is generated at run time. Use a lambda when the behaviour is short; use a named class when it has state, a name worth reading, or more than one method.

Your first refactor: when a pattern starts to pay off

In 30 seconds Patterns are not added on day one. You write the simple version, feel the pain when the same if / else grows again, and then refactor. Coupling is how much one class knows about another: tight = it names or creates concrete classes inside; loose = it knows only an interface and is handed the object from outside.

Exercise. This checkout already takes card, UPI and cash, and the business wants EMI next month and a wallet after that. Run it, then before you open the hint write down: what must you edit for each new payment type, and what could break while you do?

💡 Remember itA tightly coupled showroom has the cashier hard-wired to one card machine: a new payment method means rewiring the counter. A loosely coupled one has a standard socket: any machine that fits the socket plugs in, and the counter is never opened.
Before: one method, every payment type
Hint: find the smell
Look for an if / else (or switch) on a type code that keeps growing. Every new payment type opens Checkout.pay, so tested branches are edited again (it breaks Open / Closed, section 9). Card fees, UPI rules and cash receipts all live in one method (several reasons to change, S, section 8). A typo in the string "wallet" is only found at run time. And you cannot test the checkout with a fake payment: it is tightly coupled to every concrete way of paying.
Solution: one interface, one class per type
Give the varying part a name: an interface Payment with String pay(long amount). Move each branch into its own class (CardPayment, UpiPayment, CashPayment). Give Checkout a Payment field set through its constructor, and let it call payment.pay(amount) without knowing which one it has. main chooses the class (section 12: inject the detail). A new type is a new class, or just a lambda, since Payment has one method (section 13). Compare the two views of the lab, then run the after program.

This visualisation needs JavaScript.

After: the checkout depends on an interface

You just discovered the Strategy pattern: a family of interchangeable behaviours behind one interface, chosen from outside. Lesson 01 (Strategy) starts exactly here.

Go deeper: when not to refactor yet
Two branches that never change do not need a pattern; the if / else is easier to read. A common rule of thumb is "rule of three": refactor when the third variation arrives, or as soon as you need to test the client with a fake. Refactor in small, safe steps: extract the interface, move one branch at a time, run the program after each step, and only then delete the old method.

13 interview questions

Answer out loud first, then open the card.

01What is a design pattern? Why use one?
A named, reusable solution to a design problem that keeps recurring, described as roles for classes and objects rather than finished code. It gives a team a shared vocabulary ("use a Strategy"), reuses designs that are known to work, and makes code easier to change in the direction the pattern plans for. The cost is extra classes and indirection, so use one only when the problem is really there.
02What are the three categories of GoF patterns? Give two of each.
Creational (how objects are created): Singleton, Factory Method, Builder, Abstract Factory, Prototype. Structural (how objects are composed): Adapter, Decorator, Proxy, Facade, Composite, Bridge, Flyweight. Behavioral (how objects interact and share responsibility): Strategy, Observer, Command, State, Template Method, Chain of Responsibility, Iterator, Mediator, Memento, Visitor, Interpreter.
03Interface vs abstract class: when do you choose which?
An interface defines a capability that unrelated classes can share; a class can implement many; it has no instance state (only constants) and no constructor, though since Java 8 it can have default and static methods. An abstract class is a partial base for closely related classes that share state and code; a class can extend only one. Choose an interface for the type you program against, and add an abstract class underneath when several implementations share real code.
04What does "program to an interface, not an implementation" mean?
Declare fields, parameters and return types with the interface (List, PaymentGateway) and name the concrete class only where the object is created. The using code then works with any implementation, including future ones and test fakes, and the choice can change in one place.
05Composition vs inheritance: why "favour composition"?
Inheritance is fixed at compile time, exposes the parent's internals to the child (fragile base class), and multiplies classes when features combine (bodies × engines). Composition keeps each feature in its own class behind an interface, lets the owner delegate to it, and lets you swap parts at run time. Use inheritance only for a true, substitutable is-a relationship.
06What is SOLID? One line for each letter.
Single responsibility: one reason to change. Open/closed: extend by adding code, not by editing it. Liskov substitution: subtypes must be usable wherever the parent is. Interface segregation: no client depends on methods it does not use. Dependency inversion: high and low level both depend on abstractions.
07Does Single Responsibility mean a class should have one method?
No. It means one reason to change: the class answers to one actor or one concern. An Invoice record with several methods about the invoice's own rules is fine; printing and storage are different concerns and belong elsewhere.
08Give an example of a Liskov violation, and how you would spot one.
ElectricCar extends Car where refuel() throws UnsupportedOperationException, or the classic Square extends Rectangle that breaks setWidth. Signs: overrides that throw or do nothing, callers that check instanceof before calling, and subclasses that need stricter inputs than the parent. Fix it by changing the abstraction so every subtype can keep its promise.
09Dependency Inversion vs Dependency Injection vs IoC?
DIP is the principle (depend on abstractions, not concretions). DI is a technique that applies it (pass the dependency in through the constructor, a setter or a field). IoC is the general idea that a framework controls object creation and the flow of calls; Spring's IoC container creates beans and performs the injection.
10Can you overuse design patterns?
Yes. A pattern adds interfaces, classes and indirection; applied to a problem you do not have, it makes simple code harder to read (often called "patternitis"). Start simple, and introduce a pattern when the second or third variation actually appears, or when a SOLID principle is clearly being broken. Interviewers like to hear you say when not to use one.
11Overloading vs overriding: which is decided when?
An override has the same name and parameter types as a parent or interface method; the JVM picks it at run time from the object's class (dynamic dispatch). An overload has the same name but different parameter types; the compiler picks it at compile time from the declared types of the arguments. So with Car car = new ElectricCar(), car.describe() runs ElectricCar's override, but welcome(car) calls the welcome(Car) overload. Static, private and final methods are never overridden.
12What is a functional interface?
An interface with exactly one abstract method (default and static methods don't count, nor do public Object methods such as equals). A lambda or method reference can implement it, because the compiler knows which method the code is for. @FunctionalInterface is optional but makes the compiler reject a second abstract method. JDK examples: Runnable, Comparator, Function, Supplier, Consumer, Predicate.
13Anonymous class vs lambda: what is the difference?
Both create an object that implements an interface in place. In an anonymous class this is the anonymous object itself; in a lambda this is the enclosing object. An anonymous class can hold fields, have several methods, extend a class or implement a multi-method interface; a lambda only implements a functional interface and has no state of its own. Each anonymous class is a separate .class file; lambdas are linked at run time through invokedynamic. Both may capture only effectively final local variables.

Review

9 takeaways

  • A design pattern is a named solution to a recurring design problem: an arrangement of classes you write yourself, not a library.
  • Three GoF families: creational (creating), structural (composing), behavioral (interacting). This course teaches them in five moves: Swap, Create, Wrap, Talk, Compose; ★ ◆ ○ mark how often interviews ask.
  • Interface = a promise (many per class, no state); abstract class = a half-built base (one per class, state and code).
  • Four arrows read every diagram: implements, extends, has-a (diamond at the owner), calls.
  • Program to an interface and prefer composition: the field typed as an interface is the heart of most patterns.
  • Overrides are chosen at run time by the object (dynamic dispatch); overloads at compile time by the declared types.
  • SOLID: one reason to change · extend, don't modify · subtypes keep promises · small interfaces · depend on abstractions.
  • A functional interface has one abstract method; a named class, an anonymous class, a lambda and a method reference all implement it.
  • Refactor to a pattern when the pain is real: a growing if / else on a type code becomes an interface plus one class per type (Strategy).
