PATTERNS 05 · MOVE 2 · CREATE

Builder: assemble a complex object step by step

In Factory Method the question was which class to create. Builder asks a different one: how do we assemble one object that has many options? A dealership Car has two required values and a long list of optional extras. You will see why long constructors and setters hurt, refactor to a Builder in small steps, watch it run, and choose it like a senior engineer.

PATTERNS 05

Builder: fill in an order form, then build() a finished, valid object

Seven sections, four levels: a beginner can stop after section 04; sections 05 to 07 add the interview depth.

01

See it: the problem Builder solves

Level 1 · See it
In 30 seconds When an object has many options, do not make the caller pass them all to one constructor, or build it half-empty and fill it with setters. Collect the options in a separate builder object, check them once, then create the finished object in one go. The result is readable code and a car that is always complete, valid and unchangeable.

The dealership problem. A Car must have a model and a fuel. Everything else is optional: colour, sunroof, alloy wheels, GPS, extended warranty, seat covers, and more arrive every quarter. Each new option tempts someone to add yet another constructor or another setter.

Words used here. A constructor is the method that builds an object (new Car(...)). A parameter is one value you pass to it. A setter is a method like setColour that changes one field after the object exists. Immutable means the object cannot change after it is made. A client is the code that uses a class.

💡 Remember itOrdering a car at the dealership. You fill in an order form step by step: model and fuel first, then the extras you want. Nobody hands you a half-built car. When you press Confirm, the dealer checks the form (is a sunroof allowed on this trim?) and hands over the finished car. Picture parts snapping onto a frame until the frame is complete.

02

Build it: from telescoping constructors to a Builder

Level 2 · Build it
In 30 seconds Four steps. 1) A nested Car.Builder holds the options; required ones go in its constructor. 2) Fluent methods set an option and return this. 3) Car gets one private constructor and final fields. 4) build() validates and returns the car. Run the program after each step.
Before: telescoping constructors, then JavaBeans setters

What breaks. The first two cars differ only in which boolean is true; both compile and neither line tells you what it means. The setter version reads better, but the third car has no fuel (it prints null), accepts a warranty of -4 years, and anyone holding it can change it later. Every new option means another constructor or another setter, and no single place checks the rules.

The refactor. Use the lab to see each step and why it is made.

After: Effective Java Builder, an immutable Car

The chain reads like the order form, defaults cover the options you skip, and the last two cases show the rules in build() rejecting a bad order with an exact message. Car has no setters and no public constructor, so a car that is half-built or changed later cannot exist. It is also safe to share between threads, because nothing in it ever changes.

Go deeper: why are the required values in the Builder's constructor?
Because a builder without a model is meaningless, and the compiler can enforce that: new Car.Builder() does not compile. Optional values use fluent methods and defaults. If a value is "required but easy to forget" and cannot go in the constructor (many required fields), use a step builder (section 06), or check it in build() and throw.

04

Practise: add an option, add a rule

Level 2 · Practise

The dealership now sells seat covers as an optional extra, off by default. Add it to a (smaller) Car and its builder. Rule: do not add any constructor to Car other than the private one. Expected lines: Tiago Petrol | seat covers=false and Tiago Petrol | seat covers=true.

Hint
Three small edits: a private final boolean seatCovers in Car, a private boolean seatCovers (default false) in the builder, and a fluent method seatCovers(boolean on) that returns this. Copy the field in the private constructor.
Solution

No existing caller is edited. Ran on JDK 25:

public class ExSeatCovers {
    public static void main(String[] args) {
        Car plain = new Car.Builder("Tiago", "Petrol").build();
        Car covered = new Car.Builder("Tiago", "Petrol").seatCovers(true).build();   // the new option
        System.out.println(plain.describe());     // Tiago Petrol | seat covers=false
        System.out.println(covered.describe());   // Tiago Petrol | seat covers=true
    }
}

final class Car {
    private final String model, fuel;
    private final boolean seatCovers;                         // NEW field

    private Car(Builder b) { model = b.model; fuel = b.fuel; seatCovers = b.seatCovers; }

    String describe() { return model + " " + fuel + " | seat covers=" + seatCovers; }

    static class Builder {
        private final String model, fuel;
        private boolean seatCovers;                           // NEW: optional, default false

        Builder(String model, String fuel) { this.model = model; this.fuel = fuel; }

        Builder seatCovers(boolean on) { this.seatCovers = on; return this; }   // NEW fluent setter

        Car build() { return new Car(this); }
    }
}

Add a rule to build(): a warranty of more than 3 years needs the Top trim. A violating order must throw IllegalStateException with the message Warranty over 3 years needs the Top trim.

Hint
Rules belong in build(), not in the setters: while the options are still being collected the trim may not be set yet, so a check in warrantyYears(...) would depend on the order of the calls.
Solution

One if in build(). Ran on JDK 25:

public class ExRule {
    public static void main(String[] args) {
        Car ok = new Car.Builder("Nexon", "EV").trim("Top").warrantyYears(5).build();
        System.out.println(ok.describe());   // Nexon EV Top warranty=5y
        try {
            new Car.Builder("Nexon", "EV").warrantyYears(5).build();               // Base trim, 5 years
        } catch (IllegalStateException e) {
            System.out.println(e.getMessage());   // Warranty over 3 years needs the Top trim
        }
    }
}

final class Car {
    private final String model, fuel, trim;
    private final int warrantyYears;

    private Car(Builder b) { model = b.model; fuel = b.fuel; trim = b.trim; warrantyYears = b.warrantyYears; }

    String describe() { return model + " " + fuel + " " + trim + " warranty=" + warrantyYears + "y"; }

    static class Builder {
        private final String model, fuel;
        private String trim = "Base";
        private int warrantyYears;

        Builder(String model, String fuel) { this.model = model; this.fuel = fuel; }
        Builder trim(String trim) { this.trim = trim; return this; }
        Builder warrantyYears(int years) { this.warrantyYears = years; return this; }

        Car build() {
            if (warrantyYears > 3 && trim.equals("Base"))                     // the new rule lives in build()
                throw new IllegalStateException("Warranty over 3 years needs the Top trim");
            return new Car(this);
        }
    }
}

Explain Builder to a new teammate using the order form: why is the telescoping constructor a problem, why are setters not a good fix, where do the required values go, and where do the rules go?

Model answer. A constructor with many parameters is unreadable (which boolean is which?) and every new option needs another constructor. Setters fix readability but make the object mutable and possibly half-built, with no place to check the rules. A Builder collects the options in a separate object: required values go in the builder's constructor, options are fluent methods that return this, and build() checks every rule once and returns an immutable Car through a private constructor. A bad order throws in build(), so an invalid car can never exist.
05

Choose it: roles, look-alikes and trade-offs

Level 3 · Choose it
In 30 seconds Use Builder when an object has many parameters, several of them optional, or when it must be valid and immutable once created. Do not use it for an object with two or three fields: a constructor or a record is simpler.

This visualisation needs JavaScript.

Two forms of one idea. The classic GoF Builder has a Director, a Builder interface and several ConcreteBuilders that produce different representations from the same steps (a car and a price sheet). It is the third tab above and runs below. The fluent builder (Effective Java) is what you will write and meet nearly every day: one nested class, no Director, the caller is the recipe.

Use it when

  • A class has many parameters, especially optional ones, or several of the same type (boolean, String) that are easy to swap.
  • The object must be immutable and always valid, with all rules checked in one place.
  • The same steps must produce different representations (GoF form).

Do not use it when

  • The object has two or three fields: use a constructor, or a record (section 06).
  • The only question is which class to create: that is Factory Method.
  • You need a copy of an existing object: copy it (Prototype, coming) or use toBuilder().

Trade-offs

  • Complexity: a second class (about twice the code for the fields) and boilerplate, which Lombok or an IDE can generate. Worth it from about four or five parameters.
  • Extensibility: a new option is one field and one method; no existing caller is edited.
  • Coupling: callers depend on the builder's method names; the product's constructor stays private.
  • Testing: easy: build a valid car in one line, then change one option to test one rule. Rules live in one place.
  • Performance: one extra short-lived object per build; ignore it unless you build millions in a hot loop.
  • Runtime errors: a missing required option found in build() is a runtime error, not a compile error (unless you use a step builder).

In a Spring Boot backend

A conceptual sketch. A controller builds a validated domain object from a request, and Spring's own builders assemble the response. A rule that fails in build() becomes an HTTP 422 through an @ExceptionHandler.

@RestController
@RequestMapping("/orders")
class OrderController {

    @PostMapping
    ResponseEntity<OrderView> create(@RequestBody OrderRequest req) {
        Car car = new Car.Builder(req.model(), req.fuel())      // required
                .trim(req.trim())
                .sunroof(req.sunroof())
                .warrantyYears(req.warrantyYears())
                .build();                                        // rules checked here
        URI location = UriComponentsBuilder.fromPath("/orders/{id}")
                .buildAndExpand(42).toUri();
        return ResponseEntity.created(location)
                .header("X-Dealer", "Trinity")
                .body(new OrderView(car.describe()));
    }

    @ExceptionHandler(IllegalStateException.class)
    ResponseEntity<String> invalid(IllegalStateException e) {
        return ResponseEntity.unprocessableEntity().body(e.getMessage());
    }
}

Where Java and Spring already use it

  • StringBuilder: collects parts with append, then toString() gives the finished String (conceptually a Builder; the builder itself is mutable).
  • HttpRequest.newBuilder() (java.net.http), Stream.builder(), Locale.Builder and ProcessBuilder: fluent builders in the JDK. (ProcessBuilder configures and then start()s a process; conceptually similar.)
  • Spring: ResponseEntity.ok().header(...).body(...), UriComponentsBuilder, and RestClient.builder() (Spring Framework 6.1+).
  • Library: Lombok's @Builder generates a builder class from annotations (section 06; not used in this course's programs).

In this code (it ran on JDK 25), which line plays the Builder's finishing step, the one that produces the final object?

public class SpotBuilder {
    public static void main(String[] args) {
        StringBuilder sb = new StringBuilder();
        sb.append("Nexon").append(" ").append("EV");      // collect the parts
        String s = sb.toString();                          // produce the finished object
        System.out.println(s + " " + s.length());
    }
}
// Nexon EV 8
  1. new StringBuilder()
  2. sb.append("Nexon").append(" ").append("EV")
  3. sb.toString()
  4. System.out.println(...)
new StringBuilder() starts the form and append adds parts (each returns the same builder, so the calls chain). toString() is the build() step: it returns the finished, unchangeable String. println just uses the result.
06

Master it: Builder in modern Java

Level 4 · Master it
In 30 seconds A record gives you an immutable class with validation in its compact constructor. Add toBuilder() (or a with… method) to copy an object with one change. For a few required fields use a step builder; for lots of boilerplate, Lombok @Builder generates the builder for you.
Create with…when
a plain constructortwo or three fields, all required
a record with a compact constructora small immutable value; validate in the constructor; no optional fields
a fluent Builder (nested class)many parameters, some optional; rules checked in build()
a step builderseveral required fields that must be given in order, enforced by the compiler
Lombok @Builderyou want the fluent builder without writing it (a third-party library, so it adds a dependency)
Step builder: required fields checked by the compiler

Each required step returns an interface that offers only the next step, so Order.start().fuel("EV") does not even compile. It costs more code; use it when forgetting a required value would be costly.

Lombok @Builder (not used here)

Lombok is a library that generates code at compile time. Annotating a class gives you a builder with the same shape as ours; it does not add your validation, so put rules in a custom build() or in the constructor. Conceptual sketch, not run here:

@Builder(toBuilder = true)
public class Car {
    private final String model;
    private final String fuel;
    @Builder.Default private final String colour = "White";
}

Car car = Car.builder().model("Nexon").fuel("EV").build();
Advanced details: thread safety and copying
The finished Car is immutable, so it can be shared between threads without locks. The builder is not: it is mutable, so use one builder per order and never share it. If a builder holds a list, copy it in build() (List.copyOf) or the product still shares the builder's list. If many steps are optional, build() should apply defaults, not null checks scattered in the product.
Common mistakes
  • Validating in the setters: the answer then depends on the order of calls. Check in build().
  • A public constructor next to the builder: callers bypass the rules.
  • A mutable product: adding setters to Car defeats the point.
  • Reusing one builder across threads or orders and leaking old options into the next car.
  • A Builder for a three-field class: over-engineering; use a record.
  • Calling Factory Method "Builder": one picks the class, the other assembles one object.

A new requirement. The online configurator lets a customer change only the colour of an existing order, and three teams share the same Car objects. Which design do you choose?

  1. Add setColour to Car so the configurator edits it in place
  2. Add yet another public Car constructor that takes the old car plus a colour
  3. Make the Car fields non-final and synchronise every method
  4. Keep Car immutable and add toBuilder(): car.toBuilder().colour("Blue").build() makes a new, validated car
The copy goes through build(), so every rule is checked again, and the original is untouched for the other teams. Options 1 and 3 make a shared object mutable (surprises, locking). Option 2 starts the telescoping problem again.

Patterns it works with

  • Factory Method: decides which class; a Builder can be the factory method's product-assembly step.
  • Abstract Factory (lesson 08, coming): creates whole families; its factories may use builders inside.
  • Composite (coming): a Builder is a natural way to assemble a tree of parts.
  • Prototype (coming) and toBuilder(): two ways to make "the same object with a change".
  • Template Method: a Director is a fixed recipe, close to a template of steps.

Interview and review

Interview and review

Answer out loud first, then open the card.

01What is the Builder pattern? (the 30-second answer)
B · Builder separates the construction of a complex object from its representation: you collect the options step by step in a builder, then build() returns the finished object. In Java it is usually a static nested class with fluent setters that return this, required values in its constructor, and a build() that validates and creates an immutable product. Example: new Car.Builder("Nexon","EV").colour("Red").sunroof(true).build(); in the JDK, HttpRequest.newBuilder() and StringBuilder.
02Walk me through it in more depth.
I · Car has final fields and a private constructor taking the builder, so the builder is the only way in. Car.Builder has the required values (final, set in its constructor), optional ones with defaults, one fluent method per option, and build() which checks every cross-field rule (sunroof not on Base trim, warranty 0 to 5) and then calls new Car(this). Benefits: readable named options, no invalid objects, immutability and thread safety of the product, one place for rules, and new options without touching callers. Costs: extra boilerplate, a runtime (not compile-time) check for missing required values, one extra object per build.
03Why a Builder instead of constructors or setters?
B · Long constructors are positional and unreadable (true, false, true) and need a new overload for each option (the telescoping constructor problem). JavaBeans setters are readable but leave the object mutable and possibly half-built, with no moment where the whole object is validated, and they are not safe to share between threads. A Builder keeps the named options of setters and the all-at-once, immutable result of a constructor.
04How does it give you immutability and thread safety?
I · The product has only final fields, set in a private constructor, no setters, and defensive copies of any mutable parts. Once build() returns, nothing can change it, and final fields are safely published, so threads can share it without locks. The builder is mutable and is not thread-safe: use one per order.
05Where should validation go: the setters, the constructor or build()?
I · In build() for rules across several fields (sunroof needs a non-Base trim): all values are known by then, and the order of the calls does not matter. Simple single-field checks may also go in the setter to fail early. Some teams also check in the product's constructor so that no path can skip the rule. Never rely on callers to check.
06Builder vs Factory Method (and Abstract Factory)?
I · Factory Method decides which class to create, through an overridable method; one call, one product. Builder decides how one complex object is assembled, in steps, and the class is usually fixed. Abstract Factory creates a family of matching products. They combine: a factory method can return the result of a build().
07What is the classic GoF Builder and the Director?
A · GoF has a Builder interface with step methods, ConcreteBuilders that implement them and keep the product being built, and a Director that calls the steps in a fixed order. The same Director can drive different builders to produce different representations (a CarBuilder and a PriceSheetBuilder). The fluent Builder in Effective Java drops the Director and the interface: the caller is the recipe. Use the GoF form only when you really need several representations.
08How does Lombok's @Builder relate to this?
B · It is a library that generates the same fluent builder class at compile time from annotations, so you do not write the boilerplate. It does not add your cross-field rules by itself (write them in a custom build or the constructor), and it adds a dependency. Know how to write the builder by hand: interviewers ask.
09How do you handle required fields, and what is a step builder?
A · Put required values in the builder's constructor, or check them in build(). A step builder returns a different interface after each required step, so the compiler rejects an incomplete chain: safer, but more code. Records do not have optional fields, so combine a record with a builder if you need both immutability and options.
10How would you copy an object with one field changed?
I · Add toBuilder() (copy-with): it creates a builder pre-filled from the product; change one option and call build() again, so the rules are re-checked. For a record, a withColour(...) method that calls the canonical constructor does the same.
IntentCollect the options of a complex object step by step, then build a finished, valid, usually immutable result.
StructureProduct (private constructor, final fields) ← Builder (required in constructor, fluent options, build() validates). GoF adds a Director and ConcreteBuilders.
Use whenMany parameters, several optional, rules across fields, and the object must be immutable.
Trade-offBoilerplate and a runtime check for required values. Skip it for two or three fields: use a record.

8 takeaways

  • Builder: collect the options in a builder, then build() the finished object.
  • The smells: telescoping constructors (positional, unreadable) and JavaBeans setters (mutable, half-built).
  • Effective Java form: nested Car.Builder, required values in its constructor, fluent methods that return this.
  • Rules that span several fields are checked once, in build().
  • Car has final fields and a private constructor, so it is immutable and thread-safe; the builder is not thread-safe.
  • Factory Method decides WHICH class; Builder decides HOW one object is assembled.
  • GoF Builder = Director + Builder interface + ConcreteBuilders; the fluent builder is the common modern form.
  • Modern Java: records with compact constructors, toBuilder(), step builders, Lombok @Builder; no Builder for tiny classes.
