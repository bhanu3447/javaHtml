Template Method: one checklist, blanks to fill in

Every new car gets the same inspection in the same order; only a few checks depend on the model. Template Method writes that order once, in a base class, and lets each subclass fill in just the blanks. Same goal as Strategy, different tool: inheritance instead of composition.

PATTERNS 02

Template Method: fix the steps, vary the details

Seven sections: see the problem, build the pattern, watch it run, practise, choose it, master it, then interview and review.

01

See it: one inspection, three copies

Level 1 · See it
In 30 seconds Template Method writes the steps of a job once, in a fixed order, in a base class, and leaves a few steps blank for subclasses to fill in. The base class decides when each step runs; a subclass decides only what its own steps do.

In lesson 01 (Strategy) you varied part of a behaviour by handing an object in from outside (composition). Template Method has the same goal, but uses inheritance: the varying part is a method a subclass (a class that extends another) overrides.

The dealership problem. Before a car is delivered, the workshop runs a pre-delivery inspection (PDI): book a bay, common checks, model-specific checks, an optional road test, sign-off. Petrol, diesel and EV cars each got their own class, written by copying the last one. Step through the Pain lab to watch the copies drift.

💡 Remember itA printed checklist form. Head office prints the steps and their order; the mechanic only writes in the blank fields ("model checks: ____"). A field marked "optional" can be left as printed. Nobody at a branch can reorder the printed steps.

02

Build it: from copies to one template

Level 2 · Build it
Before: three classes, three copies of the order

What breaks. The order of the steps lives in three places, so every checklist change must be made three times, and the output shows two silent mistakes: the diesel copy never got brake fluid, and the EV copy signs off before the road test. A fourth fuel type means a fourth copy. The only real differences are one line per class.

This visualisation needs JavaScript.

After: the order lives in one final method

Four words carry the pattern: the template method (inspect, final), the primitive operation (modelChecks, abstract: must be filled), the hook (needsRoadTest and roadTest: have a default, may be overridden) and the fixed steps (private: cannot be changed).

03

Watch it run: the parent calls the child

Level 2 · Watch it run

One call, new EvInspection().inspect("Nexon EV"), prints six lines. The lab follows every call. Notice the direction of the arrows into the right-hand lane: the base class calls the subclass, never the reverse.

This visualisation needs JavaScript.

This reversed control is called the Hollywood principle: "don't call us, we'll call you". A subclass writes small methods and waits to be called; the template decides when. Frameworks work the same way: you write doGet, the servlet container calls it.

Now drive it yourself. Pick a car type, choose whether to override the road-test hook, and press Run inspection. Green steps come from the subclass, the rest from the base class; the output is exactly what the Java program prints.

04

Practise

Level 2 · Practise

CNG cars arrive next month. Their model checks are tank valve, leak test, cylinder certificate. Add support for them to InspectionAfter.java and inspect an "Ertiga CNG". Which existing classes do you need to open?

Hint
Only one step differs for CNG. Which method is abstract in PreDeliveryInspection? You need one new class with one method, and one line in main. No existing class is opened.
Solution
class CngInspection extends PreDeliveryInspection {
    @Override protected void modelChecks() { System.out.println("cng   : tank valve, leak test, cylinder certificate"); }
}

new CngInspection().inspect("Ertiga CNG");
// == PDI Ertiga CNG ==
// base  : bay booked
// base  : tyres, lights, wipers, brake fluid
// cng   : tank valve, leak test, cylinder certificate
// base  : road test 5 km
// base  : signed off
It keeps the default road-test hook. The order, the common checks and the sign-off come from the base class for free.

The service workshop has the same disease. Refactor ServiceBefore into an abstract ServiceJob with a final long run(String model) template that returns the bill in rupees (labour Rs 1500 for every car). Petrol cars need an oil change (Rs 2500); EVs do not. The output must stay the same apart from the prefixes.

Hint
Three kinds of step: fixed (receive the car, wash, invoice), must-fill (the model work and its price: an abstract method returning long), and optional (the oil change: a hook needsOilChange() with the default true, which the EV overrides). Add the prices up inside the template.
Solution
public class ServiceJobs {
    public static void main(String[] args) {
        System.out.println("total Rs " + new PetrolService().run("Swift"));
        System.out.println("total Rs " + new EvService().run("Nexon EV"));
        // == service Swift ==
        // base  : car received, job card opened
        // petrol: spark plugs
        // base  : oil change
        // base  : washed, invoice printed
        // total Rs 4800
        // == service Nexon EV ==
        // base  : car received, job card opened
        // ev    : battery coolant check
        // base  : washed, invoice printed
        // total Rs 2700
    }
}

abstract class ServiceJob {
    public final long run(String model) {             // the template method
        System.out.println("== service " + model + " ==");
        System.out.println("base  : car received, job card opened");
        long bill = 1500;                              // labour, every car
        bill += modelWork();                           // primitive operation
        if (needsOilChange()) {                        // hook with a default
            System.out.println("base  : oil change");
            bill += 2500;
        }
        System.out.println("base  : washed, invoice printed");
        return bill;
    }
    protected abstract long modelWork();
    protected boolean needsOilChange() { return true; }
}

class PetrolService extends ServiceJob {
    @Override protected long modelWork() { System.out.println("petrol: spark plugs"); return 800; }
}

class EvService extends ServiceJob {
    @Override protected long modelWork() { System.out.println("ev    : battery coolant check"); return 1200; }
    @Override protected boolean needsOilChange() { return false; }      // no engine oil in an EV
}
Run on JDK 25. The EV class is two one-line methods; a new car type cannot forget the wash or the invoice.

Explain Template Method to a new colleague in four or five sentences, using the inspection checklist. Say which method is final, which must be filled in, which may be, and who calls whom.

The pre-delivery inspection always runs the same steps in the same order, so the order is written once in an abstract base class, in a final method inspect(): the template method. Fixed steps like booking a bay and signing off are private methods there. The step that differs per car type, modelChecks(), is abstract, so every subclass must fill it in. Optional steps are hooks: needsRoadTest() and roadTest() have defaults that a subclass may override. The client calls only inspect(), and the base class calls the subclass's methods at the right moment, never the other way round.
05

Choose it: when, when not, and its look-alikes

Level 3 · Choose it

This visualisation needs JavaScript.

Use it when

  • Several classes run the same steps in the same order and differ in one or two of them.
  • The order is a rule you must protect (sign-off last, audit first): final enforces it.
  • The variants are known when you write the code and are stable: a few subclasses, not dozens.

Do not use it when

  • The varying step must be chosen or changed at run time: use Strategy (a field or a lambda).
  • Variations combine (fuel × market × branch): subclasses multiply. Compose objects instead.
  • Only one variant exists, or two that never change: a plain method with an if is clearer.

RelationA factory method is often one step of a template method: the base runs prepare → createReport() → sign and subclasses override only createReport() (lesson 04).

Trade-offs. Duplication goes away and the order is enforced, but subclasses are tightly coupled to the base class: they depend on which methods it calls and when (the fragile base class problem). Testing a step means creating a subclass. One class can extend only one base, so you cannot mix two templates. Performance cost: none worth measuring.

In a backend. The same template, as Spring beans: each fuel type is a @Component, and a service picks the right one per car. A conceptual sketch:

// conceptual sketch: Vehicle, FuelType and InspectionReport are your own classes
public abstract class PreDeliveryInspection {
    public final InspectionReport inspect(Vehicle car) {      // template method
        InspectionReport report = new InspectionReport(car);
        commonChecks(car, report);
        modelChecks(car, report);                               // primitive operation
        if (needsRoadTest(car)) roadTest(car, report);          // hook
        return report.signOff();
    }
    protected abstract void modelChecks(Vehicle car, InspectionReport report);
    protected boolean needsRoadTest(Vehicle car) { return car.odometerKm() < 50; }
    public abstract FuelType fuelType();
    // commonChecks, roadTest: private / protected steps as in the Java program
}

@Component
class EvInspection extends PreDeliveryInspection { /* modelChecks, fuelType */ }

@Service
class DeliveryService {
    private final Map<FuelType, PreDeliveryInspection> byFuel;
    DeliveryService(List<PreDeliveryInspection> all) {        // Spring injects every subclass bean
        byFuel = all.stream().collect(Collectors.toMap(PreDeliveryInspection::fuelType, i -> i));
    }
    public InspectionReport prepare(Vehicle car) { return byFuel.get(car.fuelType()).inspect(car); }
}

In the JDK and Spring

  • java.io.InputStream: read(byte[], int, int) is written once on top of the abstract read() (one byte). A subclass implements read() and gets the array version, readAllBytes() and more.
  • java.util.AbstractList: implement get(int) and size(); iterator(), indexOf, contains, equals and hashCode are built on them.
  • jakarta.servlet.http.HttpServlet: service() reads the HTTP method and calls doGet, doPost… which you override (the defaults answer "method not allowed").
  • Spring OncePerRequestFilter: doFilter is final and calls your doFilterInternal. AbstractController.handleRequest calls your handleRequestInternal. AbstractApplicationContext.refresh() has empty hooks such as onRefresh().
  • Spring JdbcTemplate is the callback variant, not classic subclassing: it runs the fixed steps (get a connection, run the SQL, loop over rows, close, translate errors) and you pass the varying step in as a RowMapper lambda. Conceptually a template method whose blank is filled by an object, which is Strategy.
List<Car> evs = jdbcTemplate.query(
    "select model, price from car where fuel = ?",
    (rs, rowNum) -> new Car(rs.getString("model"), rs.getLong("price")),   // the one step you supply
    "EV");

Simplified from java.io.InputStream (argument checks and error handling left out). Which role does each method play?

public abstract class InputStream {
    public abstract int read() throws IOException;      // one byte, or -1 at the end
    public int read(byte[] b, int off, int len) throws IOException {
        int c = read();
        if (c == -1) return -1;
        b[off] = (byte) c;
        int i = 1;
        for (; i < len; i++) {
            c = read();
            if (c == -1) break;
            b[off + i] = (byte) c;
        }
        return i;
    }
}
  1. read() is the template method; read(byte[], int, int) is the primitive operation
  2. read(byte[], int, int) is the template method; read() is the primitive operation every subclass must implement
  3. Both are hooks: each has a default body
  4. Neither: this is Strategy, because a stream is passed around
The array version fixes the loop and calls the abstract one-byte read(), the blank each stream (file, socket, byte array) fills in. Note it is not final: FileInputStream overrides it with a faster native bulk read, so here the "template" also acts as a hook with a default. Real code bends the textbook shape.
06

Master it: lambdas, default methods and the traps

Level 4 · Master it

The modern alternative. Instead of subclasses, pass the varying steps into one class as lambdas: Runnable for a step, BooleanSupplier (or Supplier<Boolean>) for the hook, Consumer<T> when the step needs the car. The order is still written once, but the steps are now objects, so they can be picked at run time, from a map or a config. That is Template Method turned into Strategy.

Prefer lambdas when the steps are one-liners, when the choice happens at run time, or when you would otherwise need a subclass per combination. Keep subclasses when the steps share state or helper methods, or when there are many protected steps (a class with five lambdas in its constructor is hard to read).

Default methods in an interface: a partial alternative
A default method can hold the order, and the abstract interface method is the blank. But an interface cannot enforce the order: final default does not compile ("modifier final not allowed here"), so any class may override the template. Its steps must be public (no protected), and it has no instance fields to share state between steps.
Advanced details
Spring proxies and final. Spring adds @Transactional and similar behaviour with a subclass proxy (CGLIB) when there is no interface to proxy. A proxy cannot override a final method, so a final template on such a bean runs without the transaction, and inside it the proxy's own (empty) fields are seen, often as null. Put the annotation on a non-final public method that calls the template, or proxy through an interface.
Constructors. Never call an overridable step from the base class constructor: the subclass's fields are not initialised yet when it runs.
Threads. The template itself adds no thread-safety concern; shared mutable fields in the base class do, exactly as in any class.
Common mistakes
Forgetting final on the template (a subclass reorders or skips steps). Making fixed steps protected or public "just in case" (now they can be overridden). Too many abstract steps (every subclass must write ten methods; make most of them hooks). Hooks that are never overridden (delete them). Calling super.inspect() from a subclass, which shows the template is not really fixed. Deep hierarchies of templates calling templates.

Changing requirements. The dealership grows to nine car types, and each branch wants to switch optional checks on or off and add its own local checks from an admin screen, without a new release. What do you do with PreDeliveryInspection?

  1. Add a subclass for every branch and car type combination
  2. Keep the subclasses and add one hook per optional check
  3. Keep the fixed order in one class, but compose the varying steps: a list of step objects (Strategy or lambdas) built from configuration at run time
  4. Remove final from inspect() so branches can override it
Run-time choices and combinations are exactly where inheritance stops scaling: 9 types × N branches would be a class explosion, and hooks are still fixed at compile time. Keep what Template Method gave you (one place for the order, sign-off last) and make the steps objects you can load and combine. Removing final brings back the drift you started with.

Works with. Strategy (a step of the template delegates to a strategy, or the whole template becomes one); Factory Method (a creation step inside a template, lesson 04); composition over inheritance (P00) is the reason to know when to stop. State (lesson 03) is a close cousin of Strategy, not of this pattern.

Interview and review

Interview and review

Answer out loud first, then open the card.

01What is the Template Method pattern? (30-second answer)
B · A behavioral pattern where a base class defines the skeleton of an algorithm in one method, the template method, usually final, and subclasses override only the steps that vary. Fixed steps stay in the base, required steps are abstract, optional ones are hooks with a default. Example: InputStream.read(byte[], int, int) built on the abstract read().
02Explain it in more depth, with an example from your work.
I · Our pre-delivery inspection had a class per fuel type with the same five steps copied, and the copies drifted. I moved the order into an abstract PreDeliveryInspection.inspect(), marked it final, made the fixed steps private, made the model checks abstract and the road test a hook. New fuel type = one subclass with one method. It applies the Hollywood principle (the base calls the subclass) and Open/Closed for the steps. The cost is inheritance coupling, so if the steps had needed to change at run time I would have used Strategy, or lambdas, instead.
03Why is the template method usually final?
B · Because the order is the pattern. If a subclass could override inspect(), it could skip or reorder steps (sign off before the road test) and the base class could no longer guarantee anything. final lets the compiler enforce the skeleton; subclasses vary only the steps they are allowed to.
04Hook vs abstract step: what is the difference?
B · An abstract step (primitive operation) has no body, so every concrete subclass must implement it. A hook has a default body (empty, or return true), so a subclass may override it to add or skip behaviour. Use abstract for what truly differs per subclass, hooks for optional extension points.
05Template Method vs Strategy?
I · Both vary part of a behaviour. Template Method uses inheritance: the base class controls the flow and subclasses override steps; the variant is fixed when you choose which class to create. Strategy uses composition: the context holds an interface field and calls it; the variant can be swapped at run time and combined freely. Template Method varies steps of one algorithm, Strategy usually the whole algorithm. Modern Java blurs it: passing the steps as lambdas turns a template into a strategy.
06What is the fragile base class problem here?
I · Subclasses depend on the base class's internals: which steps it calls, in which order, with what state. A harmless-looking change to the base (call roadTest() twice, rename a hook, change a default) silently changes every subclass. Mitigate it: keep the template final, keep fixed steps private, keep the number of protected steps small, document what each hook may assume, and test the base with a minimal subclass.
07How many subclasses before you would switch to Strategy?
I · It is not a number but a shape. A handful of stable subclasses that each override one or two steps is fine. Switch when the choice must happen at run time, when variations combine (each new dimension multiplies subclasses), when subclasses start overriding hooks just to switch things off, or when you want to test a step without the base class. Many teams start to move around the third independent variation.
08Where do you see Template Method in Java and Spring?
A · InputStream.read(byte[],int,int) on read(); AbstractList (implement get and size); HttpServlet.service() dispatching to doGet/doPost (not final, so it can be overridden); Spring's OncePerRequestFilter (final doFilter → doFilterInternal) and AbstractApplicationContext.refresh() with hooks like onRefresh(). JdbcTemplate is the callback variant: the fixed JDBC steps are in the template, the varying step (a RowMapper) is passed in, not overridden.
09Why should the base class constructor not call a step?
A · Java runs the base constructor before the subclass's field initialisers. If it calls an overridden step, the subclass method runs on a half-built object and sees its fields as null or 0. Run the template from a normal method after construction.

7 takeaways

  • Template Method writes the order of the steps once, in a base class method, and subclasses fill in the steps that vary.
  • The template method is final: the order is the rule, and the compiler protects it.
  • Abstract step = must fill in; hook = has a default, may override; private step = fixed.
  • Hollywood principle: the base class calls the subclass ("don't call us, we'll call you").
  • Same goal as Strategy, different tool: inheritance and compile-time choice instead of composition and run-time choice.
  • Passing the steps as lambdas turns the template into a Strategy; default methods cannot make the template final.
  • JDK and Spring: InputStream, AbstractList, HttpServlet, OncePerRequestFilter; JdbcTemplate is the callback variant.
