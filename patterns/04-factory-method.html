PATTERNS 04 · MOVE 2 · CREATE

Factory Method: let a subclass decide what to build

Move 2 is about creating objects. In Strategy the question was "which Discount do we use?"; here it is "who decides which Discount (or Car) to new?". The dealership has new PetrolCar() and new EvCar() scattered over checkout, test drives and reports. Factory Method moves that decision into one overridable method. You will feel the pain, refactor in small steps, watch it run, and choose it like a senior engineer.

PATTERNS 04

Factory Method: one overridable method decides which class to create

Seven sections, four levels: a beginner can stop after section 04; sections 05 to 07 add the interview depth.

01

See it: the problem Factory Method solves

Level 1 · See it
In 30 seconds Code that uses an object should not decide which class to build. Put the building in one method, the factory method, declared in a base class and overridden by subclasses. The base class does its work with whatever car the method returns, and never writes new PetrolCar().

The dealership problem. Checkout, test-drive booking and reports each need a car for a given fuel, so each one has its own if / else with new PetrolCar(), new DieselCar(), new EvCar(). When the dealership adds CNG, every one of those places must be edited, and the compiler cannot tell you which one you forgot.

Words used here. new is the keyword that builds an object. A product is the object being created (a car). A creator is the class whose code needs a product and asks for one. A factory method is a method whose job is to return a new product. Concrete means a real class you can build, as opposed to an interface.

💡 Remember itA factory machine with an order slot. The counter takes your order, checks it and hands over the finished item: the same steps every time. Behind the slot, the machine decides what to build. A city machine builds a petrol car, an EV machine builds an electric one. The counter never changes; you swap the machine.

02

Build it: from scattered new to Factory Method

Level 2 · Build it
In 30 seconds Three steps. 1) Callers should hold the interface (Car), not a class. 2) Move the ladder into one static method: a Simple Factory. 3) Turn the creating step into an abstract method that subclasses override: the real Factory Method. Run the program after each step.
Before: every place chooses the car class

What breaks. Adding CNG means editing three ladders in three classes. The copies already differ: Reports returns null for an unknown fuel, the others silently build an EvCar. A forgotten ladder is a silent bug, and none of these classes can be tested without building real cars.

Step 2: a Simple Factory. Move the ladder into one static method. This is not a GoF pattern, just a common stepping stone, and often good enough. Its limit: one class knows every car class, and a static method cannot be overridden or swapped for a fake.

Step 3: the real Factory Method. Use the lab to see how the factory turns into an overridable method.

This visualisation needs JavaScript.

After: Factory Method, each showroom decides its car

The same lines of output for every showroom, and Showroom contains no car class name. sellCar() is a small Template Method: a fixed routine (inspect, then deliver) with one step, createCar(), left to the subclass. Factory Method is very often one step of a Template Method.

Go deeper: abstract or default body?
The factory method may be abstract (every subclass must choose) or have a default implementation that subclasses may override (for example, the base Showroom builds a petrol car unless told otherwise). A default keeps small hierarchies short; abstract forces a decision.

04

Practise: add a showroom, test with a fake

Level 2 · Practise

The dealership starts selling diesel cars again. Add a DieselShowroom (and a DieselCar) to the After program, and sell one. Rule: do not edit Showroom, CityShowroom or any existing class. Expected last lines: Inspecting Nexon Diesel and Delivered Nexon Diesel: Rs 1400000.

Hint
Two new classes: a product (implements Car) and a creator (extends Showroom) whose createCar() returns it. Then new DieselShowroom().sellCar() in main.
Solution

Only the new classes and the lines in main were written. Ran on JDK 25:

public class ExDiesel {
    public static void main(String[] args) {
        new CityShowroom().sellCar();
        // Inspecting Nexon Petrol
        // Delivered Nexon Petrol: Rs 1250000
        new DieselShowroom().sellCar();                  // the new creator plugs in
        // Inspecting Nexon Diesel
        // Delivered Nexon Diesel: Rs 1400000
    }
}

interface Car {
    String describe();
    long price();
}

class PetrolCar implements Car {
    public String describe() { return "Nexon Petrol"; }
    public long price() { return 1250000; }
}

class DieselCar implements Car {                         // NEW product
    public String describe() { return "Nexon Diesel"; }
    public long price() { return 1400000; }
}

abstract class Showroom {                                // unchanged
    abstract Car createCar();

    void sellCar() {
        Car car = createCar();
        System.out.println("Inspecting " + car.describe());
        System.out.println("Delivered " + car.describe() + ": Rs " + car.price());
    }
}

class CityShowroom extends Showroom {                    // unchanged
    Car createCar() { return new PetrolCar(); }
}

class DieselShowroom extends Showroom {                  // NEW creator
    Car createCar() { return new DieselCar(); }
}

You want to test sellCar() without any real car class. Write a fake creator: a Showroom whose createCar() returns a tiny StubCar (describe Stub, price 1), and call sellCar() on it.

Hint
An anonymous subclass of the abstract Showroom is enough: new Showroom() { Car createCar() { return new StubCar(); } }. The business method is the code under test; only the creation is replaced.
Solution

Because creation is a method, a test can override just that method. Ran on JDK 25:

public class FakeShowroom {
    public static void main(String[] args) {
        Showroom test = new Showroom() {                  // a fake creator: no real engine classes
            Car createCar() { return new StubCar(); }
        };
        test.sellCar();
        // Inspecting Stub
        // Delivered Stub: Rs 1
    }
}

interface Car {
    String describe();
    long price();
}

class StubCar implements Car {
    public String describe() { return "Stub"; }
    public long price() { return 1; }
}

abstract class Showroom {
    abstract Car createCar();

    void sellCar() {
        Car car = createCar();
        System.out.println("Inspecting " + car.describe());
        System.out.println("Delivered " + car.describe() + ": Rs " + car.price());
    }
}

Explain Factory Method to a new teammate using the showroom: what is the creator, what is the factory method, who decides which car is built, and what changes in the code when a CNG car arrives?

Model answer. Showroom is the creator: it has the business method sellCar() and an abstract factory method createCar(). sellCar() calls createCar() and works with the result as a Car. Each subclass (CityShowroom, EvShowroom) overrides createCar() to build its own product, so the subclass decides, and the client only picks which showroom to use. For CNG you add a CngCar and a CngShowroom; nothing existing is edited (Open / Closed).
05

Choose it: roles, look-alikes and trade-offs

Level 3 · Choose it
In 30 seconds Use Factory Method when a class does a routine that needs a product, but should not know which concrete class to build, and the choice belongs to subclasses or configuration. Do not use it when one new in one place is all you have.

This visualisation needs JavaScript.

Use it when

  • A class's routine needs an object whose concrete class varies (fuel, market, file format) and new variants keep arriving.
  • You want subclasses or configuration to choose the product, so the routine stays untouched.
  • You want to test the routine with a fake product by overriding one method.

Do not use it when

  • There is one product class that does not vary: plain new is clearer.
  • A simple factory or a Map of Suppliers is enough and there is no routine around the creation: skip the creator hierarchy.
  • You need several matching objects created together (engine + battery + charger for one market): that is Abstract Factory.

Static factory method vs the GoF pattern

Effective Java item 1 recommends static factory methods (List.of(...), LocalDate.of(...)) instead of constructors: they have names, may return a cached or subtype instance, and need not create a new object each time. That is a different thing from the GoF Factory Method, which is an overridable method in a class hierarchy. A static method cannot be overridden, so it gives you none of the "subclass decides" benefit. The names are a convention: of, from, valueOf, getInstance, newInstance.

Trade-offs

  • Complexity: a parallel hierarchy (a creator subclass per product) can feel heavy for small cases.
  • Extensibility and coupling: a new product is a new subclass; the creator depends only on the product interface.
  • Testing: override the factory method with a fake product (section 04); a static factory cannot be swapped.
  • The client still picks a creator: the decision moved, it did not vanish. Put that choice at the edge (configuration, Spring).
  • Performance: one virtual call; not a concern.

In a Spring Boot backend

A conceptual sketch. @Bean methods in a @Configuration class are, conceptually, factory methods: Spring calls them to create objects and hands them out as beans. For harder cases a FactoryBean<T> builds the object itself.

@Configuration
class ShowroomConfig {

    @Bean
    Showroom showroom(DealerProperties props) {   // a factory method for the bean
        return switch (props.fuel()) {
            case "ev" -> new EvShowroom();
            default -> new CityShowroom();
        };
    }
}

@Service
class SalesService {
    private final Showroom showroom;                 // knows only the abstract creator

    SalesService(Showroom showroom) { this.showroom = showroom; }

    void sell() { showroom.sellCar(); }
}

Where Java and Spring already use it

  • Collection.iterator() is a factory method: each collection (ArrayList, LinkedList, HashSet…) overrides it to return its own Iterator, and the code that loops only knows Iterator.
  • Calendar.getInstance() and NumberFormat.getInstance(): static factory methods that choose the concrete class for the locale (conceptually similar: not an overridable method).
  • DocumentBuilderFactory.newInstance() (javax.xml.parsers) finds and creates the parser factory implementation.
  • List.of, Optional.of, LocalDate.of, Integer.valueOf (caches small values): static factory methods.
  • Spring: @Bean methods and FactoryBean<T> (conceptually factory methods that create the bean).

In this code (it ran on JDK 25), which method plays the factory method role?

import java.util.ArrayList;
import java.util.Iterator;
import java.util.LinkedList;
import java.util.List;

public class SpotIterator {
    public static void main(String[] args) {
        List<String> a = new ArrayList<>(List.of("Nexon", "Tiago"));
        List<String> b = new LinkedList<>(List.of("Nexon", "Tiago"));
        print(a);
        print(b);
    }

    static void print(List<String> cars) {
        Iterator<String> it = cars.iterator();            // which class is created? the list decides
        System.out.println(it.next() + " " + it.getClass().getSimpleName());
    }
}
// Nexon Itr
// Nexon ListItr
  1. print
  2. it.next()
  3. cars.iterator()
  4. main
iterator() returns a new Iterator and each collection overrides it: ArrayList builds its own Itr, LinkedList its ListItr. print is the code that uses the product through the Iterator interface and never knows the class: the creator's business method.
06

Master it: Factory Method in modern Java

Level 4 · Master it
In 30 seconds A factory method is "a way to create a Car", so a Supplier<Car> can stand in for it: a constructor reference (EvCar::new) is the whole creator. Use a Map<String, Supplier<Car>> to choose by name. Keep subclasses when the creator has real routine code around the creation.
Create with…when
a creator subclassthe creator has a routine around the creation (sellCar()) and subclasses differ in more than one thing
a Supplier<T> / constructor referencethe only thing that varies is "how to build one"
a Map<String, Supplier<T>> registrythe choice comes from a string (a request, configuration, a database row)
a static factory methodyou want a named, cached or subtype-returning constructor replacement (of, from, valueOf, getInstance, newInstance)

Is a Supplier "still the pattern"? Yes, in spirit: a creator asks something else to build the product. The parameterized factory method (one method taking a type argument) is the same idea with a switch inside, so it carries the Open / Closed cost of a Simple Factory.

Advanced details: caching and instances
A factory method may return a cached or shared instance instead of a new one: Integer.valueOf(127) returns the same object each time (small values are cached; the program above shows true for 127 and false for 1000), which is why == on boxed numbers is unreliable. A constructor can never do that, so a factory method can also hand out a singleton or a pooled object. If a registry map is read by many threads, build it once and never change it (Map.of is immutable); a mutable HashMap shared between threads needs a thread-safe map.
Common mistakes
  • Calling an overridable factory method from a constructor: the subclass is not fully built yet and its fields are still null or 0.
  • A factory method that returns a concrete class (PetrolCar createCar()) so callers depend on it again: return the interface.
  • Moving the if / else instead of removing it: a factory with a switch is fine once, at the edge; a switch in every creator is not the pattern.
  • A creator subclass for every tiny variation when a Supplier would do.
  • Calling a static factory "Factory Method": it is a useful idiom, not the GoF pattern.

A new requirement. The dealership adds a CNG car next month and a hybrid after that. A new sellCar() step (insurance check) must apply to every showroom. Which design do you choose?

  1. Add a "cng" branch to the switch in CarFactory and copy the insurance check into each caller
  2. Keep Factory Method: put the insurance check once in Showroom.sellCar() and add a CngShowroom and a HybridShowroom that override createCar()
  3. Make every car class create itself with a static create() method
  4. Use Strategy: give each car a discount object
The shared routine belongs in the base class, so a new step is written once (and the routine is a Template Method). New fuels are new subclasses, so nothing existing is edited. Option 1 copies the check everywhere and keeps editing a switch. Option 3 cannot be overridden or swapped. Option 4 solves a different problem (behaviour, not creation).

Patterns it works with

  • Template Method: sellCar() is the template and createCar() one of its steps; Factory Method is often a step of a Template Method.
  • Strategy: a factory can create the right strategy for a code (the one remaining switch at the edge).
  • Abstract Factory (lesson 08, coming): a group of factory methods that create a matching family. Builder (lesson 05, coming): for one complex object built in steps.
  • Singleton and Prototype: a factory method can return a shared instance or a copy.

Interview and review

Interview and review

Answer out loud first, then open the card.

01What is the Factory Method pattern? (the 30-second answer)
B · Factory Method defines a method for creating an object in a base class, but lets subclasses decide which concrete class to instantiate. The base class has a business method that calls the abstract factory method and works with the result through an interface, so it never names a concrete class. Example: Showroom.sellCar() calls createCar(), which CityShowroom and EvShowroom override; in the JDK, Collection.iterator().
02Walk me through it in more depth.
I · Four roles: the Product interface (Car), ConcreteProducts implementing it, the Creator (Showroom) with the factory method and an operation that uses it, and ConcreteCreators that override the factory method. The client picks a creator. Benefits: Open / Closed (a new product is a new subclass), loose coupling to concrete classes, one place per product where new lives, and testing with a fake creator. Costs: a parallel hierarchy and the choice of creator still has to be made somewhere.
03Simple Factory vs Factory Method vs Abstract Factory?
I · Simple Factory is one class or static method with a switch that returns a product; it is not a GoF pattern. Factory Method is an overridable method in a creator class: the subclass decides, so new products mean new subclasses. Abstract Factory is an interface with several factory methods that create a family of matching products (an India set vs an EU set); it is often implemented with factory methods. Rule of thumb: one product, switch on a parameter = simple factory; one product, subclass decides inside a routine = factory method; several related products that must match = abstract factory.
04Static factory method vs the GoF Factory Method?
I · A static factory method (Effective Java item 1) is a named static method that returns an instance: List.of, LocalDate.of, Integer.valueOf. Pros: names, may return a cached or subtype instance, no new object needed, can hide implementation classes. Cons: cannot be overridden, so no polymorphic choice; classes with only static factories and private constructors cannot be subclassed; harder to discover in docs. The GoF Factory Method is an instance method that subclasses override. Same word, different mechanism.
05How does it support Open / Closed and Dependency Inversion?
B · Open / Closed: the creator's routine is closed for modification, and a new product is added by a new subclass instead of another branch. Dependency Inversion: the high-level Showroom depends on the abstraction Car, and the concrete class is chosen by a subclass or injected from outside, so no high-level code names PetrolCar.
06What is a parameterized factory method?
I · A factory method that takes an argument (a type code, a string, an enum) and chooses the product: Car createCar(String fuel). It is compact, but the switch inside has the same Open / Closed problem as a Simple Factory unless subclasses override it for new kinds, or the argument selects from a registry (Map<String, Supplier<Car>>). Good at the edge of the system, risky if it spreads.
07How do you test code that uses a factory method?
I · Override the factory method in a test subclass (or an anonymous class) that returns a stub or mock product, so the business method runs without real engines, databases or network. With a static factory you cannot do this without a mocking library or a seam; that is one reason to prefer an overridable method or an injected Supplier.
08When would you NOT use Factory Method?
B · When there is one product and it does not vary, when a simple factory or a Map of suppliers is enough, or when you need matching families (Abstract Factory) or step-by-step construction (Builder). Adding a creator hierarchy for variation that never comes is over-engineering.
09Why is calling a factory method from a constructor dangerous?
A · Java runs the base-class constructor before the subclass's fields are initialised, so an overridden factory method called there runs on a half-built subclass and can see null or default values. Call it lazily or from a normal method after construction, or pass the product in (injection).
IntentA base class declares a method that creates the product; subclasses decide which class to build.
StructureCreator (factory method + business method) ← ConcreteCreators; each creates a ConcreteProduct of the Product interface.
Use whenA routine needs a product whose class varies and new variants keep arriving; testing needs a fake.
Trade-offA parallel class hierarchy; the creator must still be chosen. Skip it for one fixed class.
RememberFactory machine with an order slot: the counter takes the order, the machine behind decides what to build.

8 takeaways

  • Factory Method: a method that creates the product, declared in a base class and overridden by subclasses.
  • Roles: Creator = Showroom, factory method = createCar(), ConcreteCreator = CityShowroom, Product = Car.
  • The smell: new and an if / else on a type code scattered in many places.
  • Simple Factory (one static switch) is a useful stepping stone, not a GoF pattern.
  • Factory Method is often one step of a Template Method: the routine is fixed, the creation varies.
  • A static factory method (List.of, valueOf) is Effective Java item 1, not the GoF pattern: it cannot be overridden.
  • Modern Java: a Supplier or constructor reference (EvCar::new) and a Map of suppliers replace many small creator classes.
  • Test by overriding the factory method with a fake; do not use it for one fixed class.
