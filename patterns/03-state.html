PATTERNS 03 · MOVE 1 · SWAP

State: let the order's stage decide what it can do

A car order is booked, then paid, then delivered, and what you may do with it depends on where it is. Instead of a growing switch on a status string, give each stage its own class and let the order hand every request to its current stage. The stages themselves decide what comes next.

PATTERNS 03

State: one class per stage, transitions inside the stages

Seven sections: see the pain, build the pattern, watch it run, practise, choose it, master it, then the interview questions and review.

01

See it: an order that behaves differently at every stage

Level 1 · See it
In 30 seconds When an object's behaviour depends on what stage it is in, keep the stage as an object. The main object (the context) passes every request to its current state object; each state is a class that knows what is allowed and which state comes next. Changing stage = swapping one object for another.

The dealership problem. A customer books a car. The order can then be paid, then delivered. It can be cancelled while booked (nothing to refund) or after payment (refund the money), but never after delivery. Every action (pay, deliver, cancel) has a different answer in every stage, and the business keeps adding stages.

💡 Remember itA traffic light. The light box at the junction does not contain a big "if red… if green…" rule: it simply shows its current lamp, and each lamp knows how long it stays and which lamp comes next (green → amber → red → green). Swap the lamp, and the same box behaves differently.

04

Practise: change the lifecycle yourself

Level 2 · Practise

Customers who try to cancel a delivered car should get a helpful message: cannot cancel: the car is already delivered, raise a return request. Change one class in OrderAfter.java so a.cancel() prints it. Which class, and why only that one?

Hint
Today the "cannot cancel" line comes from the interface's default cancel. Which state is the order in when a.cancel() runs? A class can override a default method.
Solution
Override cancel in Delivered only. No other class changes, because the rule belongs to that one state. The output's fourth line becomes the new message; ORD-2 is unchanged. 
class Delivered implements OrderState {
    public String name() { return "Delivered"; }
    public void cancel(Order o) { System.out.println("cannot cancel: the car is already delivered, raise a return request"); }
}
// ORD-1: Allocated -> Delivered (keys handed over)
// cannot cancel: the car is already delivered, raise a return request

Change request: every car gets a pre-delivery inspection (PDI). Add a status Inspected between Allocated and Delivered and a new action inspect(). After the change, deliver() on an Allocated order must be rejected; cancelling from Inspected refunds the price. Count the classes you edit.

Hint
A new action touches the interface (one default method that rejects) and Order (one delegating line). A new status is one new class. Then move the "deliver" arrow: Allocated now goes to Inspected on inspect, and Inspected goes to Delivered on deliver.
Solution
Edited: OrderState (+1 default), Order (+1 line), Allocated (deliver becomes inspect). New: Inspected. Booked, Paid, Delivered and Cancelled are untouched. Tested on JDK 25: 
interface OrderState {
    // … name(), pay, allocate, deliver, cancel as before …
    default void inspect(Order o)  { o.reject("inspect"); }     // new action: rejected everywhere by default
}
class Allocated implements OrderState {
    public String name() { return "Allocated"; }
    public void inspect(Order o) { o.moveTo(new Inspected(), "PDI passed"); }   // was deliver()
    public void cancel(Order o)  { o.moveTo(new Cancelled(), "refund Rs " + o.price()); }
}
class Inspected implements OrderState {                         // the new status: one new class
    public String name() { return "Inspected"; }
    public void deliver(Order o) { o.moveTo(new Delivered(), "keys handed over"); }
    public void cancel(Order o)  { o.moveTo(new Cancelled(), "refund Rs " + o.price()); }
}
// in Order:  void inspect()  { state.inspect(this); }

// Order a = new Order("ORD-3", 1500000); a.pay(); a.allocate(); a.deliver(); a.inspect(); a.deliver();
// ORD-3: Booked -> Paid (Rs 1500000 received)
// ORD-3: Paid -> Allocated (chassis reserved)
// ORD-3: cannot deliver an order that is Allocated
// ORD-3: Allocated -> Inspected (PDI passed)
// ORD-3: Inspected -> Delivered (keys handed over)

Explain to a new teammate, in your own words: in the State pattern, what does the context do, what does a state do, who decides the next state, and where does "you cannot do that now" live?

Model answer. The context (our Order) is the object everyone talks to; it keeps a reference to its current state object and forwards every request to it, passing itself along. Each state is a class that implements the requests for one stage: it does the work and, if the stage changes, creates the next state and tells the context to switch (moveTo). So the states decide the transitions, not the client and not the context. "Not allowed" is written once, as a default (or base-class) method that rejects; a state overrides only the actions it allows, so final states like Delivered override nothing.

Trade-offs. Complexity: five small classes instead of one class; worth it only when the switches really grow. Extensibility: a new stage is a new class (Open / Closed). Coupling: states know their successors and call back into the context, so the context needs a small package-private API (moveTo, reject). Testing: each state is tested alone with a real or fake context. Performance: one extra call per request; stateless states can be shared instead of created each time (section 06).

In a Spring Boot backend

A conceptual sketch: the order is a JPA entity, the stage is stored as text, and the service loads the order, asks the state machine for the next stage and saves it.

@Entity
public class CarOrder {
    @Id @GeneratedValue private Long id;
    private long price;
    @Enumerated(EnumType.STRING)                 // stored as 'PAID', not as 1
    private Status status = Status.BOOKED;       // the enum-based states from section 06
    @Version private long version;               // two clerks cannot both move the same order

    public void pay() { status = status.pay(); } // IllegalStateException if not allowed
}

public interface CarOrderRepository extends JpaRepository<CarOrder, Long> {}

@Service
public class OrderService {
    private final CarOrderRepository repo;
    public OrderService(CarOrderRepository repo) { this.repo = repo; }

    @Transactional
    public void pay(Long id) {
        CarOrder order = repo.findById(id).orElseThrow();
        order.pay();                             // the state decides; the change is saved on commit
    }
}

In the JDK and Spring. Thread.State (NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED) is an enum of states, not the GoF pattern: Thread does not delegate its behaviour to it, you only read it. Spring Statemachine is a separate Spring project where states, events and transitions are declared in configuration; it is conceptually the same idea at framework scale. Order, payment and approval workflows in most backends are State machines, written either way.

Is this the State pattern?

Thread t = new Thread(() -> {});
System.out.println(t.getState());   // NEW
t.start();
t.join();
System.out.println(t.getState());   // TERMINATED
  1. Yes: each Thread.State constant is a state object that Thread delegates start() to.
  2. Not the GoF pattern: Thread.State is an enum that reports the stage; Thread's methods do not delegate to it.
  3. It is Strategy: the client picks the state.
  4. It is Singleton, because each constant exists once.
getState() returns a value describing the thread's stage; start() and join() are not forwarded to a state object, and you cannot add a state. An enum of states becomes the State pattern only when the behaviour lives in the constants and the owner delegates to them (as in section 06).
06

Master it: enums, sealed types and shared states

Level 4 · Master it

Modern Java: an enum-based state machine. When the set of stages is fixed and the states hold no data of their own, an enum whose constants override methods is the State pattern in one file: each constant is a state object, created once by the JVM and shared by every order. The order stores just the constant; the database stores its name.

Go deeper: sealed interface + records + switch, when each state carries data
If a state needs its own data (the amount paid, the chassis reserved, the refund), make each state a record under a sealed interface. The transitions become switch expressions with type patterns; with no default, the compiler checks that every state is handled, so adding a sixth record breaks the build until every switch handles it. This flips the design: behaviour sits in functions over states, not inside the states. Good for immutable, event-driven code; less good when you keep adding actions.
Go deeper: sharing stateless states, persistence, thread safety
Sharing. Our state classes have no fields, so one instance of each is enough: keep them in static final constants (or use the enum) instead of new Paid() on every move. That is a per-state Singleton (lesson 06, coming). A state that holds per-order data (an on-hold state that remembers where to resume) cannot be shared. Persistence. Store the state's name() (or the enum name with EnumType.STRING), never the ordinal; on load, map the name back to the state object with a small factory or Status.valueOf. Thread safety. Two threads calling pay() and cancel() at once can both read the old state; make transitions synchronized on the order, or in a database use optimistic locking (@Version) so the second save fails and is retried.

Common mistakes

  • Keeping the old switch "just for one case": now the rules live in two places.
  • Letting the client call setState(new Paid()): anyone can skip payment. Keep the setter package-private, used only by states.
  • Throwing UnsupportedOperationException from each state by hand instead of one shared default: copies drift.
  • Storing the enum ordinal in the database: inserting "Allocated" renumbers every later stage.
  • Using State for two stages and one action: a boolean was enough.

New requirement. Finance wants to put any open order (Booked, Paid or Allocated) on hold during a payment dispute, and resume() must return it to exactly the stage it was in. What is the cleanest change to the class-based design?

  1. Add a boolean onHold to Order and an if (onHold) at the top of every method.
  2. Add an enum constant ON_HOLD; on resume, always go back to BOOKED.
  3. Add a class OnHold with a field previous (the state it interrupted); hold() in each open state moves to new OnHold(this), and OnHold.resume moves back to previous.
  4. Make the client keep the previous state and call a public setState on resume.
The new stage carries data (where to resume), so it is a class with a field, created per order (not shared). Every other action on OnHold is rejected by the defaults, and the other states change only by gaining hold(). The boolean brings back a switch in every method; resuming to BOOKED loses information; a public setter lets the client skip rules.

Works well with. Strategy (a state can use a strategy, e.g. Paid picks a refund rule) · Singleton (shared stateless states; lesson 06) · Flyweight (many orders sharing state objects) · Factory Method (rebuild a state from its stored name) · Observer (notify the customer on every transition) · Memento (keep a history of stages for undo or audit). Its Move 1 siblings, Strategy and Template Method, also swap behaviour; section 07 compares all three.

07

Interview and review

Interview and review

Answer out loud first, then open the card.

01Explain the State pattern in 30 seconds.
State lets an object change its behaviour when its internal stage changes. The object, called the context, holds a reference to a state object and forwards every request to it. Each stage is its own class implementing a common interface; it handles the request and, when needed, switches the context to the next state. Example: a car order moving Booked → Paid → Delivered, where cancel refunds from Paid and is rejected after delivery, with no switch statements.
02Give the deeper answer: structure, benefits, costs.
Roles: Context (holds state, delegates, exposes a narrow way to change state), State interface (one method per request; defaults or an abstract base hold the "not allowed" answer), ConcreteStates (one per stage, implementing allowed requests and choosing successors). Benefits: no conditionals on a status code, each stage's rules in one class, new stages added as classes (Open / Closed), illegal actions handled in one place, each state testable alone. Costs: more classes, states coupled to their successors and to the context's API, transitions spread over classes (draw the state diagram). Alternatives: an enum with per-constant methods when stages are fixed, a sealed hierarchy with pattern-matching switches when states carry data, a state-machine library for configurable workflows.
03State vs Strategy: the class diagrams are identical. What is the difference?
B · Intent and who changes the object. With Strategy the client chooses one algorithm from outside, and the strategies don't know each other (a discount rule). With State the states themselves replace each other as the object moves through its lifecycle, usually many times, and each state knows its successors. Strategy answers "how should this be done?", State answers "what can I do now, and what happens next?".
04Who should own the transitions: the context or the states?
I · Both are valid GoF variants. States own them (as here): adding a stage touches only its neighbours, but states depend on each other. The context owns them (a transition table in Order): the whole lifecycle is visible in one place and states stay independent, but the context grows with every stage. Choose states-own when the per-stage logic is rich; context-own (or a table/enum) when the flow must be read and audited at a glance.
05How do you persist the state in a database?
I · Store a stable name of the stage ("PAID"), not the object and not an enum ordinal. With JPA: an enum field with @Enumerated(EnumType.STRING), or a converter. On load, rebuild the state object from the name (Status.valueOf, or a small factory/map for class-based states). Any per-state data (refund amount, chassis) goes in normal columns. Add @Version so concurrent transitions are detected.
06How do you test a State implementation?
I · Test each state on its own: put an order into that state, call every action, and check the resulting state name and output (or the exception). That gives a table "state × action → expected", which is exactly the state diagram; every missing arrow is a "rejected" test. Add one end-to-end test of the happy path. Because the context only delegates, it needs very few tests itself.
07When is a plain enum and a switch enough?
B · When there are few stages, one or two actions depend on them, and the list rarely changes, e.g. a boolean-like "draft / published". A switch over an enum (not a String) is type-safe, and a switch expression without default even forces you to handle a new constant. Move to State (or an enum with per-constant methods) when several methods switch on the same field.
08Are state transitions thread-safe?
A · Not by themselves: "read state, decide, write next state" is a check-then-act race. If two threads call pay() and cancel() together, both can act on the old state. Guard the transition: synchronized methods on the context, an AtomicReference<OrderState> with compareAndSet, or, across servers, a database transaction with optimistic locking (@Version). Stateless shared state objects themselves are safe to share; states with fields belong to one order.

8 takeaways

  • State: the context forwards every request to its current state object; changing stage means swapping that object.
  • Smell it: the same status field switched on in several methods, growing with each change request.
  • One class per stage holds all of that stage's rules; the "not allowed" answer is written once, as a default.
  • The states decide the transitions (they create the next state and call moveTo); the client never sets the state.
  • Same class diagram as Strategy; the difference is who changes the object: the client (Strategy) or the states (State).
  • An enum with per-constant methods is State in one file when the stages are fixed; sealed records + switch fit when states carry data.
  • Persist the stage's name (EnumType.STRING), never the ordinal; guard concurrent transitions with locking or @Version.
  • Thread.State is an enum of states, not the GoF pattern; Spring Statemachine is the framework-scale version of the idea.
