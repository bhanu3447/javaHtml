PATTERNS 01 · MOVE 1 · SWAP

Strategy: swap the rule, keep the checkout

The dealership's checkout keeps growing an if / else for every new discount. Strategy puts each discount rule in its own small class behind one interface, so the checkout just asks "the current rule" to do the maths. You will feel the pain, refactor it step by step, watch it run, and then choose it (or not) like a senior engineer.

PATTERNS 01

Strategy: interchangeable behaviour behind one interface

Seven sections, four levels: a beginner can stop after section 04; sections 05 to 07 add the interview depth.

01

See it: the problem Strategy solves

Level 1 · See it
In 30 seconds When one job can be done in several interchangeable ways (several discount rules), put each way in its own class behind one interface. The object that needs the job done keeps one of them and hands the work to it. Changing the behaviour means handing it a different object, not editing its code.

The dealership problem. At checkout the price depends on an offer: none, festival 10% off, Rs 20000 off for loyal customers, 15% for corporate buyers. Marketing invents a new offer every few weeks. Each one lands as another branch inside Checkout.

Four words you will see on every pattern page. The client is the code that uses an object (here main). The context is the object whose behaviour should vary (Checkout). A strategy is one interchangeable behaviour, an object that does the varying part. Delegation means the context passes that part of the work to the strategy instead of doing it itself.

💡 Remember itA car's drive modes. The driver turns a knob to Eco, Sport or Snow; the car is the same car, but throttle and gears now follow a different rule. The car does not contain an if / else for every mode you might invent: each mode is a module that plugs into the same slot.

02

Build it: from the if / else ladder to Strategy

Level 2 · Build it
In 30 seconds Find what varies (the rule), give it an interface, move each branch into its own class, give the context a field of the interface type, and let the client choose. Run the program after every step: the output must not change.
Before: every offer is a branch, twice

What breaks. Every new offer edits two methods of a class that already works, so tested branches are re-tested each time. The two ladders must stay in step by hand. A typo such as "festive" silently means no discount. And you cannot test the loyalty rule alone: it only exists inside Checkout.

This visualisation needs JavaScript.

After: every offer is a class, Checkout delegates

Same four lines of output, but Checkout has no offer names in it any more. The typo problem also moved: new FestiveDiscount() does not compile, so the mistake is caught before the program runs.

Go deeper: why a setter and a constructor?
The constructor guarantees Checkout always has some rule (no null checks later). The setter allows a swap on the same object, which is what the GoF book shows. Many real systems skip the setter and create a new context per request instead, which keeps the context immutable and thread-safe: a strategy chosen once per checkout is enough.

04

Practise: add a rule, refactor a ladder

Level 2 · Practise

Students now get 5% off. Add a StudentDiscount to the After program (section 02) and print a student checkout of Rs 700000. Rule: you may not edit Checkout or any existing discount class. Expected output line: Student 5%: Rs 665000.

Hint
A new rule is a new class that implements Discount, with apply and label. Then the client hands it in with setDiscount (or the constructor). 5% off means price * 95 / 100.
Solution

Only the new class and two lines in main were written; the rest is unchanged (shortened here to the parts used). Ran on JDK 25:

public class StudentOffer {
    public static void main(String[] args) {
        Checkout checkout = new Checkout(new FestivalDiscount());
        checkout.print(700000);                         // Festival 10%: Rs 630000
        checkout.setDiscount(new StudentDiscount());    // the new rule plugs in
        checkout.print(700000);                         // Student 5%: Rs 665000
    }
}

interface Discount {
    long apply(long price);
    String label();
}

class FestivalDiscount implements Discount {
    public long apply(long price) { return price * 90 / 100; }
    public String label() { return "Festival 10%"; }
}

class StudentDiscount implements Discount {             // NEW: one new class, nothing else edited
    public long apply(long price) { return price * 95 / 100; }
    public String label() { return "Student 5%"; }
}

class Checkout {                                        // unchanged
    private Discount discount;
    Checkout(Discount discount) { this.discount = discount; }
    void setDiscount(Discount discount) { this.discount = discount; }
    long total(long price) { return discount.apply(price); }
    void print(long price) { System.out.println(discount.label() + ": Rs " + total(price)); }
}

The delivery desk charges by delivery mode: showroom pickup (free), home delivery (Rs 50 per km) and flatbed truck (Rs 2000 + Rs 80 per km). Refactor DeliveryDesk to Strategy: one interface, the modes chosen by name from a Map, and a clear error for an unknown mode. Keep the same output.

Hint
The varying part is "how to charge for km": long charge(int km), one method, so a functional interface fits and the simple modes can be lambdas. The flatbed has two numbers (base and per-km): a small record that implements the interface keeps them named. The desk gets a Map<String, DeliveryCharge> through its constructor and looks the mode up instead of branching.
Solution

The desk is the context, DeliveryCharge the strategy, the map a registry the client fills. A new mode is one more map entry. Ran on JDK 25:

import java.util.Map;

public class DeliveryAfter {
    public static void main(String[] args) {
        DeliveryDesk desk = new DeliveryDesk(Map.of(
            "pickup", km -> 0,
            "home", km -> 50L * km,
            "flatbed", new Flatbed(2000, 80)));
        System.out.println(desk.charge("pickup", 12));    // 0
        System.out.println(desk.charge("home", 12));      // 600
        System.out.println(desk.charge("flatbed", 12));   // 2960
        try {
            desk.charge("drone", 12);
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());           // unknown mode: drone
        }
    }
}

@FunctionalInterface
interface DeliveryCharge {                                // the Strategy
    long charge(int km);
}

record Flatbed(long base, long perKm) implements DeliveryCharge {   // a strategy with data
    public long charge(int km) { return base + perKm * km; }
}

class DeliveryDesk {                                      // the Context
    private final Map<String, DeliveryCharge> modes;

    DeliveryDesk(Map<String, DeliveryCharge> modes) { this.modes = modes; }

    long charge(String mode, int km) {
        DeliveryCharge c = modes.get(mode);
        if (c == null) throw new IllegalArgumentException("unknown mode: " + mode);
        return c.charge(km);
    }
}

Explain Strategy to a new teammate using the checkout: what is the context, what is a strategy, who chooses it, and what changes in the code when a new offer arrives?

Model answer. Checkout is the context: it needs a discount applied but should not know the rules. Discount is the strategy interface (apply, label), and each offer (FestivalDiscount, LoyaltyDiscount…) is a concrete strategy. Checkout keeps one Discount in a field and delegates to it. The client (main, or Spring in a real app) chooses which one to hand in, and can swap it with setDiscount. A new offer is one new class; Checkout is not edited (Open / Closed), and each rule can be tested alone.
05

Choose it: roles, look-alikes and trade-offs

Level 3 · Choose it
In 30 seconds Use Strategy when the same job has several interchangeable versions that change or grow, and the client (not the context) should pick one. Do not use it for two branches that never change: an if / else is clearer.

This visualisation needs JavaScript.

Use it when

  • One job has several versions (pricing, tax, sorting, payment fees) and new ones keep arriving.
  • You want to choose or swap the version at run time, from configuration or user input.
  • You want to test each rule alone, or test the context with a fake rule.

Do not use it when

  • There are two or three cases that have not changed in a year: keep the if / else or a switch.
  • The versions differ only by a number (10%, 15%): one class with a percent field (or a record) is enough.
  • The behaviour should change by itself as the object's status changes: that is State (P03), not Strategy.

Trade-offs

  • Complexity: more classes (one per rule) and one level of indirection to follow when reading.
  • Extensibility and coupling: a new rule is a new class; the context depends only on the interface.
  • Testing: each rule is tested with one line; the context with a lambda as a fake.
  • The client must know the options to choose one; hide that behind a map or a factory when there are many.
  • Performance: one interface call, which the JIT usually inlines; not a concern in practice.

In a Spring Boot backend

A conceptual sketch: each discount is a bean, and Spring injects all of them into the checkout service as a map keyed by bean name. The request carries the offer code; the service looks the strategy up. A new offer is a new @Component.

public interface DiscountPolicy {
    long apply(long price);
}

@Component("festival")
class FestivalPolicy implements DiscountPolicy {
    public long apply(long price) { return price * 90 / 100; }
}

@Component("loyalty")
class LoyaltyPolicy implements DiscountPolicy {
    public long apply(long price) { return Math.max(0, price - 20000); }
}

@Service
class CheckoutService {
    private final Map<String, DiscountPolicy> policies;   // Spring fills it: bean name → bean

    CheckoutService(Map<String, DiscountPolicy> policies) { this.policies = policies; }

    long total(long price, String offerCode) {
        DiscountPolicy policy = policies.get(offerCode);
        if (policy == null) throw new IllegalArgumentException("unknown offer: " + offerCode);
        return policy.apply(price);
    }
}

Where Java and Spring already use it

  • List.sort(Comparator) and Collections.sort(list, comparator): the sort algorithm is the context, the Comparator is the strategy.
  • The java.util.function interfaces (Function, Predicate, Supplier…) are ready-made strategy types: stream.filter(predicate) takes the rule as an argument.
  • ThreadPoolExecutor takes a RejectedExecutionHandler (AbortPolicy, CallerRunsPolicy, DiscardPolicy…): what to do when the queue is full.
  • Spring Security's PasswordEncoder (BCryptPasswordEncoder, Argon2PasswordEncoder, Pbkdf2PasswordEncoder); DelegatingPasswordEncoder picks one by the {id} prefix of the stored hash.
  • Spring injecting a List<T> or Map<String, T> of all beans of a type is the usual way to collect strategies (conceptually a registry, as in the sketch above).

In this code (it ran on JDK 25), which object plays the Strategy role?

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class SortStrategy {
    public static void main(String[] args) {
        List<Car> cars = new ArrayList<>(List.of(
            new Car("Nexon", 1250000), new Car("Tiago", 550000), new Car("Harrier", 1800000)));
        cars.sort(Comparator.comparingLong(Car::price));             // strategy 1: cheapest first
        System.out.println(cars);
        cars.sort(Comparator.comparingLong(Car::price).reversed());  // strategy 2: dearest first
        System.out.println(cars);
    }
}

record Car(String model, long price) {
    public String toString() { return model; }
}
// [Tiago, Nexon, Harrier]
// [Harrier, Nexon, Tiago]
  1. the List of cars
  2. the Comparator passed to sort
  3. the Car record
  4. main
The Comparator is the interchangeable rule ("which car comes first"). List.sort is the context: its sorting algorithm stays the same and delegates every comparison to the comparator it was given. main is the client that picks the rule, and swapping it changes the order without touching the sort code.
06

Master it: Strategy in modern Java

Level 4 · Master it
In 30 seconds If the strategy interface has one abstract method, it is a functional interface (P00, section 13), so a strategy can be a lambda or a method reference. Use a class or record when the rule has data, several methods or a name to show; use a map or an enum to choose by name.
Write the strategy as…when
a lambdaa one-line rule with no data and no name to show
a method referencethe rule already exists as a method (Offers::loyalty)
a record or classit carries data (PercentOff(15)), has several methods (label()), needs dependencies or its own tests
an enum constantthe set of rules is fixed and known at compile time, and you want names, values() and safe switch
a Map<String, Discount>the choice comes from a string (a request, a config file, a database row)

Is a lambda "still the pattern"? Yes: the pattern is the roles (a context delegating to an interchangeable behaviour chosen from outside), not the number of classes. Lambdas just remove the boilerplate.

Advanced details: state, threads and sharing
A strategy with no fields (all four discounts) is stateless, so one instance can be shared by every thread and every checkout: Spring beans are singletons by default for this reason, and an enum constant or a static lambda works the same way. If a strategy keeps mutable state (a counter, a cache), it is no longer safe to share: create one per use or make it thread-safe. A context with a setter is mutable too: swapping the strategy on a checkout another thread is using is a race; prefer a new context per request or a final field.
Common mistakes
  • Moving the if / else, not removing it: a factory with the same ladder is fine once, at the edge; a ladder in the context again means the pattern was not applied.
  • Strategies that know the context's internals (reach back into Checkout fields): pass what they need as parameters.
  • One class per number: Percent10, Percent15… use one parameterised strategy.
  • Checking the type of the strategy (instanceof FestivalDiscount) in the context: that brings the coupling back.
  • Using Strategy for two fixed cases: more code to read for no gain.

A new requirement. Marketing now wants offers to stack (festival, then loyalty on the reduced price), and the list of offers per city must come from a database table so it can change without a redeploy. Which design do you choose?

  1. Add a "festival+loyalty" branch for each combination to Checkout
  2. Switch to the State pattern so the checkout moves from one discount to the next
  3. Keep Strategy: look up each offer code from the table in a Map<String, Discount> and combine them with andThen into one Discount for the checkout
  4. Make one Checkout subclass per combination of offers
Combinations multiply (n offers → 2ⁿ combinations), so branches or subclasses explode. State is about an object's own lifecycle, not about a list chosen from outside. Strategies compose: the registry turns codes from the database into strategy objects, andThen chains them (the ModernStrategy program prints 610000 for festival then loyalty), and Checkout still sees one Discount. This is Strategy cooperating with a Composite-like chain.

Patterns it works with

  • Factory Method: creates the right strategy from a code, keeping the one remaining switch at the edge of the system.
  • Template Method: its look-alike built on inheritance; a template step can delegate to a strategy.
  • State: the same class diagram, but the object switches its own state objects.
  • Decorator and Composite: wrap or combine strategies (stacked discounts). Singleton / Flyweight: share one stateless strategy instance.

Interview and review

Interview and review

Answer out loud first, then open the card.

01What is the Strategy pattern? (the 30-second answer)
B · Strategy defines a family of interchangeable algorithms, puts each one in its own class behind a common interface, and lets the client choose which one a context object uses. The context holds a reference to the interface and delegates to it, so new behaviour is added with a new class instead of a new if / else. Example: Checkout delegating to a Discount such as FestivalDiscount; in the JDK, List.sort(Comparator).
02Walk me through it in more depth.
I · Three roles: the Strategy interface (one operation, e.g. apply(price)), ConcreteStrategies implementing it, and the Context that has-a Strategy and calls it for the varying step. The client picks the concrete strategy (constructor, setter, factory, map or DI). Benefits: Open / Closed (new rule = new class), Single Responsibility (one rule per class), easy testing, run-time swapping. Costs: more classes, the client must know the options, and the strategy interface must fit every variant (if one rule needs extra data, pass a richer parameter object). In modern Java a single-method strategy is a functional interface, so lambdas and method references are strategies too.
03Strategy vs State: the diagrams look the same. What is the difference?
I · Intent and who chooses. In Strategy the client picks the behaviour from outside and the strategies don't know each other (any discount for any checkout). In State the object itself changes its state object as events happen (an order goes booked → paid → delivered), and states usually know which state comes next. Strategy answers "how should this be done?"; State answers "what can I do right now, given where I am?".
04How do you choose the strategy at run time?
I · Something at the edge maps an input to a strategy, so the context never branches. Options: a factory method with one switch; a Map<String, Strategy> registry (getOrDefault or a clear error for unknown keys); an enum whose constants hold the strategies; or dependency injection: Spring injects all DiscountPolicy beans as a List or a Map keyed by bean name, and the service picks by key. The choice can come from the request, configuration, a feature flag or the database.
05With lambdas, is Strategy still a pattern?
A · Yes. The pattern is the design (a context delegating to an interchangeable behaviour supplied from outside), not the class count. Lambdas make concrete strategies cheap when the interface has one method and the rule has no state or name. You still want classes or records when the strategy has data, several methods, dependencies, or deserves its own tests and a name in logs. Many people say "in functional style Strategy is just passing a function": that is the same idea, which is why Comparator works both ways.
06How does Strategy follow Open / Closed and Dependency Inversion?
B · Open / Closed: the context is closed for modification (no branch per rule) and open for extension (add a class that implements the interface). Dependency Inversion: the high-level Checkout depends on the abstraction Discount, not on FestivalDiscount; the low-level rules depend on the same abstraction, and the concrete one is injected from outside. It also helps Single Responsibility: each rule has one reason to change.
07Strategy vs Template Method?
I · Both vary part of an algorithm. Template Method uses inheritance: a base class fixes the steps and subclasses override some; the choice is fixed when you pick the subclass at compile time. Strategy uses composition: the whole varying algorithm is a separate object, swappable at run time and combinable. Prefer Strategy when variants must be mixed or switched; Template Method when the skeleton is fixed and only a few steps differ.
08When would you NOT use Strategy?
B · When there are two or three stable cases (a plain if / else or switch is clearer), when variants differ only by a value (use a parameter), or when nobody needs to swap or test the variants separately. Adding interfaces for change that never comes is over-engineering; refactor to Strategy when the third variant arrives or when you need a fake in a test.
09Can strategies be shared between threads or be singletons?
A · Stateless strategies can: one instance for the whole application (Spring singleton beans, enum constants, static lambdas) is safe and avoids allocation. A strategy with mutable fields is not safe to share; make it immutable, create one per use, or synchronise. Watch the context too: a setStrategy on an object shared by threads is a race, so prefer a final field and a new context per request.

8 takeaways

  • Strategy: one interface for a job, one class per way of doing it, and a context that delegates to the one it holds.
  • Client = who uses and chooses; Context = Checkout; Strategy = Discount; ConcreteStrategy = each offer.
  • The smell: a growing if / else on a type code (an offer name) inside a class that should not care.
  • Refactor in small steps: interface, one class per branch, field of the interface type, client chooses; run after each step.
  • A new rule is a new class: Open / Closed and Dependency Inversion in action; each rule tests alone.
  • Strategy vs State: the client chooses vs the object switches itself. Strategy vs Template Method: composition vs inheritance.
  • Modern Java: a one-method strategy is a functional interface (lambdas, method references); records for rules with data; maps, enums or Spring DI to choose by name.
  • Don't use it for two stable cases; an if / else is simpler.
