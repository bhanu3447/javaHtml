    I1Core Java & OOP

    MustJava languageabout 120 min8 questions
    In 30 seconds Java is pass-by-value. Overloading binds at compile time and overriding at runtime on the object. Prefer composition, use interfaces for capabilities and abstract classes for shared state and a template flow. Build immutable types with a final class, final fields and defensive copies, or with records.

    What interviewers test at 3–4 years

    • Can you explain the four pillars with your own example, not a textbook line?
    • Overloading vs overriding, and which one is decided at runtime
    • Abstract class vs interface after Java 8 (default and static methods)
    • Pass-by-value, static vs instance, final, and object initialisation order

    Concepts: how it works inside

    JDK, JRE, JVM

    JDK = compiler (javac) + tools + JRE. JRE = JVM + class libraries. JVM loads bytecode, verifies it, interprets it, and JIT-compiles hot methods to native code. Since Java 11 there is no separate JRE download; you ship a JDK or a jlink runtime.

    Encapsulation

    Hide state behind methods so the object protects its own invariants. A BankAccount exposes withdraw(amount), which checks the balance, rather than a public balance field.

    Inheritance vs composition

    Inheritance is an is-a link and couples you to the parent's internals. Prefer composition (has-a) and delegate. Use inheritance for real type hierarchies you control.

    Polymorphism

    Compile-time: overloading, picked by the reference types of the arguments. Runtime: overriding, picked by the actual object through the virtual method table. Static, private and final methods are not overridden.

    Abstraction

    Abstract class: shared state, constructors, and partial implementation. A class extends only one. Interface: a capability contract, with default, static and private methods since Java 8/9. A class implements many. If two defaults clash, the class must override.

    Pass-by-value

    Java always copies the value. For objects the value is the reference, so a method can mutate the object but cannot make the caller's variable point somewhere else.

    Interview questions

    Answer out loud first, then open the model answer. All of them are also in the mock interview.

    1Overloading vs overriding?

    Overloading: same name, different parameter list, resolved by the compiler. Overriding: same signature in a subclass, resolved at runtime on the real object. The return type may be covariant, access cannot be narrowed, and the method cannot throw broader checked exceptions.

    Say this: Overloading is decided at compile time from reference types; overriding at runtime from the object, through the vtable.

    2Can we override a static or private method?

    No. A static method with the same signature in a subclass hides the parent's; the call binds to the reference type. Private methods are not inherited, so a same-named method in the child is a new method.

    Say this: Static methods are hidden, not overridden; private ones aren't visible to override.

    3Abstract class vs interface: when do you pick which?

    Interface for a capability several unrelated classes share (Comparable, PaymentGateway). Abstract class for a family that shares state or a template algorithm (a BaseExporter with a fixed export flow and one abstract step).

    Say this: Interface for what it can do, abstract class for what it is plus shared code.

    4Why is multiple inheritance of classes not allowed?

    The diamond problem: two parents with the same method and state leave the JVM unable to choose. Interfaces allow it for behaviour only, and a default-method conflict must be resolved explicitly with A.super.m().

    Say this: Diamond ambiguity for state; interfaces allow it but force you to resolve default conflicts.

    5What is the initialisation order of a class?

    Parent static blocks, then child static blocks (once, at class load). Then, per object: parent instance initialisers and constructor, then child instance initialisers and constructor.

    Say this: Static parent, static child, then instance parent, constructor parent, instance child, constructor child.

    6Is Java pass-by-reference?

    No, always pass-by-value. void reset(List<String> l){ l = new ArrayList<>(); } doesn't affect the caller, but l.clear() does, because both copies point to the same object.

    Say this: Java passes a copy of the reference: you can change the object, not the caller's variable.

    7What does final mean on a class, a method, and a variable?

    Class: cannot be extended (String). Method: cannot be overridden. Variable: assigned once. A final reference to a mutable object still allows mutation, so final doesn't make an object immutable.

    Say this: final fixes the reference, not the object's contents.

    8How do you make a class immutable?

    Make the class final, the fields private final, add no setters, defensively copy mutable inputs and outputs (List.copyOf), and don't let this escape in the constructor. Records do most of this, but still copy any list components.

    Say this: Final class, final fields, no setters, defensive copies; a record plus List.copyOf does most of it.

    Traps: sounds right, but is wrong

    Sounds rightActually
    “Overloading is runtime polymorphism”Overloading is resolved at compile time. Only overriding is runtime.
    “final makes the object immutable”final freezes the reference. The object it points to can still change.
    “Interfaces can't have method bodies”They can since Java 8 (default and static) and Java 9 (private).
    “Java passes objects by reference”It passes a copy of the reference. Reassigning the parameter does nothing to the caller.
    “Constructors are inherited”They are not. A subclass must call super(...), implicitly or explicitly.

    I2Strings, equals & hashCode

    MustJava languageabout 60 min7 questions
    In 30 seconds Strings are immutable, pooled and hash-cached. == checks identity and equals checks content. Use StringBuilder for building strings in loops. equals and hashCode go together, and breaking the pair breaks every hash-based collection.

    What interviewers test at 3–4 years

    • Why String is immutable, and what the String pool is
    • == vs equals, and how many objects new String("x") creates
    • String vs StringBuilder vs StringBuffer
    • The equals/hashCode contract and what breaks when you violate it

    Concepts: how it works inside

    String pool

    Literals are interned in the String Constant Pool, which has lived on the heap since Java 7. The same literal reuses one object. new String("x") always creates a new heap object (plus the pooled literal if it isn't there yet).

    Why immutable

    Safe sharing in the pool, thread safety, a cached hashCode (great for HashMap keys), and security: file paths, URLs and class names can't be changed after validation.

    Builder vs Buffer

    StringBuilder is mutable and unsynchronized, so use it for local string building. StringBuffer is synchronized and legacy. Concatenating with + in a loop creates garbage, so use a builder.

    equals/hashCode contract

    If a.equals(b) then a.hashCode() == b.hashCode(). The reverse need not hold (collisions). equals must be reflexive, symmetric, transitive and consistent. Override both or neither.

    Compact Strings (Java 9+)

    A String stores a byte[] plus a coder flag. Latin-1 text uses 1 byte per char, otherwise UTF-16. That cuts memory for typical text about in half.

    Interview questions

    Answer out loud first, then open the model answer. All of them are also in the mock interview.

    1How many objects does String s = new String("hello") create?

    Up to two: the literal "hello" in the pool (if it isn't already there, created at class load) and one new object on the heap that s points to.

    Say this: One pooled literal if it's new, plus one heap object every time.

    2Why is String immutable?

    For pooling (sharing is only safe if nothing can change), thread safety without locks, a cached hash for map keys, and security, so a validated path or URL can't be mutated afterwards.

    Say this: Pooling, thread safety, cached hash, security.

    3== vs equals for Strings?

    == compares references. equals compares characters. Two equal literals are usually == because of the pool, but runtime-built strings are not. Always use equals, and use "x".equals(s) or Objects.equals to stay null-safe.

    Say this: == is identity, equals is content; never rely on the pool.

    4What happens if you override equals but not hashCode?

    Two equal keys land in different buckets, so map.get(equalKey) returns null and a HashSet keeps duplicates. The demo in Collections shows exactly this.

    Say this: Equal objects hash to different buckets, so lookups miss and sets keep duplicates.

    5Why is String a popular HashMap key?

    It's immutable, so its hash can't change while it's in the map, and the hash is computed once and cached in a field.

    Say this: Immutable and hash cached, so the bucket never goes stale.

    6When would you call intern()?

    Rarely: to dedupe many repeated runtime strings (codes read from a file). G1's -XX:+UseStringDeduplication is usually the better, automatic option.

    Say this: Almost never by hand; G1 string dedup does it automatically.

    7StringBuilder capacity growth?

    Default capacity is 16. When it fills, the new capacity is (old × 2) + 2, and the array is copied. Presize with new StringBuilder(expected) in hot loops.

    Say this: Grows to about double plus 2 with an array copy; presize when you know the size.

    Traps: sounds right, but is wrong

    Sounds rightActually
    “s1 == s2 works for equal strings”Only for pooled or constant strings. Runtime concatenation gives a different object.
    “StringBuffer is faster because it's newer”It's older and synchronized. StringBuilder is the default.
    “Equal hashCodes mean equal objects”Collisions are allowed. Only equal objects must have equal hashes.
    “The String pool is in PermGen”It moved to the heap in Java 7, and PermGen was removed in Java 8.
    “Using + in a loop is fine”Each iteration allocates a new String. Use StringBuilder.

    I3Exception Handling

    HighJava languageabout 45 min7 questions
    In 30 seconds Errors are for the JVM, checked exceptions for recoverable conditions, unchecked for bugs. Use try-with-resources and know suppressed exceptions. Never return from finally. In Spring, throw domain exceptions and translate them once in @RestControllerAdvice.

    What interviewers test at 3–4 years

    • Checked vs unchecked, and why Spring prefers unchecked
    • try-with-resources and suppressed exceptions
    • finally semantics and the return-in-finally trap
    • How you design a custom exception hierarchy and map it to HTTP

    Concepts: how it works inside

    Hierarchy

    Throwable → Error (JVM problems such as OOM and StackOverflow: don't catch) and Exception. RuntimeException and its subclasses are unchecked; every other Exception is checked.

    Checked vs unchecked

    Checked exceptions are recoverable conditions the caller must handle or declare (IOException). Unchecked ones are programming errors or failures that can't be fixed locally (NullPointerException, IllegalArgumentException).

    try-with-resources

    Any AutoCloseable is closed automatically in reverse order. If close throws while the body already threw, the close exception is added as suppressed instead of hiding the real one.

    Best practices

    Catch the narrowest type, never swallow, wrap with the cause (new XException(msg, e)), log once at the boundary, and don't use exceptions for normal control flow.

    In Spring

    Throw domain exceptions such as OrderNotFoundException from services and translate them centrally with @RestControllerAdvice into ProblemDetail (RFC 7807/9457) responses.

    Interview questions

    Answer out loud first, then open the model answer. All of them are also in the mock interview.

    1Checked vs unchecked exceptions?

    Checked exceptions extend Exception (not RuntimeException) and must be caught or declared. Unchecked ones extend RuntimeException. Use checked for recoverable conditions the caller can act on, and unchecked for bugs and failures that can't be fixed locally.

    Say this: Checked forces the caller to handle it; unchecked signals bugs or unrecoverable failures.

    2Does finally always run?

    Almost always: after a return, after an exception, after break. It doesn't run on System.exit(), if the JVM crashes or is killed, or in a daemon thread at JVM shutdown.

    Say this: Yes, except System.exit, a JVM crash or kill, or an abandoned daemon thread.

    3What if both try and finally return a value?

    The finally's return wins and silently discards the try's value and any exception in flight. That's why returning from finally is a code smell.

    Say this: finally's return overrides everything, including exceptions, so never return from finally.

    4What are suppressed exceptions?

    In try-with-resources, if the body throws and then close() throws too, the close exception is attached to the primary one via addSuppressed. You read it with getSuppressed().

    Say this: Secondary close failures ride along on the main exception.

    5throw vs throws?

    throw raises an exception instance inside a method body. throws in a signature declares the checked exceptions the method may propagate.

    Say this: throw does it; throws declares it.

    6Overriding rules for exceptions?

    An overriding method may throw fewer or narrower checked exceptions, never broader or new checked ones. Unchecked exceptions are unrestricted.

    Say this: Narrower or fewer checked exceptions only.

    7How do you handle exceptions in a REST API?

    Domain exceptions from services, one @RestControllerAdvice mapping them to status codes (404, 409, 422), a consistent error body with ProblemDetail, a correlation id, and no stack traces leaked to clients.

    Say this: Central advice, consistent problem body, correct status, no stack traces.

    Traps: sounds right, but is wrong

    Sounds rightActually
    “catch (Exception e) {} is fine for now”Swallowing hides failures. Log with context or rethrow wrapped.
    “Catch Throwable to be safe”It catches OutOfMemoryError and other JVM errors you can't recover from.
    “finally runs even after System.exit”It doesn't. The JVM halts.
    “@Transactional rolls back on any exception”By default only RuntimeException and Error. Checked exceptions commit unless you set rollbackFor.
    “Custom exceptions should extend Exception”In Spring apps extend RuntimeException, so you don't pollute every signature.

    I4Collections Internals

    MustJava languageabout 150 min8 questions
    In 30 seconds HashMap: spread hash, index = hash & (n-1), equals in the bin, resize at 0.75 by doubling, treeify at 8 with a table of at least 64. ConcurrentHashMap: CAS plus a per-bin lock, lock-free reads, no nulls. Use ArrayList and ArrayDeque by default, TreeMap for order, LinkedHashMap for LRU, and immutable keys always.

    What interviewers test at 3–4 years

    • HashMap internals: hashing, bucket index, collisions, resize, treeify
    • ArrayList vs LinkedList, HashSet internals, TreeMap ordering
    • ConcurrentHashMap vs Hashtable vs synchronizedMap
    • Fail-fast vs fail-safe iterators, Comparable vs Comparator, an LRU cache

    Concepts: how it works inside

    HashMap put()

    hash = h ^ (h >>> 16) mixes high bits into low ones, then index = hash & (n-1) (n is a power of two). An empty bucket stores the node. Otherwise it walks the bin, and if equals matches it replaces the value, else appends at the tail.

    Resize and treeify

    Default capacity 16, load factor 0.75, so it resizes after 12 entries by doubling. Each node either stays at index i or moves to i + oldCap, depending on one hash bit. A bin with 8 or more nodes becomes a red-black tree if the table has at least 64 slots (otherwise the table resizes), and turns back into a list at 6.

    Lists

    ArrayList: backing array, O(1) get, amortised O(1) add, grows 1.5×. LinkedList: O(1) insert at a known node but O(n) get and poor cache locality. In practice ArrayList (or ArrayDeque for queues) wins.

    Sets and sorted maps

    HashSet is a HashMap with a dummy value. LinkedHashSet/Map keep insertion (or access) order. TreeMap is a red-black tree, O(log n), sorted, with floorKey, ceilingKey and headMap.

    Concurrent maps

    Hashtable and synchronizedMap lock the whole map. ConcurrentHashMap (Java 8+) uses CAS for an empty bin and synchronized on the bin head otherwise, so reads are lock-free. It allows no null keys or values, and its iterators are weakly consistent.

    Iterators

    Fail-fast iterators (ArrayList, HashMap) check modCount and throw ConcurrentModificationException. Fail-safe or weakly consistent ones (CopyOnWriteArrayList, CHM) don't throw. Use removeIf or Iterator.remove().

    Interview questions

    Answer out loud first, then open the model answer. All of them are also in the mock interview.

    1How does HashMap work internally?

    It's an array of bins. put computes a spread hash, the index is hash & (n-1), and on a collision it chains nodes. Lookups compare the hash first, then equals. At size > 0.75 × capacity it doubles, and long chains (8 or more, table at least 64) become red-black trees, so the worst case is O(log n), not O(n).

    Say this: Array of bins, index = hash & (n-1), equals resolves collisions, resize at 0.75, treeify at 8.

    2Why is the capacity always a power of two?

    So hash & (n-1) equals hash % n but is cheaper, and on resize each node goes either to i or to i + oldCap based on a single bit, with no full rehash.

    Say this: Bitmask instead of modulo, and a cheap split on resize.

    3What happens when two keys have the same hashCode?

    They land in the same bin. HashMap walks the bin comparing equals. Different keys coexist as a chain or tree. Performance drops if many keys collide, which is why a good hashCode matters.

    Say this: Same bin, equals tells them apart; too many collisions hurt performance.

    4Can a HashMap have a null key?

    Yes, one null key, stored in bin 0 because its hash is treated as 0, and many null values. ConcurrentHashMap and Hashtable allow neither, because in a concurrent map get returning null would be ambiguous.

    Say this: HashMap allows one null key; CHM forbids nulls because null would be ambiguous.

    5How does ConcurrentHashMap achieve thread safety?

    Java 8+: no segments. It CASes a new node into an empty bin and synchronizes on the first node of a non-empty bin, so only that bin is locked. Reads use volatile reads and never lock. Resizing is done cooperatively by several threads. Use compute or merge for atomic read-modify-write.

    Say this: CAS on empty bins, per-bin lock otherwise, lock-free reads; use merge or compute for atomic updates.

    6What happens if you mutate a key after putting it in a HashMap?

    Its hashCode changes, so lookups go to a different bin and the entry becomes unreachable: a memory leak plus wrong results. Keys should be immutable (String, records, enums).

    Say this: The entry is lost in its old bin; keys must be immutable.

    7Comparable vs Comparator?

    Comparable is the natural order inside the class (compareTo). Comparator is an external, pluggable order: Comparator.comparing(Employee::dept).thenComparing(Employee::salary, reverseOrder()).

    Say this: Comparable is the one natural order; Comparator gives as many external orders as you need.

    8How would you build an LRU cache?

    Extend LinkedHashMap with accessOrder=true and override removeEldestEntry to return size() > capacity. To build it from scratch: a HashMap plus a doubly linked list, O(1) get and put. For concurrency use Caffeine.

    Say this: LinkedHashMap in access order plus removeEldestEntry, or a HashMap with a doubly linked list.

    Traps: sounds right, but is wrong

    Sounds rightActually
    “HashMap worst case is O(n)”Since Java 8 a treeified bin gives O(log n), assuming comparable keys or tie-breaking.
    “Hashtable and ConcurrentHashMap are the same”Hashtable locks the whole table. CHM locks per bin and reads lock-free.
    “LinkedList is faster for inserts”Only once you hold the node. Finding the position is O(n), and the memory overhead is high.
    “Collections.unmodifiableList is immutable”It's a read-only view. Changes to the backing list show through. Use List.copyOf.
    “Iterator on CHM throws ConcurrentModificationException”CHM iterators are weakly consistent and never throw it.

    I5Java 8 → 21 Features

    MustJava languageabout 120 min8 questions
    In 30 seconds Lambdas implement functional interfaces. Streams are lazy pipelines that run on the terminal op, with groupingBy for most interview questions and toMap needing a merge function. Use Optional only as a return type. From modern Java: records, sealed types with exhaustive switch, pattern matching and virtual threads.

    What interviewers test at 3–4 years

    • Lambdas, functional interfaces and method references
    • The Stream API: lazy evaluation, collectors, groupingBy, flatMap; live coding
    • Optional done right
    • What you use from 11/17/21: records, sealed types, switch patterns, virtual threads

    Concepts: how it works inside

    Functional interfaces

    One abstract method: Function<T,R>, Predicate<T>, Supplier<T>, Consumer<T>, BiFunction, UnaryOperator. Lambdas capture effectively-final locals only.

    Streams are lazy

    Intermediate ops (filter, map, sorted) build a pipeline. Nothing runs until a terminal op (collect, findFirst, count). Elements flow one at a time, and short-circuit ops stop early. A stream can be consumed only once.

    Collectors

    groupingBy, partitioningBy, counting, averagingDouble, toMap (needs a merge fn for duplicate keys!), joining, collectingAndThen, teeing (12).

    Optional

    A return type for "maybe no result". Use map, orElse, orElseThrow. Don't use it for fields, parameters or collections, and never call get() without a check.

    Modern Java (17 and 21 LTS)

    var (10), text blocks (15), records (16), pattern matching for instanceof (16), sealed classes (17), switch patterns and record patterns (21), virtual threads (21), sequenced collections (21).

    1map vs flatMap?

    MustJava languageabout 180 min9 questions
    In 30 seconds Know the six thread states. synchronized gives atomicity and visibility; volatile gives only visibility. Pools run core, then queue, then max, then reject, so bound your queues. Use CompletableFuture with your own executor and timeouts. Prevent deadlocks with lock ordering or tryLock. Virtual threads are for I/O-bound concurrency.

    Concepts: how it works inside

    Race condition

    count++ is read, add, write: three steps. Two threads interleave and lose updates (the demo below loses thousands of the 400,000). Fix it with synchronized, a Lock, or AtomicInteger/LongAdder.

    synchronized vs volatile

    synchronized gives mutual exclusion and visibility (a happens-before edge on unlock/lock). volatile gives only visibility and ordering, with no atomicity: use it for flags such as running = false.

    ThreadPoolExecutor

    New task: if threads < core, start a thread. Else queue it. If the queue is full and threads < max, start a thread. Else reject (AbortPolicy by default). newFixedThreadPool uses an unbounded queue, so it can grow until OOM. Define bounded pools in production.

    CompletableFuture

    supplyAsync → thenApply (sync map) / thenCompose (flatMap async) / thenCombine (join two) / allOf. Handle failures with exceptionally or handle, and set orTimeout. Pass your own executor for I/O.

    Locks and deadlock

    A deadlock needs mutual exclusion, hold-and-wait, no preemption, and a circular wait. Prevent it with a global lock order or with tryLock(timeout). ReentrantLock adds tryLock, fairness and Conditions. ReadWriteLock lets many readers in at once.

    Virtual threads (21)

    Cheap JVM-scheduled threads that unmount from the carrier thread while they block on I/O. One thread per request scales to millions. They suit I/O-bound work, not CPU-bound work. Don't pool them. In Boot 3.2+ set spring.threads.virtual.enabled=true.

    I7JVM Internals & GC

    HighJava languageabout 90 min7 questions
    In 30 seconds Heap (young and old) plus Metaspace are shared; stacks are per thread. GC traces reachability from roots, collects the young generation often and promotes survivors. G1 is the default, ZGC for low latency. Delegation is parent first. For leaks: heap dump, MAT dominator tree, then follow the GC root path.

    What interviewers test at 3–4 years

    • JVM memory areas and which errors each one throws
    • How generational garbage collection works; G1 vs ZGC
    • Class loading and parent delegation

    Concepts: how it works inside

    Memory areas

    Heap (objects, String pool; shared): Young (Eden + two Survivors) and Old. Metaspace (class metadata, native memory, since Java 8). Stack per thread (frames, locals, references). PC register and native method stack.

    Generational GC

    Most objects die young. Minor GC copies the live objects from Eden and one survivor into the other survivor and increments their age. Objects past the tenuring threshold (default up to 15) are promoted to Old. Major or mixed collections clean Old.

    Collectors

    G1 (default since 9): region-based, with pause-time goals (-XX:MaxGCPauseMillis=200). ZGC (generational in 21+): sub-millisecond pauses on huge heaps. Parallel: throughput for batch jobs. Serial: tiny heaps.

    Class loading

    Bootstrap → Platform → Application loader. Parent-first delegation: a loader asks its parent before loading, so java.lang.String can't be spoofed. The phases are load, link (verify, prepare, resolve), then initialise (static blocks).

    JIT

    The interpreter starts the code, and hot methods are compiled by C1, then C2 (tiered compilation) with inlining and escape analysis. That's why the first requests after a deploy are slower (warm-up).

    Diagnosing

    OOM: start with -XX:+HeapDumpOnOutOfMemoryError, then analyse the dump in Eclipse MAT (dominator tree). High CPU: top -H → thread id → jstack. Continuous profiling: JFR plus JMC. GC logs: -Xlog:gc*.

    Each transaction has a first-level cache: the same id returns the same instance. Changes to managed entities are flushed automatically at commit (dirty checking), so no save() is needed for updates.

    Entity states

    Rollback by default only on unchecked exceptions and Errors. Use rollbackFor = Exception.class for checked ones. Catching an exception inside the method means no rollback. readOnly = true skips dirty checking, a speed-up for queries.

    Locking

    Optimistic: a @Version column; an update with a stale version throws OptimisticLockException; best for low contention. Pessimistic: @Lock(PESSIMISTIC_WRITE) → SELECT … FOR UPDATE; for hot rows like stock counts.

    I13Kafka & Messaging

    HighDistributed systemsabout 90 min7 questions
    In 30 seconds Partitions are the unit of order and parallelism, so key by the entity that needs ordering. One partition goes to one consumer per group. The practical default is at-least-once with idempotent consumers. Retry with backoff, then a DLT. Producers use acks=all with idempotence. Kafka is a log, not a queue.

    What interviewers test at 3–4 years

    • Topic, partition, offset, consumer group: how scaling and ordering work
    • Delivery semantics: at-most-once, at-least-once, exactly-once
    • Retries, dead-letter topics and idempotent consumers
    • Kafka vs RabbitMQ; producer acks

    Concepts: how it works inside

    Model

    A topic is split into partitions, each an append-only log with offsets. Messages with the same key go to the same partition (murmur2(key) % partitions), so ordering is per key. Replicas give fault tolerance (leader + ISR).

    Consumer groups

    Each partition is consumed by exactly one consumer in a group. Parallelism is therefore at most the partition count, and extra consumers sit idle. Different groups each get all messages (pub-sub). Adding or removing a consumer triggers a rebalance.

    Offsets and delivery

    Commit after processing = at-least-once (duplicates possible, so make consumers idempotent). Commit before = at-most-once (can lose messages). Exactly-once within Kafka uses an idempotent producer plus transactions and read_committed consumers.

    Producer settings

    acks=all + min.insync.replicas=2 for durability. Idempotence is on by default (Kafka 3.0+), which dedupes retries per partition. linger.ms/batch.size trade latency for throughput.

    Error handling

    Spring Kafka's DefaultErrorHandler retries with backoff, then publishes to a dead-letter topic (orders.DLT). Non-blocking retries use @RetryableTopic (retry topics). Poison messages must never block a partition forever.

    Concepts: how it works inside

    Indexes

    B-tree indexes give O(log n) lookups and range scans. A composite (customer_id, created_at) serves filters on customer_id, or customer_id + created_at, but not created_at alone (leftmost prefix). Covering index: all needed columns are in the index (INCLUDE). Each index slows writes down.

    Clustered vs non-clustered

    SQL Server and MySQL InnoDB store the table ordered by the clustered key (usually the PK). Secondary indexes point to that key. PostgreSQL tables are heaps; every index points to a tuple location.

    Isolation levels

    READ UNCOMMITTED (dirty reads) < READ COMMITTED (non-repeatable reads, phantoms) < REPEATABLE READ (phantoms per the standard) < SERIALIZABLE. Defaults: PostgreSQL and SQL Server: READ COMMITTED (SQL Server locks unless RCSI is on). MySQL InnoDB: REPEATABLE READ.

    Window functions

    ROW_NUMBER(), RANK(), DENSE_RANK(), LAG/LEAD, and running totals with SUM() OVER (ORDER BY …). They compute per row without collapsing like GROUP BY does.

    Normalisation

    1NF atomic values, 2NF no partial dependency on a composite key, 3NF no transitive dependency. Denormalise deliberately for read-heavy paths (reporting tables, cached counts), with a plan to keep them in sync.

    HighDataabout 60 min6 questions
    In 30 seconds Cache-aside: read through the cache with a TTL, write the DB then evict. Guard against stampede (single-flight), penetration (null caching or Bloom filter) and avalanche (jitter).     Concepts: how it works inside

    Cache-aside

    Read: check the cache, on a miss load from the DB and put it in the cache with a TTL. Write: update the DB, then delete the cache key (don't update it, which races). Most common, and it tolerates cache downtime.

    Other strategies

    Write-through: write the cache and DB together. Write-behind: write the cache, flush to the DB later (fast, risky). Read-through: the cache loads itself. Choose by consistency needs.

    Failure modes

    Stampede: a hot key expires and 1000 requests hit the DB. Fix with a lock or single-flight (@Cacheable(sync = true)), early refresh, or jittered TTLs. Penetration: requests for missing ids; cache nulls briefly or use a Bloom filter. Avalanche: many keys expire together; jitter the TTLs.

    Redis

    In-memory, single-threaded command execution (atomic commands), with data types string, hash, list, set, sorted set (leaderboards), stream, and HyperLogLog. Persistence via RDB snapshots or AOF. Uses: cache, sessions, rate limiting (INCR + EXPIRE), distributed locks (SET key val NX PX 30000 / Redisson), pub/sub.

    Two-level caching

    Caffeine local (microseconds, per instance) in front of Redis (shared, about 1 ms). Local caches go stale across instances, so keep TTLs short or broadcast invalidations.

    Unit-test the handler logic directly. For an integration test, use Testcontainers Kafka (or EmbeddedKafka), produce a message, and assert with Awaitility that the DB state changed. Test that duplicates are ignored and poison messages go to the DLT.

    I17DSA: The Coding Round

    MustProblem solvingabout 240 min8 questions
    In 30 seconds Clarify, match the pattern, state the brute force, optimise, code cleanly, dry-run, and state Big-O, talking throughout. Drill the 15–20 most-asked problems until the pattern is automatic, and know the Java collections toolkit cold.

    What interviewers test at 3–4 years

    • Arrays, strings, hashing: one or two medium problems in 45 minutes
    • Recognising the pattern: two pointers, sliding window, stack, heap, binary search, BFS/DFS
    • Stating time and space complexity and improving brute force
    • Clean Java: collections API, edge cases, naming, talking while coding

    Concepts: how it works inside

    Approach (UMPIRE)

    Understand (ask about constraints and edge cases) → Match a pattern → Plan (say the brute force, then optimise) → Implement → Review (dry run) → Evaluate (Big-O). Talk the whole time.

    Pattern → signal

    Pair or sum lookup → HashMap. Sorted array, pairs → two pointers. Longest or shortest substring or subarray → sliding window. Matching brackets, next greater → stack. Top K → heap. Sorted or monotonic answer → binary search. Grid, levels, shortest path → BFS. Combinations → backtracking. Overlapping subproblems → DP.

    Complexity budget

    About 10⁸ simple ops per second. n ≤ 10⁵ needs O(n log n) or better; n ≤ 10³ allows O(n²); n ≤ 20 allows O(2ⁿ).

    Java toolkit

    HashMap.merge, getOrDefault, ArrayDeque (stack and queue), PriorityQueue with a comparator, Arrays.sort, Collections.reverse, StringBuilder, Character.isLetterOrDigit, int[26] counters, and lo + (hi - lo) / 2.

    Most-asked list (3–4 yrs)

    Two sum, valid parentheses, longest substring without repeats, anagram grouping, top-K frequent, merge intervals, kth largest, LRU cache, reverse a linked list, detect a cycle, level-order traversal, number of islands, binary search variants, move zeros, product except self, max subarray (Kadane), first non-repeating char.

    1Reverse a linked list.

    Iteratively: prev = null; while (cur != null) { next = cur.next; cur.next = prev; prev = cur; cur = next; } return prev;. O(n) time, O(1) space. The recursive version uses O(n) stack.

    Say this: Three pointers: prev, cur, next; O(n) time, O(1) space.

    2Detect a cycle in a linked list.

    Floyd's tortoise and hare: slow moves 1 step, fast moves 2; if they meet there's a cycle. To find the start, reset one pointer to head and move both 1 step until they meet. O(n) time, O(1) space.

    Say this: Fast and slow pointers; reset to head to find the entry.

    3Merge overlapping intervals.

    Sort by start. Walk through, and if the current start ≤ the last end, extend the end with max; otherwise add a new interval. O(n log n).

    Say this: Sort by start, then extend or append.

    4Maximum subarray sum.

    Kadane: cur = max(x, cur + x); best = max(best, cur). O(n), O(1). If all values are negative it returns the largest single value.

    Say this: Kadane: extend or restart at each element.

    5First non-repeating character.

    Count with int[256] or a LinkedHashMap, then scan the string again for the first count of 1. O(n) time, O(1) space for a fixed alphabet.

    Say this: Count, then a second pass for the first count of 1.

    6Number of islands.

    Scan the grid; on each unvisited '1', increment the count and flood-fill (DFS or BFS) to mark the whole island. O(rows × cols). Mention the recursion depth and use BFS with ArrayDeque for big grids.

    Say this: Count each flood fill; BFS avoids deep recursion.

    7Kth largest element.

    A min-heap of size k: offer each element and poll when size > k, so the root is the answer. O(n log k). Quickselect averages O(n) with an O(n²) worst case.

    Say this: Size-k min-heap, O(n log k), or quickselect.

    8Product of array except self without division.

    Prefix products left to right into the result array, then multiply by a running suffix product right to left. O(n) time, O(1) extra space.

    Say this: Prefix pass, then suffix pass.

    Traps: sounds right, but is wrong

    Sounds rightActually
    “Jump straight into coding”Clarify inputs and constraints and state the brute force first. Interviewers grade the process.
    “(lo + hi) / 2 is fine”It can overflow. Use lo + (hi - lo) / 2.
    “Use Stack and Vector”Use ArrayDeque, which is faster and not synchronised.
    “== to compare Integer values from a map”It's false above 127 (Integer cache). Use equals or unbox.
    “Recursion is always fine”Deep inputs cause StackOverflowError. Iterate or use an explicit stack.

    I18System Design (LLD + HLD)

    HighProblem solvingabout 150 min7 questions
    In 30 seconds Requirements, estimates, API, data model, diagram, deep-dive, trade-offs. Scale reads with caches and replicas, absorb spikes with queues, partition by key. A rate limiter is a token bucket in Redis at the gateway. A URL shortener is counter + Base62 plus a cache. For LLD: clear entities plus strategies (SOLID).

    What interviewers test at 3–4 years

    • LLD: model classes for a parking lot, a library or a rate limiter, with SOLID
    • HLD: URL shortener, notification service, rate limiter, at a 3–4 year level
    • Back-of-envelope estimates, scaling reads and writes, caching, partitioning
    • Trade-offs: SQL vs NoSQL, consistency vs availability

    Concepts: how it works inside

    Framework (45 min)

    1. Requirements, functional and non-functional (QPS, latency, availability) → 2. Estimates → 3. API → 4. Data model → 5. High-level diagram → 6. Deep-dive on 1–2 parts → 7. Bottlenecks, failure and trade-offs.

    Scaling toolkit

    Stateless app servers behind a load balancer. Cache (Redis) for hot reads, read replicas, partitioning or sharding by key, a CDN for static content, queues (Kafka) to absorb spikes and decouple, and idempotency for retries.

    CAP in practice

    During a network partition you choose consistency (reject or stall) or availability (serve possibly stale data). Payments lean CP; feeds and counters lean AP with eventual consistency.

    Rate limiter

    Token bucket (bursts allowed, smooth average), leaky bucket, fixed window (boundary burst), sliding window log or counter. Distributed: Redis INCR with EXPIRE or a Lua script, keyed per user or API key. Return 429 with Retry-After.

    URL shortener

    Writes are rare, reads are hot. Generate an id with a counter or Snowflake and Base62-encode it (7 chars ≈ 3.5 trillion). The table is code → long_url. Cache hot codes and return 301/302. Analytics go async through Kafka.

    1Design a URL shortener.

    Requirements: shorten and redirect, about 100:1 read-heavy, low latency. ID: a distributed counter or Snowflake, Base62 to 7 chars, which avoids collisions (unlike hashing).     2Design a rate limiter for an API.

    Where: at the gateway. Algorithm: token bucket per user (it allows short bursts). State: Redis with an atomic Lua script (refill + take), keys with a TTL. Response: 429 + Retry-After + X-RateLimit headers. Fail open or closed by endpoint risk. Local buckets plus periodic sync if Redis latency matters.

    Say this: Token bucket in Redis via Lua at the gateway; 429 with Retry-After.

    3Design a notification service (email/SMS/push).

    An API accepts the request → validate and store → publish to Kafka per channel → channel workers call providers with retries and backoff, then a DLT. Templates and user preferences, idempotency key per notification, rate limits per user, a status table for delivery tracking, provider fallback.

    Say this: Queue per channel, idempotent workers, retries and DLT, preferences and status tracking.

    4LLD: design a parking lot.

    Entities: ParkingLot → Floor → Spot (type: bike, car, truck), Vehicle, Ticket, Payment. A SpotAllocationStrategy interface (nearest-first, by type) gives you open/closed. PricingStrategy per vehicle and duration. Thread safety on allocation (per-floor lock or atomic spot claim).

    Say this: Clear entities, strategies for allocation and pricing, safe concurrent allocation.

    5SQL or NoSQL for a new service?

    SQL when you need relationships, transactions, ad-hoc queries and strong consistency (orders, payments). NoSQL (document or key-value) for huge scale with simple access patterns, flexible schema, or very high write throughput. Many systems use both.

    Say this: SQL by default; NoSQL for scale with simple, known access patterns.

    6How do you scale a read-heavy service?

    Cache first (Redis plus HTTP caching or CDN), read replicas for the DB (handle replication lag: read-your-writes from the primary), denormalised read models (CQRS), indexes and pagination, then horizontal app scaling behind a load balancer.

    Say this: Cache, replicas, read models, then more stateless instances.

    7Estimate storage for 100M URLs a month for 5 years.

    100M × 12 × 5 = 6B rows. About 500 bytes each (URL + metadata) ≈ 3 TB, plus replication × 3 ≈ 9 TB. Writes: 100M / (30 × 86,400) ≈ 40/s; reads at 100× ≈ 4,000/s.

    Say this: Show the arithmetic: rows × bytes × replicas; QPS from monthly volume.

    Traps: sounds right, but is wrong

    Sounds rightActually
    “Start drawing boxes immediately”Clarify requirements and scale first. The design depends on them.
    “Use microservices for every design”Justify each split. A simple design that scales wins.
    “Hash the URL with MD5 for the code”It collides and is long. Counter + Base62 is simpler and unique.
    “Fixed window rate limiting is enough”It allows a 2× burst at window edges. Use a token bucket or sliding window.
    “Caching solves consistency”Caching adds staleness. State the TTL and invalidation plan.

    What interviewers test at 3–4 years

    Concepts: how it works inside

    Docker

    A multi-stage build: build with Maven/Gradle, run on a slim JRE base. Use layered jars (java -Djarmode=tools) for cache-friendly layers, run as non-root, and set memory via -XX:MaxRAMPercentage=75 (container aware).

    CI/CD

    On a PR: build → unit tests → static analysis (Sonar) → integration tests → image build and scan → deploy to dev/stage → smoke tests → manual or auto promote to prod (blue-green or canary). Trunk-based or GitFlow; small PRs.

    Production debugging

    Start from alerts and dashboards (error rate, p99 latency), find the trace, read the logs by traceId, check recent deploys and config changes, then thread or heap dumps if needed. Roll back first, root-cause second.

    1Liveness vs readiness probe?

    Liveness: is the process healthy? Failure → Kubernetes restarts the pod. Readiness: can it take traffic now (warmed up, dependencies OK)? Failure → removed from the Service endpoints, not restarted. Don't put DB checks in liveness, or a DB blip restarts everything.

    2How do you do zero-downtime deployment?

    A rolling update with readiness probes and maxUnavailable: 0, graceful shutdown (server.shutdown=graceful) so in-flight requests finish, backward-compatible DB migrations (expand → migrate → contract), or blue-green / canary with quick rollback.

    Say this: Rolling with readiness and graceful shutdown, plus backward-compatible migrations.

    3How do you size JVM memory in a container?

    Modern JDKs are container aware. Use -XX:MaxRAMPercentage=75 rather than a fixed -Xmx, and leave headroom for Metaspace, thread stacks, direct buffers and code cache. An OOMKilled pod means the total process exceeded the limit, not just the heap.

    Say this: MaxRAMPercentage around 75; OOMKilled means total memory, not only heap.

    4Walk me through debugging a latency spike in production.

    Check the dashboards: which endpoint, since when, and a correlated deploy? Open a slow trace to find the slow span (DB? downstream? GC?). Then the DB slow log and pool metrics (Hikari pending), GC logs, thread dumps for blocked threads. Mitigate first (rollback, scale, feature flag), then fix the root cause and write a post-mortem.

    Say this: Metrics, then trace, then the specific span; mitigate first, then root-cause.

    Traps: sounds right, but is wrong

    Sounds rightActually
    “Use -Xmx equal to the container limit”Non-heap memory pushes the process over the limit and it gets OOMKilled.
    “Liveness should check the database”A DB outage would restart every pod in a loop.
    “Logs are enough”You need metrics for alerting and traces to locate the hop.
    “latest tag in production”Pin versions or digests for reproducible rollbacks.
    “Run containers as root”Use a non-root user and a minimal base image.
