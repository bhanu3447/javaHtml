From "why not a spreadsheet?" to the five sublanguages

Seven sections, nine labs, two live editors, fifteen interview questions. Play the visuals first; the text around them is short on purpose and the depth is folded under "Go deeper". S1

Data, databases, and why not just files

In 30 seconds Data is raw facts ("Asha", "Nellore", 640000). A database is an organised collection of related data, stored so it can be found and changed safely. You could keep the same facts in files or spreadsheets, and small shops do, until many people use the data at once: copies disagree, edits overwrite each other, wrong values slip in, a crash corrupts a file, and anyone holding a copy sees everything. A database fixes all five.

💡 Remember itFiles are every salesperson keeping their own notebook about the same customer. A database is one register at the front desk: one entry per customer, one person writes at a time, the clerk refuses nonsense, and only staff with a key can open the salary page.
Go deeper: data vs information, and the exact words

Data = raw facts. Information = data given meaning ("Asha, from Nellore, spent ₹28.7 lakh with us in 2024"). The database is the stored data itself; the DBMS (database management system) is the software that manages it; a database system is the two together plus the applications that use them.

The five file-system problems have textbook names you will meet in interviews: data redundancy and inconsistency, concurrent-access anomalies (the lost update), integrity problems, atomicity problems (half-done work after a crash) and security problems. Also: data isolation (facts scattered in files of different formats) and difficulty accessing data (a new question needs a new program).

S2

What a DBMS does

In 30 seconds A DBMS is the program that owns the data. Everything goes through it: it stores the data on disk, answers queries, lets many users work at once (a lock makes the second writer of a row wait for the first; a transaction is a group of changes that all happen or none do), checks rules on every change, recovers after a crash, and enforces permissions. An RDBMS is a DBMS that stores data as related tables and speaks SQL: MySQL, PostgreSQL, Oracle, SQL Server, SQLite.

Go deeper: ACID in four lines

A transaction is a group of statements the database treats as one unit ("record the sale and mark the car sold"). ACID is the promise a relational database makes about it:

Atomicity: all of it happens or none of it (a crash halfway leaves nothing behind). Consistency: every rule (keys, CHECKs) holds before and after. Isolation: transactions running at the same time do not see each other's half-done work (how strictly is the isolation level). Durability: once COMMIT returns, the change survives a power cut, because it is already in the log on disk.

The race above is an isolation problem: each session's "read, then write" was correct alone and wrong together. The one-statement fix works because a single UPDATE re-checks in_stock = 1 on the row it changes, while it holds that row's write lock.

Go deeper: embedded vs client-server, and the three levels

Client-server databases (PostgreSQL, MySQL, SQL Server, Oracle) run as a separate server process; your app connects over the network, and many apps share one server. Embedded databases (SQLite, H2) are a library inside your program: no server, the database is one file. SQLite is the most deployed database in the world (every phone has dozens of SQLite files) and it is what runs on this page.

The classic three-schema architecture: the external level (what each user sees: views), the conceptual level (all tables, columns, keys: the schema) and the internal level (files, pages, indexes on disk). Data independence means you can change a lower level without breaking the one above: add an index (internal) and no query changes; add a column (conceptual) and existing views keep working.

Prepared statements and the plan cache. Parsing and optimizing cost time, so drivers let you send the SQL once with placeholders (SELECT … WHERE city = ?), then run it many times with different values. In most products the parsed (and often the planned) statement is reused, and because the value travels separately from the SQL text, it can never be read as SQL: this is also the standard defence against SQL injection (Lesson S11). In Java: PreparedStatement.

S3

Types of databases: SQL and NoSQL

In 30 seconds Relational (SQL) databases keep data in tables with a fixed structure and join them freely (a join reads matching rows from two tables in one query, such as a sale with its car; Lesson S06). NoSQL ("not only SQL") is everything else, each shaped for one kind of question: document (MongoDB: one JSON-like document per thing), key-value (Redis: look up by key, very fast), wide-column (Cassandra: massive writes across many machines), graph (Neo4j: relationships many hops deep), time-series (InfluxDB: readings over time). Choose by the questions you will ask.

Go deeper: is MongoDB SQL? NewSQL? and why big companies use several

MongoDB is not SQL. It is a document database with its own query language (db.cars.find({ price: { $gt: 1000000 } })) and an aggregation pipeline that plays the role of GROUP BY. It does support multi-document ACID transactions since version 4.0. Lesson S16 compares it side by side with SQL.

NewSQL systems (Google Spanner, CockroachDB, YugabyteDB, TiDB) keep SQL and ACID but scale horizontally like NoSQL. Search engines (Elasticsearch, OpenSearch) are another NoSQL family, built for full-text search.

Polyglot persistence: real systems mix them. An e-commerce site might keep orders in PostgreSQL, sessions in Redis, the product catalogue in MongoDB, search in Elasticsearch and analytics in BigQuery. In a system-design interview, say which store you pick and why (the access pattern), not just the name.

The line is blurring. PostgreSQL's JSONB column stores a binary JSON document inside a relational row, with indexes on its fields, so one database can hold strict tables and flexible documents. MySQL has a JSON type; SQL Server and Oracle have JSON functions too.

CAP: when the network between two copies of the data breaks (a partition), a distributed database must choose: refuse some requests to stay consistent (CP: Spanner, HBase), or answer from whichever copy it can reach and accept stale data for a while (AP: Cassandra and DynamoDB by default, eventually consistent). Without a partition you can have both. Interviewers also like PACELC: even with no partition, you trade latency against consistency.

Scaling SQL horizontally is possible, just not automatic: read replicas for read-heavy load; sharding (split rows across servers by a key such as customer_id; Vitess for MySQL, Citus for PostgreSQL); or a NewSQL database that shards for you. The cost is cross-shard joins and transactions. Lesson S15 goes deeper.

S4

Tables, rows, columns and keys

In 30 seconds A table holds one kind of thing. A row is one thing (one car), a column is one property every row has (price). The formal words: table = relation, row = tuple, column = attribute; the number of columns is the degree, the number of rows the cardinality, and the allowed values of a column its domain. A key is a column (or set of columns) whose value is different in every row, so it can point at exactly one row.

Go deeper: why most tables use surrogate keys, and NULL in UNIQUE columns

Natural keys read nicely but real-world values change (a licence is reissued, an email changes) and they are long, and every foreign key copies them. Most teams use a surrogate primary key (id, auto-generated) and put UNIQUE on the natural one, so duplicates are still refused.

A key is a rule about all possible data, not a fact about today's rows: two cars that happen to have different prices today do not make price a key. You decide keys from the meaning of the data.

NULL in a UNIQUE column differs by product: PostgreSQL, MySQL, Oracle and SQLite allow many NULLs (NULL is not equal to NULL); SQL Server allows only one unless you use a filtered unique index (WHERE email IS NOT NULL). PostgreSQL 15+ can opt into SQL Server's behaviour with UNIQUE NULLS NOT DISTINCT. A classic interview follow-up.

Which kind of generated id? An auto-incrementing integer is small and fast but guessable and needs one central counter; a random UUIDv4 can be made anywhere but scatters inserts across the index; time-ordered ids (UUIDv7, Twitter's Snowflake) give both. Lesson S01 draws why this matters in MySQL, which stores rows in primary-key order.

S5

Relationships: 1:1, 1:N, M:N

In 30 seconds Tables connect through foreign keys: a column that holds another table's primary key (sales.customer_id holds a customers.id). 1:1: one row matches at most one row on the other side. 1:N: one customer, many sales; the foreign key goes on the many side. M:N: many customers, many car models; it needs a third, junction table holding both keys (sales is one).

Go deeper: self-references, optional vs mandatory, and the schema

customers.referred_by and employees.manager_id point at their own table: a self-referencing (recursive) relationship, which is how trees are stored (org charts, categories, comment threads). Lesson S08 walks such trees with a recursive CTE.

Besides "how many", a relationship has optionality: must every sale have a customer? (yes: customer_id NOT NULL). Must every customer have a sale? (no: Rahul has none). ER diagrams draw both with crow's-foot symbols (Lesson S12).

The schema is the design: which tables exist, their columns and types, keys and rules, and how they reference each other. The instance is the data in it at one moment. (In PostgreSQL and SQL Server, "schema" also means a namespace inside a database, like public or dbo.)

S6

SQL and its five sublanguages

In 30 seconds SQL (Structured Query Language) is the standard language of relational databases (ANSI/ISO since 1986). It is declarative: you say what you want, the DBMS decides how (unlike Java, where you write every step). Its statements fall into five groups: DDL defines structure, DML changes rows, DQL reads rows, TCL controls transactions, DCL controls permissions. Every product speaks a dialect: T-SQL in SQL Server, Oracle SQL, and the MySQL, PostgreSQL and SQLite flavours. (PL/SQL is not Oracle's SQL dialect; it is Oracle's separate procedural language for stored procedures, like PL/pgSQL in PostgreSQL.)
SQL ├── DDL Data Definition CREATE · ALTER · DROP · TRUNCATE · RENAME ├── DML Data Manipulation INSERT · UPDATE · DELETE · MERGE ├── DQL Data Query SELECT (+ WHERE, GROUP BY, HAVING, ORDER BY…) ├── TCL Transaction Control BEGIN · COMMIT · ROLLBACK · SAVEPOINT └── DCL Data Control GRANT · REVOKE

This script makes a new table (DDL), starts a transaction (TCL), adds two rows (DML), commits (TCL) and reads them back (DQL). Try adding INSERT INTO test_drives VALUES (3, 99, 'Kiran', '2024-10-03'); before COMMIT: car 99 doesn't exist, so the foreign key refuses it. The error stops the script there, so COMMIT never runs; this copy is thrown away, but in a real session the transaction would stay open until you send ROLLBACK.

DCL (GRANT, REVOKE) is the one group SQLite does not have: an embedded database has no users; the file's permissions decide. PostgreSQL, MySQL, SQL Server and Oracle all have it (Lesson S11).

Common mistakes: saying "SQL" when you mean a product ("I know SQL" ≠ "I know MySQL": SQL is the language, MySQL one database that speaks it); text in double quotes ("Asha" is a column name in standard SQL; text goes in single quotes); forgetting the ; between statements in a script. Keywords are not case-sensitive (select works); the convention is UPPERCASE keywords, lowercase names. -- starts a comment.
Go deeper: where SQL came from, and the classification debate

IBM researchers (Chamberlin and Boyce) designed SEQUEL in 1974 for System R, based on Codd's 1970 relational model; it was renamed SQL. Oracle shipped the first commercial SQL database in 1979. ANSI standardised it in 1986 and ISO in 1987; the standard keeps growing (SQL:1999 added recursive queries, SQL:2003 window functions, SQL:2016 JSON, SQL:2023 property graphs).

Some books use only four groups and put SELECT inside DML; Oracle's documentation files COMMIT under "transaction control" and GRANT under DDL. The five-way split (DDL, DML, DQL, TCL, DCL) is the one interviews in India expect. TRUNCATE is filed under DDL in every scheme: it releases the table's storage instead of deleting rows one by one. What else it does differs by product (identity reset, rollback, triggers); Lesson S02 compares it with DELETE and DROP.

S7

Interview questions and review

Click a question to see the answer. Say your answer out loud first.

Q1What is a DBMS, and why use one instead of files?
Software that stores and manages a database and is the only way in. Over files it gives: one copy of each fact (no redundancy or inconsistency), safe concurrent access (locks, transactions), integrity rules checked on every change, recovery after crashes, security per user, and a query language so new questions don't need new programs.
Q2DBMS vs RDBMS?
An RDBMS is a DBMS that stores data in tables (relations) linked by keys, enforces those links with foreign keys, supports ACID transactions and is queried with SQL. "DBMS" is the general term and also covers hierarchical, network, file-based and NoSQL systems.
Q3SQL vs NoSQL: when do you pick which?
SQL when data is relational and correctness matters: money, orders, inventory, many joins, ad-hoc reporting. NoSQL when one access pattern dominates at very large scale or the shape varies: sessions and caches (key-value), catalogues and content (document), chat and event logs (wide-column), relationships many hops deep (graph), metrics (time-series). Name the access pattern, not the brand.
Q4Primary key vs unique key?
Both refuse duplicates. A primary key also refuses NULL and there is exactly one per table; it identifies the row and is what foreign keys point to. A table can have many unique keys, and a unique column may hold NULL (many NULLs in PostgreSQL, MySQL, Oracle and SQLite; only one in SQL Server).
Q5Super key vs candidate key vs alternate key?
A super key is any column set that is unique per row. A candidate key is a minimal super key (no column can be removed). The primary key is the candidate you choose; the remaining candidates are alternate keys. Every candidate key is a super key; not every super key is a candidate key.
Q6Surrogate key vs natural key?
A natural key comes from the real world (licence number, email); a surrogate key is a generated number with no meaning (id). Surrogates never change and keep foreign keys small, so most designs use a surrogate primary key plus a UNIQUE constraint on the natural key.
Q7How do you store a many-to-many relationship?
With a junction (bridge) table holding the two foreign keys, one row per link, plus any facts about the link itself. If a pair may appear only once (a student enrols in a course once), make the pair the composite primary key or UNIQUE. If it may repeat (Asha can buy a second Swift next year), it is an event: give each row its own id and do not make the pair unique. sales(id, customer_id, car_id, sold_on, amount) is the second kind.
Q8What are DDL, DML, DQL, TCL and DCL? Give two commands each.
DDL defines structure: CREATE, ALTER, DROP, TRUNCATE. DML changes rows: INSERT, UPDATE, DELETE, MERGE. DQL reads: SELECT. TCL controls transactions: COMMIT, ROLLBACK, SAVEPOINT. DCL controls access: GRANT, REVOKE.
Q9Is TRUNCATE DDL or DML?
DDL. It removes all rows by releasing the table's storage instead of deleting row by row, so it has no WHERE, is much faster and doesn't fire row-level DELETE triggers. The rest depends on the product. Identity counter: reset in MySQL and SQL Server; in PostgreSQL only with TRUNCATE … RESTART IDENTITY (the default is CONTINUE IDENTITY); not reset in Oracle. Rollback: yes inside a transaction in PostgreSQL and SQL Server; no in Oracle and MySQL (it commits implicitly). SQLite has no TRUNCATE: DELETE FROM t without WHERE takes a similar fast path.
Q10OLTP vs OLAP?
OLTP runs the business: many small, fast reads and writes (place an order), normalised tables, row storage (PostgreSQL, MySQL). OLAP analyses it: few large aggregate queries over history (revenue by region by month), denormalised star schemas, column storage (Snowflake, BigQuery, Redshift). Data usually flows from OLTP to OLAP through an ETL pipeline (extract, transform, load: copy the day's rows out, reshape them, load them into the warehouse).
Q11What does ACID mean? Give a one-line example of each.
Atomicity: the sale row and the "car sold" flag are written together or not at all. Consistency: a sale for car 99 is refused because the foreign key must hold after every transaction. Isolation: two sessions selling the last car must not both see it as available (the isolation level decides how strictly). Durability: after COMMIT returns, a power cut cannot lose the sale, because it is in the log on disk. Trap: the C in ACID (rules hold) is not the C in CAP (every copy returns the latest write).
Q12Two users click "Buy" on the last item at the same moment. How do you stop overselling?
Never check in one statement and write in another. Make the check part of the write: UPDATE items SET stock = stock - 1 WHERE id = ? AND stock > 0, then read the affected-row count: 1 = you got it, 0 = sold out. The row lock makes the second UPDATE wait and then re-check the condition. Alternatives: SELECT … FOR UPDATE inside a transaction (pessimistic lock), or a version column checked on update (optimistic lock, Lesson S02). Trap: wrapping the naive read-then-update in a transaction is not enough at the default isolation level of most products.
Q13What is the CAP theorem, and where do PostgreSQL and Cassandra sit?
In a distributed store, when a network partition happens you must choose between consistency (every read sees the latest write, so some requests are refused) and availability (every request is answered, maybe with stale data). A PostgreSQL primary with synchronous replicas chooses consistency (CP). Cassandra and DynamoDB default to availability with eventual consistency (AP), with tunable quorum reads and writes. Trap: CAP is only about the partition case; "CA" is not a real choice for a distributed system.
Q14Can a relational database scale horizontally?
Yes, with effort. Reads: add read replicas (watch replication lag: a user may not see their own write). Writes: shard by a key (customer_id, tenant_id) so each server owns a slice, using Vitess (MySQL) or Citus (PostgreSQL), or pick a NewSQL database (Spanner, CockroachDB, TiDB) that shards and keeps ACID across nodes. The cost: cross-shard joins and transactions are slow, and a bad shard key creates hot spots. Say vertical first (simplest), then replicas, then sharding.
Q15SELECT … WHERE city = 'Chennai' takes 8 seconds on 10 million customers. What is happening, and what do you do?
The plan is a full table scan (the lab above with the index off): the executor reads every page of the table from the buffer pool or disk and tests the condition on each row, so the cost grows with the table, not with the answer. Fix: CREATE INDEX ix_city ON customers(city); the plan becomes a search that walks a few index pages to the first 'Chennai' entry and reads only the matching rows. Check with EXPLAIN before and after. Traps a senior names: the index will be ignored if the value matches most of the table (with only three cities, city = 'Chennai' may return a third of the rows and a scan is cheaper); wrapping the column in a function (LOWER(city) = …) also defeats it; every extra index slows every INSERT and UPDATE. Lesson S13 draws the B-tree walk.
  • A database is one shared, safe copy of the data; the DBMS is the software that guards it.
  • Relational = tables + keys + SQL; NoSQL = document, key-value, wide-column, graph, time-series. Pick by access pattern.
  • Table = relation, row = tuple, column = attribute. Candidate key = minimal super key; the primary key is the one you choose.
  • 1:N puts the foreign key on the N side; M:N needs a junction table.
  • DDL shapes, DML changes, DQL reads, TCL commits or undoes, DCL grants. TRUNCATE is DDL.
  • Check and change in one statement (UPDATE … WHERE in_stock = 1) and read the affected-row count: that is how two users never buy the same last car.
