S1

What a database is

In 30 seconds A database stores facts in tables. A table has columns (the kind of fact: name, price) and rows (one thing: one customer, one car). Every row has the same columns. SQL is the language you use to ask the database questions and to change what it holds. This course's database is a small car dealership: six tables, about sixty rows.

This visualisation needs JavaScript.

💡 Remember itA database is a filing cabinet: a drawer per kind of thing (table), a folder per thing (row), the same labels on every folder (columns), and a number on each folder that no other folder in that drawer has (primary key).
Go deeper: engines, dialects and where SQL came from

The program that keeps the cabinet is a database engine (DBMS): PostgreSQL, MySQL/MariaDB, SQLite, Oracle, SQL Server. They all speak SQL, standardised since 1986, but each has a dialect: small differences in functions, in how you limit rows (LIMIT vs FETCH FIRST vs TOP), in string concatenation (|| vs CONCAT), in dates. This course runs on SQLite because it fits in a browser; the interview answers cover PostgreSQL and MySQL where they differ.

Relational means the data lives in tables (relations) that reference each other by key, instead of in one big nested document. The payoff is that each fact is stored once: a customer's name sits in one row of customers, and every sale just points at it.

S2

Tables, keys and the dealership schema

In 30 seconds A primary key is the column that identifies a row: unique, never NULL (id here). A foreign key is a column that holds another table's primary key: sales.car_id holds a cars.id. That is how tables connect, and the whole design of a database is deciding which drawers exist and which keys link them (the schema).

Go deeper: natural vs surrogate keys, composite keys

A surrogate key is a made-up number (id INTEGER PRIMARY KEY): short, stable, meaningless. A natural key is a real-world value that is already unique (cities.name here). Natural keys read nicely but change (a city renamed) and get long; most teams use surrogate keys and put a UNIQUE constraint on the natural one. A composite key is two or more columns together ((order_id, line_no)). customers.referred_by and employees.manager_id point at their own table: a self-reference, which is how trees (org charts, categories) are stored.

S3

Your first query: SELECT … FROM

In 30 seconds SELECT names the columns you want, FROM names the table. * means every column. ORDER BY sorts, LIMIT cuts, AS renames a column in the result. SQL keywords are not case-sensitive (select works), but the convention is UPPERCASE keywords and lowercase names.

💡 Remember itSELECT is which labels to read, FROM is which drawer. Everything else in a query only decides which folders and in what order.

A query can compute values, not just read them. Watch the division: two whole numbers divide as whole numbers, exactly like 7 / 2 in Java.

Common mistakes: SELECT * in application code (the result changes when the table changes; name the columns); forgetting that ORDER BY is the only way to get a guaranteed order; price / 100000 expecting 6.5; a string in double quotes ("Maruti" is a column name in standard SQL: text goes in single quotes).

S4

How a query really runs: the logical order

In 30 seconds You write SELECT first, but the engine runs FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This one fact explains most SQL confusion: why WHERE cannot see an alias from SELECT (it does not exist yet), why WHERE cannot use COUNT(*) (nothing is grouped yet) while HAVING can, and why ORDER BY can use the alias.

Go deeper: logical order vs what the engine actually does

The order above is the logical order: the rules that define what the result must be. The engine's planner is free to do anything that gives the same answer: use an index instead of reading the whole table, apply a cheap filter before an expensive join, stop early because of LIMIT. Lesson S07 shows the plan. For reading and writing queries, think in the logical order; for performance, read the plan.

Some engines (MySQL, SQLite) let you use a SELECT alias in GROUP BY or HAVING as a convenience; PostgreSQL allows it in GROUP BY but not in HAVING. Portable code repeats the expression.

S5

Primary keys, foreign keys and NULL

In 30 seconds Keys are rules the database enforces: a duplicate primary key is refused, a foreign key that points at nothing is refused, and a refused statement changes nothing. NULL means no value: not 0, not an empty string. Any comparison with NULL is unknown, so city = NULL never matches; use IS NULL. COUNT(*) counts rows, COUNT(col) counts non-NULL values.

Go deeper: constraints you will meet, and SQLite's foreign-key switch

PRIMARY KEY (unique + not null), UNIQUE, NOT NULL, CHECK (price > 0), DEFAULT 1, FOREIGN KEY … REFERENCES cars(id) with ON DELETE CASCADE | SET NULL | RESTRICT to say what happens to the child rows when the parent goes. In SQLite foreign keys are only checked after PRAGMA foreign_keys = ON on each connection (this page turns it on); PostgreSQL and MySQL/InnoDB always check them. S6

Foundations: interview questions and review

Click a question to see the answer. The mock interview on the practice page drills these.

Q1What is the difference between a primary key and a foreign key?
A primary key uniquely identifies a row in its own table: unique and never NULL, one per table. A foreign key is a column in one table that holds the primary key of a row in another (or the same) table; it is how tables relate, and the database refuses values that point at no row.
Q2In what order are the clauses of a SELECT executed?
FROM (and JOIN), WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT/OFFSET. That is why WHERE cannot use a SELECT alias or an aggregate, HAVING can use aggregates, and ORDER BY can use the alias.
Q3WHERE vs HAVING?
WHERE filters individual rows before grouping; HAVING filters groups after GROUP BY, so it can use COUNT, SUM and friends. Put a condition in WHERE whenever it does not need an aggregate: it removes rows earlier and is cheaper.
Q4Why does WHERE city = NULL return nothing?
NULL is "unknown". Any comparison with unknown is unknown, not true, and WHERE keeps only rows whose condition is true. Use city IS NULL or IS NOT NULL.
Q5COUNT(*) vs COUNT(column) vs COUNT(DISTINCT column)?
COUNT(*) counts rows. COUNT(col) counts rows where col is not NULL. COUNT(DISTINCT col) counts different non-NULL values. On services: 8, 6 and (for cost) 6.
Q6What does SELECT * cost you in application code?
The result's shape depends on the table: a new column changes every caller, reads more bytes than needed, and can defeat a covering index. Name the columns.
Q7Is the row order of a query without ORDER BY defined?
No. Engines return rows in whatever order the plan produced them (table order, index order, hash order), and it can change with data size or a new index. Only ORDER BY guarantees an order; for pagination with LIMIT/OFFSET, always sort by something unique.
Q8What is a schema?
The design of the database: which tables exist, their columns and types, their keys and constraints, and how they reference each other. (In PostgreSQL "schema" is also a namespace inside a database, like public.)
  • Table = drawer, row = folder, column = label, primary key = folder number.
  • A foreign key stores another row's key; it never copies the row.
  • Logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
  • NULL is "no value": test with IS NULL; COUNT(col) skips it.
  • Only ORDER BY gives you an order; name your columns instead of *.
