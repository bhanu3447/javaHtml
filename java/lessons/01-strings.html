01

What is a String?

A String is text: a sequence of characters such as "Hello", "42" or "". In Java it is an object (class java.lang.String), not a primitive. The variable holds a reference to the object; the object holds the letters.

Examples
Text is not a number
System.out.println("42" + 1);       // 421
System.out.println(42 + 1);         // 43
System.out.println("42".length());  // 2
"42" is two characters, so + joins text instead of adding.
char vs String
char c = 'H';          // one character, single quotes
String s = "H";        // text, double quotes
System.out.println(c + 1);   // 73   a char is a number (H = 72)
System.out.println(s + 1);   // H1   a String is text
Same letter, different kind: the primitive adds, the object joins.
Empty is not null
String empty = "";       // a real object, length 0
String nothing = null;   // no object at all
System.out.println(empty.length());    // 0
System.out.println(nothing == null);   // true
System.out.println(nothing.length());  // NullPointerException
You can call methods on ""; on null there is nothing to call them on.
02

Three ways to create one

Almost every String you write is a literal: text in double quotes, shared through the String pool. new String(...) always makes a second object (interview material, not everyday code). The third way is text computed from other data, which is always a fresh object.

WayExampleWhere the object comes fromUse it when
LiteralString a = "car";The pool: one shared object per distinct textAlways, by default
newnew String("car")A fresh heap object, outside the poolPractically never (interview questions only)
From datanew String(chars), String.valueOf(42), a.toUpperCase()A fresh heap object, not pooledWhenever the text is computed
Examples
A literal is shared
String a = "car";
String b = "car";
System.out.println(a == b);   // true   one pooled object, two variables
Same text written twice gives the same object (section 04 explains the pool).
new always makes another object
String a = "car";
String b = new String("car");
System.out.println(a == b);        // false  two objects
System.out.println(a.equals(b));   // true   same characters
== asks "same object?", equals asks "same text?" (section 06).
Computed text is a new object
String a = "car";
String up = a.toUpperCase();        // from a method
String num = String.valueOf(42);    // from a number
char[] letters = {'c', 'a', 'r'};
System.out.println(up + " " + num + " " + new String(letters));  // CAR 42 car
System.out.println(new String(letters) == a);                     // false
Anything built while the program runs is a fresh heap object, never the pooled literal.
03

Where a String lives: stack, heap, pool

A running JVM keeps things in three areas. You will meet all three in every memory question, so here is what each one is before the picture.

AreaWhat it isWhat goes thereCreated / removedWhen it is full
StackOne per thread: a pile of frames, one frame per method that is currently runningLocal variables and parameters: primitive values (int n = 7) and references (the "plate" of a String), never objectsA frame is pushed when the method is called and thrown away when it returnsStackOverflowError (endless recursion)
HeapOne for the whole program: the big area for objectsEvery object made with new or a literal: every String, its byte[], arrays, your Cars. The String pool is a table pointing at some of these objectsObjects are created on demand and removed by the garbage collector when nothing points at themOutOfMemoryError: Java heap space
MetaspaceOne for the whole program: the area for classes (it replaced PermGen in Java 8)Each loaded class: its bytecode, method tables and constant pool, which is where the text of a literal such as "Swift" sits until the first use turns it into a heap StringFilled when a class is loaded; emptied only when its class loader is collectedOutOfMemoryError: Metaspace
Which area? One line at a time
public class Garage {                 // the class itself: Metaspace (loaded once)

    void park() {                     // calling park() pushes a frame on the STACK
        int n = 7;                    // stack: the value 7 lives in the frame
        String s = "Swift";           // stack: the reference s  ·  heap: the pooled "Swift"
        String t = s + "!";           // heap: a new object "Swift!"  ·  stack: the reference t
    }                                 // return: the frame is gone, n, s, t vanish;
}                                     // the objects stay on the heap until the GC finds no reference
Variables live and die with the method; objects live as long as something points at them. The text "Swift" starts in the class's constant pool (Metaspace) and becomes a heap String on first use.

So for one String s = "Swift";: the variable s is on the stack, the String object and its byte[] are on the heap, and the String Constant Pool is a table that points at that one shared object (pooled Strings are ordinary heap objects since Java 7).

Because a variable only holds a reference, passing a String to a method copies the reference, not the text. The method can read the same object, but reassigning its parameter only moves its own copy of the plate.

Examples
Two plates, one car
String model = "Swift";
String alias = model;                 // copies the reference, not the text
System.out.println(model == alias);   // true
model = "Dzire";                      // the plate moves to another object
System.out.println(alias);            // Swift   the old object is untouched
Assignment copies the arrow. Moving one variable never affects the other.
A method gets a copy of the plate
static void rename(String name) {
    name = "Gone";            // moves only the method's own copy
}

String s = "Swift";
rename(s);
System.out.println(s);        // Swift
Java passes the reference by value: the method can read the object, not re-point your variable.
Primitive copies the value, String copies the reference
int n = 7;
int m = n;                     // the number 7 is copied
m++;
System.out.println(n + " " + m);   // 7 8

String p = "hi";
String q = p;                  // the arrow is copied
System.out.println(p == q);        // true   one object
An int variable holds the value itself; a String variable holds an address.

Inside the object

A String object is small: a reference to a byte[] called value, a coder (0 = Latin-1, one byte per char; 1 = UTF-16, two bytes) and a cached hash. The characters are in the array, a separate object. Keep that picture: variable, String object, byte array.

length() counts UTF-16 units, not symbols
System.out.println("₹".length());                // 1
System.out.println("😀".length());               // 2   one emoji, two units
System.out.println("😀".codePointCount(0, 2));   // 1   one real character
Most text fits one unit per character; emoji and rare scripts need two (the Unicode lesson comes later).
04

The String Constant Pool (SCP)

The pool keeps one shared copy of each literal, to save memory: write "OK" in five hundred places and there is one "OK" object. Sharing is safe only because a String can never change (section 07). Step through the code below and watch where each variable points.

💡 Remember itThe pool is a shared sticker book. Every "hi" literal in your program uses the same sticker; new String("hi") prints a private copy that is not in the book; intern() hands your copy to the book and gets the book's sticker back.
String pool
Heap (outside the pool)

Pooled automatically

  • Every literal "abc" and every text block
  • Compile-time constants: "a" + "b", "a" + 1, FINAL + "x"
  • static final String constants initialised with literals
  • Anything you call intern() on

Not pooled

  • new String("abc") (the heap object)
  • Runtime concatenation s + "x"
  • Method results: substring, toUpperCase, split, sb.toString()…
  • Text from a file, Scanner, a network or a database

History: Java 6 → 7 → 8

Java 6The pool is in PermGen, which has a fixed size. intern() copies the String. Heavy interning causes OutOfMemoryError: PermGen space.
Java 7The pool moves to the main heap, so pooled Strings can be garbage-collected. intern() stores a reference to the existing object.
Java 8PermGen is removed and Metaspace holds class metadata. The pool stays in the heap.
Java 11+The StringTable is concurrent and resizes itself. The default StringTableSize is 65536 (checked on JDK 25).
Examples
Every literal with the same text is one object
String a = "OK";
String b = "OK";
String c = "O" + "K";                     // joined by javac: a literal again
System.out.println(a == b && b == c);     // true
Three variables, one pooled "OK".
new is outside the pool, intern() gets you back in
String heap = new String("OK");
System.out.println(heap == "OK");            // false  a private copy
System.out.println(heap.intern() == "OK");   // true   the pool's object
intern() looks the text up in the pool and returns the shared copy.
Run-time text is not pooled
String k = "O";
String built = k + "K";                      // computed while running
System.out.println(built == "OK");           // false
System.out.println(built.equals("OK"));      // true
Only literals and constants go into the pool automatically.
The first intern() wins
String fresh = new StringBuilder("zq").append("77").toString();
System.out.println(fresh.intern() == fresh);   // true   "zq77" was not pooled: this object becomes the pooled one
String again = new StringBuilder("zq").append("77").toString();
System.out.println(again.intern() == fresh);   // true   the pool now hands out fresh
System.out.println(again == fresh);            // false
Since Java 7 nothing is copied: the pool stores a reference to the first object interned.

Use intern() rarely: each call is a hash lookup, worth it only for many repeated, long-lived values.

GC and the pool: entries are held weakly, so an unreferenced pooled String can be collected. Literals stay alive while their class is loaded.
Interview answer

The String pool is a JVM-wide table of unique String objects. Every String literal is resolved through it, so equal literals share one object, which saves memory and makes == true between them. Since Java 7 the pool lives in the main heap, so pooled Strings can be garbage-collected. new String("x") always creates a separate heap object, and intern() returns the pooled copy, adding one if needed.

Follow-ups
  • Why not intern everything? — Each call is a hash lookup and the table grows; it pays off only for many repeated, long-lived values.
  • Is the pool a cache for ==? — No. It saves memory; content is still compared with equals.

What new String("x") really does

String s = new String("hi"); compiles to this bytecode (javap -c, JDK 25):

 0: new           #7     // allocate an empty String on the heap
 3: dup                  // keep a copy of the reference
 4: ldc           #9     // get the POOLED "hi" (created on first use)
 6: invokespecial #11    // String.<init>(String): run the constructor
 9: astore_1             // s = the new heap object
  1. ldc resolves the literal and creates the pooled "hi" if this is the first time.
  2. new allocates a second String object on the heap, outside the pool.
  3. The constructor copies value, coder and hash from the pooled String. The byte[] is shared.
  4. s == "hi" is false, and s.equals("hi") is true.

Examples
Two objects, one text
String s = new String("hi");
System.out.println(s == "hi");           // false  s is the heap copy
System.out.println(s.equals("hi"));      // true
System.out.println(s.intern() == "hi");  // true   the pooled one
The literal "hi" is pooled first; new then builds a second object next to it.
Two news, three objects
String a = new String("x");
String b = new String("x");
System.out.println(a == b);                     // false  two heap copies
System.out.println(a.intern() == b.intern());   // true   both find the pooled "x"
One pooled "x" plus one heap object per new.
+ at run time makes one more
String a = new String("a");
String ab = a + new String("b");         // joined while running
System.out.println(ab == "ab");          // false  a fifth object, not pooled
System.out.println(ab.intern() == "ab"); // true
Count them: "a", "b" pooled, two heap copies, and the result.
"java" is pooled by the JDK itself before main runs, so interning a run-time "java" returns the JDK's object, not yours. == "sometimes works" for reasons like this; it is never the right tool for content.
06

== vs equals

== compares the arrows: same object? equals compares the characters. The pool makes == true by accident between literals, which is exactly why it is dangerous: the answer depends on where the String came from, not on what it says.

Examples
Same text, two objects
String a = "Swift";
String b = new String("Swift");
System.out.println(a == b);        // false  different objects
System.out.println(a.equals(b));   // true   same five characters
This is the whole lesson in two lines: content needs equals.
Literal first, so null can't bite
String input = null;
System.out.println("yes".equals(input));   // false
System.out.println(input.equals("yes"));   // NullPointerException
A method call on null throws; a literal is never null, so put it first.
compareTo: only the sign matters
System.out.println("apple".compareTo("apricot"));  // -2   'p' (112) - 'r' (114)
System.out.println("car".compareTo("cars"));       // -1   length 3 - 4
System.out.println("b".compareTo("a"));            // 1
System.out.println("Zebra".compareTo("apple"));    // -7   'Z' (90) - 'a' (97)
Negative = sorts before, 0 = equal, positive = after. Uppercase letters sort before lowercase.
switch and contains already use equals
String cmd = new String("go");
switch (cmd) {
    case "go" -> System.out.println("matched");   // matched
    default   -> System.out.println("no");
}
System.out.println(List.of("go").contains(cmd));  // true
The language and the collections compare text the right way; only a hand-written == gets it wrong.
Rule: compare content with equals(). Put the literal first ("yes".equals(input)) so a null input gives false instead of an exception. The only honest use of == on Strings is a test for null.
07

Why a String can never change

Once a String object exists, its characters are fixed for life. Every method that looks like it changes a String (toUpperCase, trim, replace, +) returns a new object and leaves the old one alone.

Sharingthe pool can hand one object to everyone
Hash cachecomputed once, safe as a HashMap key
Thread safetyno locks needed to read it
Securitya checked path or class name can't change after the check
Class loadingclass names are Strings; they must not change
Examples
The forgotten result
String s = "java";
s.toUpperCase();              // returns "JAVA"... to nobody
System.out.println(s);        // java
s = s.toUpperCase();          // keep the new object
System.out.println(s);        // JAVA
The number one String bug: the method worked, the result was thrown away.
An alias never sees a change
String a = "hi";
String b = a;                 // both point at "hi"
a = a + "!";                  // a new object; only a moves
System.out.println(a + " " + b);   // hi! hi
Nothing can edit "hi", so sharing it is always safe.
StringBuilder is the mutable one
StringBuilder sb = new StringBuilder("hi");
StringBuilder same = sb;
sb.append("!");                  // changed in place
System.out.println(same);        // hi!   one object, both see it

String s = "hi";
String t = s.concat("!");        // a second object
System.out.println(s + " " + t); // hi hi!
Compare the two: a builder edits itself, a String hands you a new one (next lesson).
Safe as a map key
Map<String, Integer> stock = new HashMap<>();
String key = "Swift";
stock.put(key, 3);
key = key.toLowerCase();                  // key now points at a NEW String
System.out.println(stock.get("Swift"));   // 3   the map's key object never changed
System.out.println(key);                  // swift
A key that could change would break the map; immutability plus the cached hash make Strings ideal keys.

💡 Remember itA String method is a photocopier, never an eraser. Ask for s.toUpperCase() and you get a fresh copy with the change on it; the original sheet in the tray is untouched. If you walk away without taking the copy (s.toUpperCase(); on its own), nothing happened. Take it home with s = s.toUpperCase();.
Examples: the six that cover most bugs
Off by one
String s = "Hello";
System.out.println(s.charAt(s.length() - 1));   // o
System.out.println(s.charAt(s.length()));       // StringIndexOutOfBoundsException: Index 5 out of bounds for length 5
Indexes run from 0 to length() - 1.
substring: the end is excluded
String s = "Hello, World";
System.out.println(s.substring(7));              // World
System.out.println(s.substring(0, 5));           // Hello
System.out.println(s.substring(5, 7).length());  // 2   always end - begin
Half-open ranges: the length of the piece is end - begin.
split takes a regex
System.out.println("a.b.c".split(".").length);      // 0   "." matches every char
System.out.println("a.b.c".split("\\.").length);    // 3   escaped: a real dot
System.out.println("a,b,,c,,".split(",").length);   // 4   trailing empties dropped
Escape . | * + ? ( or use replace, which is plain text.
Chain them: each call works on the previous result
String raw = "  Java 25  ";
String clean = raw.trim().toLowerCase().replace(" ", "-");
System.out.println(clean);              // java-25
System.out.println("[" + raw + "]");    // [  Java 25  ]   raw never changed
Three new Strings were made along the way; the original is untouched.
replace vs replaceAll
String s = "a.b.c";
System.out.println(s.replace(".", "-"));        // a-b-c   plain text
System.out.println(s.replaceAll(".", "-"));     // -----   regex: every char
System.out.println(s.replaceAll("\\.", "-"));   // a-b-c
Same name, different rules: replace is literal, replaceAll is a pattern.
Searching: -1 is an answer, not an error
String s = "Mississippi";
System.out.println(s.indexOf("ss"));       // 2
System.out.println(s.indexOf("ss", 3));    // 5    search again after index 3
System.out.println(s.lastIndexOf("i"));    // 10
System.out.println(s.indexOf("z"));        // -1   not found
Check for -1 before you pass an index to substring or charAt.

Compile time vs run time

When every part of a + is a constant (a literal, or a final variable set to a literal), the compiler joins them itself and the result is a pooled literal. With a plain variable the join happens while the program runs and gives a new heap object.

ExpressionDecided== "hello"
"hel" + "lo"Compile time (folded)true
final String p = "hel"; p + "lo"Compile time (p is a constant)true
String p = "hel"; p + "lo"Run time (new object)false
(p + "lo").intern()Run time, then pooledtrue
Examples
Folded by javac
String s = "hel" + "lo";             // the class file just says "hello"
System.out.println(s == "hello");    // true
No joining happens at run time; the literal is pooled like any other.
final makes it a constant
final String p = "hel";
String q = "hel";
System.out.println((p + "lo") == "hello");   // true    p is a constant
System.out.println((q + "lo") == "hello");   // false   q is a variable
One keyword decides whether the join happens at compile time or at run time.
Numbers fold too
String a = "v" + 25;
String b = "v25";
System.out.println(a == b);           // true    "v" + 25 is a constant expression
int n = 25;
System.out.println(("v" + n) == b);   // false   built while running
Any constant expression, not only text, is folded.
Since Java 9 run-time + uses invokedynamic with a recipe like "\u0001lo" and no StringBuilder; before that, javac emitted a StringBuilder. Either way the result is a fresh object. (How + in a loop becomes O(n²), and the StringBuilder fix, is the next lesson.)

10 interview questions

Answer each one in your head before you open it.

01What is a String? Is it a primitive?
An object of the final class java.lang.String: an immutable sequence of characters stored in a byte[]. It is not a primitive, but the language gives it special support (literals, +, switch).
02Where does a String live: stack or heap?
The variable is a reference in a stack frame (or a field in another object). The String object and its byte[] are always on the heap. Pooled Strings are heap objects too, since Java 7.
03What is the String Constant Pool? Where is it?
A table holding one shared copy of each literal (and of each interned String). It moved from PermGen to the main heap in Java 7, so its Strings can be garbage-collected.
04What is the difference between == and equals()?
== compares references and equals() compares characters. Always use equals for content, literal first for null safety.
05How many objects does new String("abc") create?
One or two: the pooled literal (if it isn't already there) plus one new heap object. The two share one byte[].
06What does intern() do?
It returns the canonical pooled copy with the same content, adding this object's reference to the pool if the text is missing. Since Java 7 nothing is copied.
07Why is String immutable?
Pool sharing is safe, the hashCode can be cached for fast HashMap keys, it is thread-safe with no locks, checked values can't change (security), and class loading is reliable.
08Why is "a" + "b" == "ab" true, but a + "b" == "ab" false?
Literal concatenation is a compile-time constant, so it is pooled. With a non-final variable, the String is built at run time as a new object. A final variable makes the result true again.
09Is a String passed by reference?
Java is always pass-by-value: the method gets a copy of the reference. It can read the same object, but reassigning the parameter does not touch the caller's variable, and the String itself can't change anyway.
10Can String be extended? Why is it final?
No. Making it final protects immutability and security (a subclass could otherwise override methods and lie about its content), and it allows JVM optimisations.
11

Review

5 takeaways

  • A String is an immutable object; the variable is only a reference to it. The object and its byte[] live on the heap.
  • Literals go through the String Constant Pool: one shared object per distinct text. new String() always makes a separate heap object; intern() returns the pooled one.
  • Compile-time constants are folded and pooled; anything built at run time is a fresh object.
  • Compare content with equals, literal first. == only says whether two variables point at the same object.
  • Every "changing" method returns a new String; reassign the result, or nothing happens.
