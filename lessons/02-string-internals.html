How a literal becomes an object (lazy resolution)

  1. javac writes "hello" into the class file's constant pool.
  2. When the class loads, the entry is only a symbol. No String exists yet.
  3. The first time the ldc instruction runs, the JVM looks for "hello" in the StringTable.
  4. If it is found, the existing reference is used. If not, a String is created, added to the table and used.
  5. Every later use of that literal, in any class, gets the same object.

D3

The String Constant Pool (SCP) in depth

The pool is a hash table (the StringTable) of references to canonical Strings, one per distinct content. Its job is to save memory by sharing repeated text. Sharing is only safe because Strings are immutable.

💡 Remember itintern() = handing your sticker to the shared sticker book: if the book already has that text you get the book's copy back; if not, yours goes in.

Pooled automatically

  • Every literal "abc" and every text block
  • Compile-time constants: "a" + "b", "a" + 1, FINAL + "x"
  • static final String constants initialised with literals
  • Anything you call intern() on

Not pooled

  • new String("abc") (the heap object)
  • Runtime concatenation s + "x"
  • Method results: substring, toUpperCase, split, sb.toString()…
  • Text from a file, Scanner, a network or a database

History: Java 6 → 7 → 8

Java 6The pool is in PermGen, which has a fixed size. intern() copies the String. Heavy interning causes OutOfMemoryError: PermGen space.
Java 7The pool moves to the main heap, so pooled Strings can be garbage-collected. intern() stores a reference to the existing object.
Java 8PermGen is removed and Metaspace holds class metadata. The pool stays in the heap.
Java 11+The StringTable is concurrent and resizes itself. The default StringTableSize is 65536 (checked on JDK 25).

intern() rules

  • If the pool already has an equal String, intern() returns that reference.
  • Otherwise it adds this object's reference and returns it. The first object to be interned becomes the canonical copy.
  • Use it rarely. It costs a hash lookup each time, and it is only worth it for many repeated, long-lived values.
GC and the pool: entries are held weakly, so an unreferenced pooled String can be collected. Literals stay alive while their class is loaded. String Deduplication (-XX:+UseStringDeduplication; G1 only before JDK 18, all collectors since) is a different feature: equal Strings share one byte[], but they remain separate objects, so == is still false. Flags: -XX:StringTableSize=N, -XX:+PrintStringTableStatistics.
Points 3 and 4 are why == "sometimes works". Its result depends on JDK internals, never on the content. Always use equals().
D4

What new String("x") really does

String s = new String("hi"); compiles to this bytecode (javap -c, JDK 25):

 0: new           #7     // allocate an empty String on the heap
 3: dup                  // keep a copy of the reference
 4: ldc           #9     // get the POOLED "hi" (created on first use)
 6: invokespecial #11    // String.<init>(String): run the constructor
 9: astore_1             // s = the new heap object
  1. ldc resolves the literal and creates the pooled "hi" if this is the first time.
  2. new allocates a second String object on the heap, outside the pool.
  3. The constructor copies value, coder and hash from the pooled String. The byte[] is shared.
  4. s == "hi" is false, and s.equals("hi") is true.

How String.equals() works

hashCode formula

s[0]*31^(n-1) + … + s[n-1]. "" → 0. Why 31? It is an odd prime, and 31*i = (i<<5) - i. The result is cached in the hash field.

The contract

  1. a.equals(b) ⇒ same hashCode
  2. Same hash ⇏ equal ("Aa" and "BB" are both 2112)
  3. Override both, or neither

== happens to be true

  • Two equal literals
  • Compile-time constants
  • Values after intern()
  • substring(0), trim() on already trimmed text (they return this)

== is false despite equal text

  • new String(...)
  • Runtime s + "x"
  • Results of substring, split or replace that changed something
  • User, file or database input

Other tools: equalsIgnoreCase, contentEquals(CharSequence), Objects.equals (null-safe), regionMatches, String.CASE_INSENSITIVE_ORDER. Also, "hello".equals(new StringBuilder("hello")) is false.

Interview answer

== checks whether two references point to the same object. String.equals first checks identity, then that the other object is a String with the same coder and length, and finally compares the bytes. hashCode is s[0]·31^(n−1) + … + s[n−1], cached after the first call. The contract is that equal objects must have equal hash codes, because a HashMap uses the hash to choose the bucket and equals to confirm the key.

Follow-ups
  • Can two different Strings have the same hash? — Yes: "Aa" and "BB" both hash to 2112. The map still keeps them apart with equals.
  • What breaks if you override only equals in your own class? — Two equal keys land in different buckets, so get misses and a HashSet keeps duplicates.
  • Why 31? — It is an odd prime, so it spreads values well, and 31 * h can be computed as (h << 5) - h.
  • What does compareTo return? — The difference of the first differing chars, or the difference in length if one is a prefix of the other.
D6

Immutability: how it is built

  1. The class is final, so no subclass can add mutable behaviour.
  2. value is private final: no outside access, and it can't be reassigned.
  3. No method writes to value.
  4. Defensive copies: constructors copy incoming arrays, and toCharArray() returns a copy.
  5. Every "modifying" method returns a new String, or this if nothing changed.
Variable can point elsewhere?Object can change?
String sYesNo
final String sNoNo
StringBuilder sbYesYes
final StringBuilder sbNoYes: sb.append("x") still works
final ≠ immutable. final locks the variable, while immutability locks the object. Can reflection break String? Since Java 16 the JDK's internals are strongly encapsulated, so setAccessible(true) on String.value throws InaccessibleObjectException.

StringBuilder and StringBuffer internals

💡 Remember itA StringBuilder is a suitcase with spare room. When it is full you buy a bigger one (old × 2 + 2) and move everything across; most packing needs no new suitcase.
                 CharSequence (interface)
          ┌────────────┼──────────────────────────┐
       String   AbstractStringBuilder  (byte[] value · coder · int count)
                       ├── StringBuilder  Java 5   · not synchronized
                       └── StringBuffer   Java 1.0 · synchronized

A builder keeps a buffer bigger than the text. length() is how many characters are used. capacity() is how many fit before it must grow. Try it:

  • Default capacity is 16. new StringBuilder("abc") gets 16 + 3 = 19. new StringBuilder(n) gets exactly n.
  • Growth rule: the new capacity is old * 2 + 2. If that is still too small, it uses exactly what is needed. The old array is then copied in.
  • Growth is rare, so append is O(1) amortised. If you know the final size, pre-size the builder.
  • toString() creates a new String (a copy). Later changes to the builder don't affect it.
  • StringBuffer: every public method is synchronized, and it caches the last toString(). A sequence of calls is still not atomic.
Neither builder overrides equals() or hashCode(). Two builders with the same text are not equal. Use compareTo (11+), contentEquals, or toString().equals(...).

Interview answer

A StringBuilder holds a resizable byte[] plus a count of used positions. The default capacity is 16, or 16 plus the length of the initial String. When an append doesn't fit, it allocates a new array of max(old*2 + 2, needed) and copies the data, so appends are amortised O(1). StringBuffer shares the same parent class, AbstractStringBuilder, but synchronizes its methods. Neither overrides equals, so compare their contents with toString(), compareTo (Java 11+) or contentEquals.

Follow-ups
  • What is length() vs capacity()? — The chars stored vs the room allocated.
  • Does setLength(0) free memory? — No, it keeps the capacity; use trimToSize() to shrink it.
  • Why is a StringBuilder a bad HashMap key? — It is mutable and uses identity equals/hashCode.

How + concatenation works

SituationWhat happens
Only constants: "a" + "b" + 1Folded at compile time into the literal "ab1", which is pooled
Java 5–8, with variablesnew StringBuilder().append(a).append("b").toString()
Java 9+, with variablesOne invokedynamic call to StringConcatFactory.makeConcatWithConstants (JEP 280). By default it works out the exact size and copies once.
+= in a loopEach pass creates a new String and copies everything, so it is O(n²) in every version

Checked with javap on JDK 25: "a" + "b" became ldc "ab", and s + "!" became invokedynamic makeConcatWithConstants.

Left to right

1 + 2 + "3" + 4 + 5 → "3345"
'a' + 'b' → 195 (an int!)

null and concat

null + "x" → "nullx"
"x".concat(null) → NPE. concat only accepts a String.
Interview answer

If every operand is a compile-time constant, javac folds the expression into one literal, which is pooled. Otherwise the result is built at runtime: up to Java 8 javac emitted a StringBuilder append chain, and since Java 9 (JEP 280) it emits a single invokedynamic call to StringConcatFactory, which chooses an efficient strategy at runtime. Either way, a runtime result is a new heap String, not a pooled one, and a loop still needs an explicit StringBuilder.

Follow-ups
  • Does final change the result? — Yes. A final local initialised with a constant is itself a constant, so a + "b" is folded.
  • What does null + "x" give? — "nullx"; concatenation turns null into the text "null".
  • Why move to invokedynamic? — The JDK can improve the strategy without recompiling your classes, and it avoids building and sizing a StringBuilder each time.

CharSequence is the read-only interface shared by String, StringBuilder, StringBuffer and CharBuffer. APIs such as contains, replace, String.join and contentEquals accept any of them.

switch

It switches on hashCode(), then confirms with equals().

HashMap keys

Strings are ideal keys: immutable, with a cached hash. A mutable key gets lost in the wrong bucket.

Passwords

Use a char[] and wipe it with Arrays.fill(pw, '\0'). A String can't be wiped.

Locale

toLowerCase() on a Turkish machine turns I into a dotless ı. Use Locale.ROOT.

25 more interview questions

01Where is the pool in Java 6, 7 and 8+?
Java 6: PermGen (fixed size). Java 7: moved to the main heap. Java 8+: still in the heap. Metaspace replaced PermGen, but it holds class metadata, not the pool.
02Are pooled Strings ever garbage-collected?
Yes. Up to Java 6 only when PermGen was collected (a full GC); since Java 7 they are ordinary heap objects. Entries are held weakly. Literals stay alive while their class is loaded.
03When exactly is a literal added to the pool?
Lazily: the first time its ldc instruction runs.
04What changed in intern() in Java 7?
Java 6 copied the String into PermGen. Java 7+ stores a reference to the existing heap object, so s.intern() == s can be true.
05Does new String("abc") copy the characters?
No. It shares the pooled String's byte[]. Only the String object is new.
06How many objects does new String("a") + new String("b") create?
5 Strings: pooled "a" and "b", 2 heap copies, and "ab" on the heap (not pooled). Before Java 9 there was also a StringBuilder.
07Is "ab" pooled after a runtime a + b?
No. It is only pooled if you call intern().
08Explain the equals/hashCode contract.
Equal objects must have equal hashes. Equal hashes don't imply equal objects. HashMap uses the hash to find the bucket and equals to confirm, so override both together.
09Why is it safe for String to cache its hashCode?
The content can never change, so the hash never changes either.
10Why does hashCode use 31?
It is an odd prime with good spread, and 31*i = (i<<5) - i is cheap.
11Can two different Strings have the same hash?
Yes. "Aa" and "BB" are both 2112.
12When does a String use 2 bytes per char?
When any character is outside Latin-1 (Hindi, Chinese, emoji). Then the coder is UTF16 for the whole String.
13Is final the same as immutable?
No. final stops reassignment of the variable. A final StringBuilder can still change.
14How is String made immutable?
A final class, a private final byte[], no setters, defensive copies, and new objects for every change.
15What is StringBuilder's default capacity, and how does it grow?
16 (or 16 + the initial text length). When full, it grows to old * 2 + 2, or exactly what is needed if that is more.
16length() vs capacity()?
The characters used vs the characters that fit before the buffer grows.
17Why is sb1.equals(sb2) false for the same text?
StringBuilder doesn't override equals, so it compares references. Use compareTo (11+) or toString().equals.
18Is StringBuffer fully thread-safe?
Each call is synchronized, but a sequence of calls (check, then append) is not atomic.
19Why was StringBuilder added in Java 5?
Most building happens in one thread, so StringBuffer's locks were wasted cost. StringBuilder has the same API without them.
20How does + work in Java 9+?
One invokedynamic call to StringConcatFactory. Constant-only expressions are still folded at compile time.
21Is + always slow?
No. A single expression is optimised. It is only slow in loops.
22What does String.valueOf(null) do?
It throws NullPointerException, because the char[] overload is chosen. valueOf((Object) null) returns "null".
23concat() vs +?
concat takes only a String, throws on null, and returns this for an empty argument. + accepts any type and turns null into "null".
24What is CharSequence?
A read-only char-sequence interface implemented by String, StringBuilder, StringBuffer and CharBuffer.
25Why use Locale.ROOT with toLowerCase()?
The default locale can change the result. In Turkish, I becomes ı. Keys and protocols need a stable result.
D13

Concept map

Where

  • Variable (stack) → reference → String (heap) → byte[]
  • Pool = StringTable in the heap (7+), resolved lazily at ldc

Pool and new

  • Literals, constants and intern() are pooled
  • new String("x") = pooled + 1 heap object, sharing the byte[]
  • Counts: 1 · 2 · "a"+"b" → 1 · new+new → 5

Compare

  • == reference · equals content · compareTo order
  • equals: same? → String? → coder → bytes
  • Equal ⇒ same hash, not the reverse

Layout

  • value + coder + hash + hashIsZero
  • Compact Strings: LATIN1 1 B, UTF16 2 B
  • final ≠ immutable

Builders

  • Capacity 16 → old*2+2
  • No equals override
  • Buffer = synchronized, but not atomic across calls

Concat and null

  • Constants folded · 5–8 StringBuilder · 9+ indy
  • null+"x" = "nullx" · valueOf(null) NPE

5 takeaways

  • Since Java 7 the pool is in the heap; literals are pooled lazily when their ldc first runs, and intern() stores a reference, not a copy.
  • A String is a byte[] plus a coder (LATIN1 or UTF16) and a cached hash; final on a variable is not the same as an immutable object.
  • new String("x") creates up to 2 String objects but shares one byte[].
  • Equal objects need equal hash codes; equal hashes don't mean equal objects ("Aa"/"BB").
  • Constant expressions are folded at compile time; everything else is concatenated at runtime (StringBuilder up to Java 8, invokedynamic since Java 9) and is not pooled.
